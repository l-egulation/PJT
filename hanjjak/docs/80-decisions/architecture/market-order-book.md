# 거래소 주문장 아키텍처 결정

## 결정

[거래소 호가창 Office Hours 설계](../../70-plans/market-order-book/design.md)의 제품 정책을 다음 저장·동시성·조회 구조로 구현한다. 현재 적용 경계는 [데이터 권한과 저장 경계](../../50-architecture/persistence.md), HTTP 계약은 [Networking](../../50-architecture/networking.md#거래소주문장-계약)이 소유한다.

- 시장 품목 canonical key는 종류 prefix와 정규화한 소문자 값을 `:`로 연결한다. 재료는 `material:potato_m1`, 스킬북은 `skillbook:active_heavy:normal`, 보석은 `gem:7:attack_speed:1200` 형식이다. 표준 URL namespace에서 `urn:hanjjak:market-instrument`의 UUIDv5를 먼저 파생하고, 그 UUID를 프로젝트 고정 namespace로 사용해 canonical key의 시장 품목 UUIDv5를 생성한다.
- 거래 가능 카탈로그 동기화에서 시장 품목을 선생성한다. 카탈로그에서 제거하거나 거래 불가로 바뀐 품목은 물리 삭제하지 않고 비활성화한다.
- 매수·매도는 `side`로 구분하는 단일 주문 저장 모델을 사용한다. 매수 쌀 escrow와 매도 외부 보관 자산도 이 주문을 참조한다.
- 같은 시장 품목의 지정가·IOC 등록, 수정, 취소, 만료와 품목 비활성화 처리는 시장 품목 row의 비관적 잠금을 먼저 획득해 직렬화한다. 주문 후보에서 `SKIP LOCKED`를 사용하지 않는다.
- 주문장은 활성 주문 원본을 인덱스로 조회해 가격대별 SQL 집계한다. 별도 비동기 depth read model은 최초 구현에 두지 않는다.
- 거래소 전용 계정 guard row를 잠근 뒤 성공 주문 mutation 이력의 최근 1분을 집계해 30회 제한과 활성 주문 수를 원자 판정한다. 성공한 등록·수정·취소만 append-only 이력에 남기며 검증 실패·멱등 재생·0체결 IOC 실패는 세지 않는다. 이력은 30일 보존한다.
- 한 개 이상 체결된 IOC만 종료 주문으로 30일 보존한다. 0체결 IOC 실패는 사용자 주문 내역에 만들지 않고 공통 command 기록으로 7일 보존한다.
- 주문장 depth는 시장 품목 revision이 이전 화면보다 낮으면 폐기한다. revision 간격이나 cursor 변경 오류를 감지하면 선택 품목 주문장·해당 품목 내 주문과 개인 거래소 요약을 전체 재조회하며 복구 중 주문 폼을 잠시 비활성화한다.
- 거래소 읽지 않음은 계정 전체에서 공유하는 체결·물품 수령함·판매 정산·주문 만료 네 stream으로 나눈다. 사건 생성 transaction이 계정·stream별 bigint sequence를 증가시키고, 각 화면의 성공 응답이 제공한 `readThroughSequence`까지 명시적 읽음 command로 cursor를 전진한다.
- 통합 물품 수령은 기존 구매 체결·판매 반환 행을 합치지 않고 행 단위로 이관한다. 개별 수령과 전체 수령은 `createdAt, deliveryId` 순서로 delivery row를 잠가 한 번 지급을 보장한다.

## 비활성 시장 처리

시장 품목을 비활성화하면 새 주문·수정·체결을 즉시 막고 화면에는 `거래 중단·취소 처리 중`을 표시한다. 활성 주문은 worker가 bounded batch transaction으로 취소한다. 매수 escrow는 반환하고 매도 잔량은 통합 물품 수령함으로 이동하며, 완료 전에는 해당 주문을 `취소 처리 중`으로 표시한다.

## 기존 데이터 이관

- 기존 활성 판매 주문은 각 행을 새 매도 주문 한 건으로 옮기고 `createdAt`을 우선순위 시각으로 보존한다. 구형 가격 수정 주문도 소급 재정렬하지 않는다.
- 기존 활성 구매 예약은 새 maker 가격 규칙으로 옮기지 않고 취소해 남은 escrow를 반환한다.
- 기존 구매 수령 물품과 판매 반환 물품은 원본 행·체결·주문 참조를 보존해 새 delivery 한 건으로 각각 이관한다.
- 잔량과 실제 escrow·외부 보관이 불일치하는 주문은 자동 보전하거나 전체 이관을 막지 않고 `복구 검토 중`으로 격리한다. 정상 주문은 계속 이관한다.
- 운영 검토는 원장으로 확인한 자산만 반환하거나 무반환 종료할 수 있다. 근거·결정자·시각을 영구 discrepancy 감사 기록에 남기며 임의 보상은 별도 관리자 보상 흐름으로 처리한다.
- 종료 주문·체결·delivery는 거래 당시 표시명 snapshot을 보존해 시장 품목이 비활성화돼도 UUID만 노출하지 않는다.

## 이상 탐지와 인수 기준

- 같은 계정·시장 품목·방향에서 성공한 취소 후 재등록 또는 가격 변경이 10분 안에 20회 이상이면 반복 주문 후보로 표시한다.
- 후보는 주문을 막거나 사용자에게 경고하지 않고 근거와 규칙 버전을 기록해 운영 검토에 제공한다.
- 비정상 가격의 수치 기준은 실제 30일 분포를 확인하기 전까지 미확정이다. 주문·호가·체결 원본은 보존하되 임의 배수로 차단하거나 표식하지 않는다.
- 최초 부하 인수는 단일 hot instrument에 동시 주문 mutation 100개를 실행해 응답 오류·timeout 0, p95 3초 이하, maker 가격·엄격한 가격/시간 우선순위와 자산 불변 조건을 모두 만족해야 한다.

## 선택 근거

- UUIDv5는 환경과 재동기화 사이에서 같은 시장 품목 ID를 유지하면서 표시명·속성 컬럼의 변경을 식별자와 분리한다.
- 단일 주문 모델은 양방향 수정·상태·내역·인덱스 규칙을 한곳에 유지한다.
- 품목 row 직렬화는 hot instrument 처리량을 제한하지만 엄격한 가격·시간 우선순위를 가장 단순하게 증명한다.
- 원본 SQL 집계는 첫 범위의 각 5단계 depth에 충분하며 비동기 read model의 지연·복구를 만들지 않는다.
- DB 성공 이력과 서버 읽음 cursor는 프로세스 재시작·다중 기기에서도 rate limit과 알림 상태를 잃지 않는다.

## 명시적으로 수용한 비용

같은 시장 품목의 모든 주문장 mutation은 직렬화되므로 인기 품목의 처리량 상한과 lock 대기가 생긴다. depth SQL 집계 비용도 주문 수와 함께 증가한다. 최초 인수 기준을 넘지 못하거나 운영 계측에서 병목이 확인될 때만 matcher queue 또는 동기 depth table을 별도 결정으로 검토한다.

## 미해결

비정상 가격 후보의 기준 가격, 배수·기간과 저유동성 예외는 실제 주문·체결 분포가 없으므로 unresolved다. I-07은 데이터 30일 수집과 오탐 검토 후 이 수치만 확정한다.
