## 1. 목적

운영자가 게임 상태를 빠르게 진단하고, 승인된 절차 안에서만 안전하게 복구하며, 모든 고위험 행동의 근거와 결과를 추적할 수 있는 별도 운영 콘솔을 기획한다. 플레이어용 게임 규칙을 새로 정의하지 않으며, 각 화면은 책임 SSOT의 상태를 조회하거나 해당 도메인 유스케이스에 명령을 보낸다.

`admin-console`은 게임 웹의 숨겨진 메뉴가 아니라 별도 빌드·배포·권한 경계를 가진 React·Vite 애플리케이션이다. DB를 직접 편집하는 범용 CRUD 도구로 만들지 않는다.

## 3. 기획 원칙

1. **읽기 우선**: 1차 화면은 조회와 진단에 집중한다. 쓰기 기능은 실제 운영 사고를 해결하는 명시적 유스케이스만 허용한다.
2. **도메인 명령만 사용**: 자산·진행·거래·세션 변경은 DB 행 편집이 아니라 서버 application command로 처리한다.
3. **최소 권한**: 메뉴 노출이 아니라 서버가 매 요청의 역할·기능 권한·대상 범위를 검증한다.
4. **감사 가능성**: 모든 로그인, 조회, 내보내기, 승인, 변경 시도를 성공·실패와 함께 남긴다. 감사 기록은 운영자가 수정하거나 삭제할 수 없다.
5. **안전한 실패**: 부분 지급, 부분 복구, 조용한 기본값 보정을 금지한다. 충돌은 현재 상태를 다시 읽고 재검토하게 한다.
6. **개인정보 최소화**: 목록은 닉네임·계정 ID 중심으로 제공하고 이메일은 권한이 있는 상세 조회에서만 표시한다. 비밀번호·세션 쿠키·전투 토큰은 절대 표시하지 않는다.
7. **정적 콘텐츠 불변**: 운영 화면이 배포된 콘텐츠 파일을 직접 수정하지 않는다. 새 콘텐츠는 검증·승인·배포 과정을 거친 버전으로만 전환한다.

## 4. 역할과 권한 후보

2026-09-11 사용자 지시로 사용자 상태 조정과 거래소 운영 명령은 `ADMIN`만 실행하는 현재 구현 기준을 사용한다. 사용자 상태 조정은 `user:manage`, 거래소 운영은 `market:manage` 권한을 요구한다. 다른 역할·명령은 아래 후보이며 구현 전에 [미해결 결정](#12-미해결-결정)을 확정해야 한다.

| 역할 후보 | 기본 책임 | 허용 기능 후보 | 명시적 제한 |
| --- | --- | --- | --- |
| `VIEWER` | 읽기 전용 상황 파악 | 대시보드, 계정 요약, 경제·콘텐츠·감사 조회 | 개인정보 상세, 내보내기, 모든 변경 불가 |
| `CS_OPERATOR` | 사용자 문의 조사 | 계정 상세, 진행·자산 원장·전투·명령 조회, 승인된 보상 요청 작성 | 직접 상태 조정, 정책 변경, 배포 불가 |
| `GAME_OPERATOR` | 게임·경제 운영 | 지표, 주문·체결·정산 조사, 콘텐츠 버전 비교·배포 요청 후보 | 사용자 상태 조정·인프라 배포·복원, 감사 삭제 불가 |
| `ENGINEER` | 장애 진단 | health, 배포 버전, 오류·지연·Outbox 상태, 상관 ID 추적 | 사용자 상태 조정은 별도 권한 없이는 불가 |
| `ADMIN` | 운영자·사용자·시장 관리 | 사용자 성장·자산·진행·치장·장비 조정, 역할 관리, 거래소 운영, 고위험 작업 승인 후보 | 자기 권한 상승, 감사 삭제, 예약·장착 상태 침범, 이미 체결된 거래 소급 취소·환수 불가 |

권한은 `resource:action` 형태의 세분 권한으로 서버에서 판정한다. 현재 사용자 상태 조정은 `user:manage`, 거래소 운영은 `market:manage`를 사용하며 `ADMIN`에만 부여한다. 다른 후보는 `account:read`, `account:pii-read`, `ledger:read`, `compensation:request`, `compensation:approve`, `content:promote`, `deployment:read`, `operator:manage`, `audit:export`다. 역할은 권한 묶음일 뿐 API가 역할명에 직접 분기하지 않는다.

사용자 상태와 거래소 외 일반 고위험 변경은 요청자와 승인자를 분리하는 2인 승인을 기본 후보로 둔다. 현재 사용자·거래소 운영 명령은 `ADMIN` 단독 실행, 운영 사유·멱등 키·append-only 감사 기록을 사용한다. 별도 2인 승인이나 break-glass가 필요하면 후속 정책으로 결정한다.

## 5. 정보 구조와 화면

### 5.1 운영 홈

첫 화면은 “지금 문제가 있는가, 어디부터 봐야 하는가”에 답한다.

- 서비스별 health/readiness와 현재 배포 commit SHA·콘텐츠 버전
- 최근 오류율·응답 지연·활성 전투·명령 실패 요약
- Outbox `PENDING`·재시도·최장 대기 시간과 소비 지연
- 가입·활성·전투 완료·실패·거래량·쌀 생성/소각의 기간 비교
- 미수령 정산, 장시간 미완료 command, 비정상 주문 등 조사 대기 항목
- 지표 카드에서 필터가 적용된 상세 화면으로 이동

현재 확정 데이터는 health와 일별 경제 지표 일부다. 활성 사용자, 오류율, command 적체, Outbox 지연은 필요한 계측 계약을 먼저 추가해야 한다.

### 5.2 계정·사용자 관리

- 계정 ID·정확한 이메일·닉네임 검색. 이메일 부분 검색은 개인정보 노출 위험 때문에 기본 제공하지 않는다.
- 계정 상태, 생성·최근 활동 시각, `stateVersion`, 활성 인증·게임 세션, 진행·자산·전투·명령 타임라인을 조회한다.
- `ADMIN`은 명시적 운영 사유와 멱등 키로 레벨·누적 경험치, 쌀 절대값·추가량, 스택 아이템 절대 수량·추가량, 보석 옵션별 추가·삭제, 목표 스테이지까지 순차 해금, 치장 등록·미등록 수량, 장비 부위별 등급·강화 단계를 조정한다.
- 아이템·치장·보석의 판매 예약 수량, 장착 보석, 인벤토리 200슬롯과 콘텐츠 허용 목록·도메인 상한을 그대로 검증한다. 예약·장착 자산을 암묵적으로 해제하지 않는다.
- 레벨·누적 경험치와 장비·치장처럼 전투 입력에 영향을 주는 조정은 활성 게임·전투 세션을 종료한다. 이미 확정된 전투·원장·거래·감사 이력을 다시 쓰지 않는다.
- 쌀 조정은 지갑 원장에 `ADMIN_USER_ADJUSTMENT`로 기록하고 절대값 설정도 실제 차이만 원장에 남긴다.
- 모든 성공·실패 조정은 관리자 ID·GitLab username·action·대상 계정·사유·멱등 키·전후 서버 상태 요약·request ID를 append-only 감사 로그에 남긴다.

닉네임·주력 재료 변경, 장착 상태 강제 변경, 스테이지 클리어 기록 위조, 과거 전투·거래·원장 삭제는 제공하지 않는다.

### 5.3 보상·복구 센터

운영 보상은 잔액 칸을 직접 덮어쓰지 않고 만료되지 않는 첨부 우편을 생성하는 command로 처리하는 방안을 제안한다. 실제 허용 대상·한도·승인 정책은 미확정이다.

- 사전 등록된 보상 템플릿 또는 항목별 보상 초안 작성
- 단일 계정·조건으로 산출한 계정 목록·확정 대상 스냅샷 지원 후보
- 사유 코드, 관련 장애·Jira 링크, 요청자, 승인자, 만료 시각 기록
- 실행 전 대상 수·총 지급량·인벤토리 수용 가능 여부·중복 지급 키 미리보기
- `Idempotency-Key`로 중복 실행 방지, 전체 성공 또는 전체 실패
- 실행 후 우편 ID·원장·command·감사 이벤트 연결
- 같은 보상 건의 재실행 대신 미처리 대상만 새 command로 명시

금지 기능: SQL 실행, 쌀·아이템 절대값 덮어쓰기, 이미 소비된 자산의 이력 삭제, 성공 결과를 되돌린 것처럼 보이게 하는 감사 수정.

### 5.4 거래소·경제 운영

- 현재 일별 공급량, 등록·취소·체결량, 거래 금액, 수수료, 정산액, 쌀 생성·소각 조회
- 주문 UUID 또는 정확한 아이템 ID로 사용자·시스템 주문을 조회한다.
- 특정 활성 주문의 미체결 잔량을 운영 사유와 함께 강제 취소한다. 매도 잔량과 매수 escrow는 사용자에게 반환하지 않고 시스템 sink로 제거한다.
- 시스템이 특정 사용자 매도 주문을 지정 수량만큼 구매한다. 정상 체결·수수료를 남기고 판매자 정산액은 즉시 지갑에 지급한다.
- 시스템이 중첩 거래 품목을 임의 총수량·단가로 하나의 매도 주문에 등록한다. 수량은 양의 저장 정수 범위 안에서 허용한다.
- 모든 변경은 `market:manage`, `Idempotency-Key`, 운영 사유와 감사·도메인 이벤트를 요구한다.

이미 체결된 거래의 소급 취소·자산 환수, 보석 인스턴스 임의 생성, 자동 유동성 공급과 가격 보호는 제공하지 않는다. 탐지 규칙도 I-07이 미완료이므로 대시보드에서 확정된 제재처럼 표현하지 않는다.

### 5.5 게임 진행·전투 진단

- 챕터·스테이지별 진입·클리어·실패 수와 이탈 지점
- 실패 코드, 콘텐츠 버전, 전투 스펙 스냅샷, seed·logical tick·예측 hash 불일치 조회
- 활성·만료·중단 전투 세션과 최근 50건 기록의 계정 타임라인
- 장비·스킬·보석·치장 효과가 전투 입력에 반영된 버전 확인
- 특정 전투의 서버 재현 입력 내보내기 및 `balance-lab` 재현 연결 후보
- 콘텐츠 버전별 클리어율·소요시간 비교

진행도 해금·클리어 직접 변경과 실행 중 전투 결과 강제 확정은 제외한다. 잘못된 진행을 복구해야 한다면 별도 도메인 명령과 보상 정책을 먼저 결정한다.

### 5.6 콘텐츠·밸런스 운영

- 현재 배포 manifest, 파일별 checksum, `working`·`applied` 상태와 참조 무결성 조회
- 이전 버전과 챕터·스테이지·드롭·장비·스킬·보석·치장 변경 diff
- content validator와 결정론 simulation 결과 확인
- 승인된 artifact만 배포 요청하고 실행 중 세션 영향·마이그레이션 필요 여부 확인
- 활성화 전 dry-run, 승인, 배포, smoke, rollback 지점을 한 변경 기록으로 연결

브라우저 폼에서 개별 수치를 즉석 수정하거나 운영 DB에 콘텐츠를 복제하지 않는다. 미확정 `working` 값을 `applied`로 승격하는 권한과 승인 절차는 결정 로그를 거쳐야 한다.

### 5.7 이벤트·명령·Outbox 진단

- event ID, event type, account ID, command ID, request/correlation ID 검색
- command의 `PROCESSING`·`SUCCEEDED`·`FAILED`와 멱등 키 fingerprint 비교
- Outbox의 생산 시각, 전달 상태, 시도 횟수, 다음 재시도 시각, 오류 요약
- 생산 command와 Kafka 전달·소비 결과의 연결
- 오래된 `PROCESSING`, 반복 실패, 소비 지연 큐
- 재처리 전 대상 이벤트·소비자의 멱등성 지원 여부 확인

임의 payload 수정·삭제는 제공하지 않는다. 재처리 기능은 소비자 멱등성과 재처리 정책이 확정된 이벤트만 허용한다.

### 5.8 운영 상태·배포

- game-api·web·admin-console·worker·consumer·PostgreSQL의 health/readiness
- 현재·이전 commit SHA image set, 배포 시각, 실행 주체, smoke 결과
- 요청률·오류율·지연, DB 연결·락 대기, 디스크·백업 최신성
- 로그·trace·metric의 request/correlation ID 연결
- 백업 목록·검증 시각, restore drill 결과, rollback 가능 버전
- 배포·rollback·restore는 GitLab protected job 또는 기존 운영 스크립트의 승인된 실행 링크로 연결

콘솔 서버가 Docker socket, 운영 DB 관리자 계정, 백업 파일 시스템을 직접 소유하지 않는다. 기존 protected runner와 명시적 확인 경계를 우회하지 않는다.

### 5.9 감사·권한 관리

- 운영자 로그인 성공·실패, 권한 변경, 개인정보 조회, 내보내기와 모든 변경 요청·결과를 검색한다.
- actor GitLab username·관리자 ID, action, 대상, 운영 사유, 변경 전후 서버 상태 요약, 결과, 멱등 키, request ID, 원격 주소와 발생 시각을 표시한다.
- 관리자 ID·action·조작 여부 필터와 최근 200건 조회를 제공한다. 감사 조회 자체도 감사 기록에 남긴다.
- 운영자 계정 활성화·비활성화, 역할 부여·회수, 세션 강제 폐기는 후속 범위다.
- 본인 권한 변경과 감사 기록 수정·삭제를 허용하지 않는다.

감사 원문에는 비밀번호, 세션 쿠키, OAuth token, 전체 인증 헤더, 불필요한 개인정보, 대형 도메인 payload를 저장하지 않는다. 전후 요약은 관리자 페이지가 반환한 서버 권한 상태 범위로 제한한다.

## 6. 공통 조회·상호작용 규칙

- 기본 기간은 짧게 시작하고 서버 제한이 있는 cursor 페이지를 사용한다.
- 모든 표는 로딩·빈 결과·부분 장애·권한 없음·오래된 데이터 상태를 구분한다.
- 시간은 UTC 원본과 운영자 로컬 표시를 혼동하지 않게 표기하며, KST 일자 판정 지표는 기준을 명시한다.
- 위험 명령은 대상과 효과를 읽기 가능한 문장으로 다시 보여 주고 사유 입력을 필수로 한다.
- 확인창의 버튼 연타 방지에 의존하지 않고 서버 멱등성과 최신 `stateVersion`을 검증한다.
- 대량 작업은 대상 조건과 대상 ID snapshot을 분리 기록한다. 실행 시점에 조건을 다시 평가해 대상이 조용히 달라지지 않게 한다.
- CSV 내보내기는 현재 필터, 컬럼, 행 수, 요청자를 기록하고 짧은 수명의 다운로드로 제공한다.

## 7. API와 데이터 경계

- 운영 API는 플레이어 API와 구분되는 `/api/admin/v1/...` namespace 후보를 사용한다.
- `admin-console`은 TypeSpec에서 생성한 전용 client만 사용한다. 서버 DB schema나 내부 DTO를 직접 참조하지 않는다.
- 같은 사용자 세션 쿠키를 운영자 인증에 재사용하지 않는다. 운영자 identity와 session은 별도 저장·폐기 경계를 가진다.
- 읽기 모델은 application query가 만들고, 쓰기는 각 도메인 application command를 호출한다.
- 운영자 권한을 위해 플레이어 리소스의 소유자 검증을 끄지 않는다. 별도 admin authorization 정책을 통과한 명시적 endpoint만 대상 계정을 지정할 수 있다.
- mutation은 멱등 키, 사유, 감사 context를 요구하고 원본 도메인 변경과 감사·Outbox 기록을 가능한 같은 원자 경계에 둔다.
- 거래소 운영 mutation은 로그인 불가능한 시스템 계정을 주문·체결의 상대 계정으로 사용해 외래 키와 이력을 유지한다. 시스템 구매 물품과 강제 취소 잔량·escrow는 시스템 sink로 처리하고 플레이어 자산으로 반환하지 않는다.
- 대시보드 지표는 원본 권한 상태가 아닌 파생 읽기 모델임을 표시하고 집계 지연 시각을 노출한다.

## 8. 보안 요구사항

1. 운영자 인증은 SSAFY GitLab OAuth 2.0 Authorization Code와 PKCE S256을 사용한다. `read_user` scope로 현재 사용자의 안정 GitLab ID와 `username`을 확인하고, 활성·비잠금 계정과 배포 설정의 `username` 화이트리스트를 모두 만족해야 관리자 세션을 발급한다. 로컬 운영자 비밀번호 로그인은 제공하지 않는다.
2. 운영 UI는 게임 web의 같은 `PUBLIC_ORIGIN` 아래 `/admin/`에서 제공하되 별도 build·container·운영자 identity·session·API 권한 경계를 유지한다. 경로를 안다는 사실은 권한이 아니며 서버가 모든 `/api/admin/v1` 요청을 검증한다.
3. OAuth `state`는 서버 DB에 해시로 저장해 10분 내 한 번만 소비한다. 공급자 access·refresh token은 사용자 확인 뒤 저장하지 않는다.
4. 운영 세션은 Secure·HttpOnly 쿠키, 명시적 Origin 검증, 비활성·절대 만료를 적용한다. 화이트리스트에서 제거된 사용자의 세션은 다음 요청에서 폐기한다.
5. 계정 검색·개인정보 상세·내보내기·고위험 명령에 별도 rate limit을 둔다.
6. 서버는 화면에서 숨긴 버튼과 무관하게 endpoint마다 권한을 검사하고 다른 운영자·역할 정보의 노출 범위를 제한한다.
7. 감사 저장소는 append-only와 별도 보존·접근 정책을 가져야 하며 애플리케이션 관리자도 원문을 수정할 수 없어야 한다.
8. 운영 secret, DB credential, OAuth token, 세션 cookie, Docker socket, backup encryption key를 브라우저나 운영 API 응답에 노출하지 않는다.

MFA 방식, `/admin/`의 추가 접근 프록시 여부, 감사 보존 기간은 미확정이다.

## 9. 단계별 우선순위

### P0 — 출시 전 읽기·진단 기반

- 운영자 인증·권한·세션 분리

- 모든 운영자 접근과 조회의 감사 로그

- 특정 주문 강제 취소·시스템 구매와 단일 시스템 매도 주문의 임의 수량 등록

## 10. 명시적 제외 범위

- 운영 DB 범용 테이블 편집기와 SQL 콘솔
- 플레이어 비밀번호 조회·재설정, 세션 쿠키·OAuth token·전투 토큰 열람
- 판매 예약 아이템·치장과 장착 보석의 암묵적 해제·삭제
- 과거 원장·거래·command·감사 이벤트 삭제·수정
- 실행 중 전투 결과 강제 성공과 스테이지 클리어 기록 위조
- 콘텐츠 수치의 브라우저 즉시 수정·무검증 활성화
- 게임 web route에 운영 화면 숨기기
- 정책 미확정 상태의 계정 정지와 이미 체결된 거래의 소급 취소·자산 환수 자동화

## 11. 성공 기준

- CS 운영자가 계정 ID 또는 정확한 이메일로 계정을 찾고 진행·자산·최근 전투·실패 command를 하나의 타임라인에서 조사할 수 있다.
- 엔지니어가 배포 SHA·콘텐츠 버전·request/correlation ID에서 로그·trace·Outbox 상태까지 추적할 수 있다.
- 경제 운영자가 기존 일별 지표를 기간·계열·세대·아이템으로 조회하고 주문·체결·정산 불일치를 조사할 수 있다.
- 권한 없는 운영자는 UI 직접 접근과 API 직접 호출 모두에서 동일하게 거절된다.
- 개인정보 조회·내보내기와 모든 mutation의 요청·승인·결과가 변경 불가능한 감사 기록으로 남는다.
- 보상 같은 승인된 mutation은 중복 요청에도 한 번만 처리되고 원장·우편·command·감사 기록이 서로 연결된다.
- admin-console 장애나 권한 시스템 장애가 플레이어 게임 API와 공개 web의 정상 이용을 막지 않는다.

## 12. 미해결 결정

다음 항목은 이 제안이 임의로 확정하지 않는다. 구현 이슈를 나누기 전에 [결정 로그](../../80-decisions/README.md)에 상태와 영향을 등록하고 관련 SSOT로 전파해야 한다.

1. 운영자 MFA, `/admin/` 추가 접근 프록시 여부와 최종 세션 수명
2. 최종 역할·세분 권한 목록, 역할 부여 주체와 권한 회수 절차
3. 거래소 운영 외 2인 승인 대상, 금액·수량·대상 수 한도, break-glass 허용 여부
4. 계정 상태 enum, 정지·해제·강제 로그아웃·삭제 정책
5. 운영 보상의 허용 자산·템플릿·우편 문구·중복 판단·인벤토리 만석 처리
6. 이미 체결된 거래 취소·환수·피해 보상의 허용 여부와 정합성 절차
7. 콘텐츠 승격 승인자, 예약 배포, 실행 중 세션의 버전 전환·rollback 기준
8. Outbox 재처리 가능 이벤트와 소비자별 멱등성·dead-letter 처리
9. 감사 로그의 저장소, 보존 기간, 마스킹, export와 삭제 법적 기준
10. 개인정보 검색·표시·내보내기 범위와 보존 정책
11. 운영 지표 backend, SLO·경보 임계값, 온콜 채널
12. admin-console container 장애 격리와 web reverse proxy health·fallback 기준
