# 캐릭터·치장 구현 우선 설계

## 목적

캐릭터 성장 영역 중 `캐릭터`와 `치장/도감`을 먼저 완성한다. 새 서버 아키텍처를 설계하지 않고 현재 `modules/cosmetics`, `apps/game-api`, `apps/web` 구조를 재사용한다. 현재 미커밋 캐릭터 창을 정리하고, 잘못 구현된 30종 치장 개발 콘텐츠를 66종 임시 카탈로그로 clean cutover한다.

실행 상태와 완료 증거는 [K-21](../../wiki/06-delivery/tasks/K-client-ux/k-21-cosmetics-vertical-slice.md)과 [K-22](../../wiki/06-delivery/tasks/K-client-ux/k-22-character-window.md)가 소유한다. 게임 규칙은 [치장 SSOT](../../30-domain/cosmetics/ssot.md), 전투 합산은 [전투 SSOT](../../30-domain/combat/ssot.md), 화면 정보 구조는 [클라이언트 UX SSOT](../../30-domain/player/ux/ssot.md)가 소유한다.

## 이번 범위

포함한다.

- 캐릭터 능력치 조회와 출처 표시
- 캐릭터 창의 능력치·치장·도감 탭
- 66종 임시 치장 카탈로그
- 치장 뽑기, 최초 자동 등록, 중복 재고, 다음 성급 등록
- 도감 세트 구성·세트 성급·세트 효과
- 6부위 착용·해제와 정보 카드 기반 미리보기
- 200회 마일스톤 조회·수령 UI
- 전설 선택 상자 조회·사용 UI
- TypeSpec, 콘텐츠 검증, Kotlin 단위·서비스 테스트, React API·컴포넌트 테스트

제외한다.

- 장비·스킬·보석 화면 통합
- 미등록 중복 치장의 거래소 연동
- 실제 치장 표시명과 이미지 제작
- 실제 캐릭터 외형 합성 렌더러
- 신규 서버 서비스·저장소 아키텍처
- PostgreSQL·Spring Boot·브라우저 실환경 E2E
- 동시 요청 부하 검증

## 카탈로그

### 영구 ID

- 치장 ID는 `cosmetic-001`부터 `cosmetic-066`까지다.
- ID만 영구 식별자다. 표시명, 이미지, 현재 등급·세트·부위 배치는 콘텐츠 버전이 소유한다.
- 정식 출시 전 임시 콘텐츠 배치를 바꿀 때는 개발 데이터를 초기화한다. 운영 보유 데이터를 임의 변환하지 않는다.

### 현재 개발 콘텐츠 버전

- 노말 4세트, 희귀 3세트, 영웅 3세트, 전설 1세트
- 총 11세트, 세트당 6종, 총 66종
- 각 세트는 `HEAD`, `TOP`, `BOTTOM`, `GLOVES`, `SHOES`, `CAPE`를 정확히 하나씩 가진다.
- 현재 버전에서는 구현과 검증을 단순하게 하기 위해 번호 순서로 세트와 부위를 배정한다. 이 배정은 영구 ID의 의미가 아니라 교체 가능한 콘텐츠 값이다.
  - `001~024`: 노말 4세트
  - `025~042`: 희귀 3세트
  - `043~060`: 영웅 3세트
  - `061~066`: 전설 1세트
  - 각 연속 6개 안에서는 `HEAD`, `TOP`, `BOTTOM`, `GLOVES`, `SHOES`, `CAPE` 순서다.

### 미정 표시 데이터

- `displayName`과 `imageUrl`은 nullable 콘텐츠 필드다.
- 표시명이 없으면 클라이언트가 번호에서 `치장 #001` 형식을 만든다.
- 세트 표시명이 없으면 `세트 #01` 형식을 사용한다.
- 이미지가 없으면 이미지 영역에 `이미지 준비 중`을 표시한다.
- fallback 문자열은 저장 콘텐츠나 영구 이름으로 취급하지 않는다.
- 이름과 이미지가 없어도 뽑기·등록·성급·도감·착용은 동작한다.

## 뽑기와 성장

- 공통 1회 비용은 5,000쌀, 10회 비용은 50,000쌀이다.
- 이 비용은 콘텐츠 고정값이다. `stage.02-10` 획득량에서 런타임 계산하지 않는다.
- 등급 확률은 노말 50%, 희귀 35%, 영웅 14%, 전설 1%다.
- 등급을 먼저 추첨하고 같은 등급의 활성 치장을 동일 가중치로 추첨한다.
- 전설 당첨은 전설 1세트의 6종에서 나온다.
- 티켓을 먼저 사용하고 부족한 횟수에 쌀 비용을 적용한다.
- 10회 할인·최소 등급 보장·중복 방지·미보유 보정은 없다.

누적 등록량에 적용하는 등급별 성급 임계값은 다음과 같다.

| 등급 | 1성 | 2성 | 3성 | 4성 | 5성 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 노말 | 1 | 480 | 720 | 1,200 | 2,400 |
| 희귀 | 1 | 168 | 252 | 420 | 840 |
| 영웅 | 1 | 134 | 202 | 336 | 672 |
| 전설 | 1 | 2 | 3 | 5 | 10 |

## 화면 흐름

### 캐릭터 창

- 메인 화면의 `캐릭터` 버튼은 현재 브라우저 문서 위에 단일 dialog를 연다.
- 창은 열릴 때마다 능력치 탭에서 시작한다.
- 탭은 `능력치`, `치장`, `도감`이다.
- 창을 열고 닫아도 기존 전투 화면을 unmount하지 않는다.

### 능력치

- 합계, 기본, 추가 스탯 순서로 표시한다.
- 공격력·최대 HP·방어 관통·치명타·공격속도·기본공격 피해·버프 지속시간을 서버 계산 결과로 표시한다.
- 레벨·장비·보석·패시브 스킬·치장 세트의 출처와 적용·제외 이유를 표시한다.
- 클라이언트는 합계, 반올림, 중복 제외와 상한을 재계산하지 않는다.

### 치장

- 현재 착용 6부위와 부위별 보유 치장 정보 카드를 표시한다.
- 카드에는 fallback 이름, 안정 ID, 부위, 등급, 성급, 등록·미등록·예약·사용 가능 수량을 표시한다.
- 카드 선택은 임시 미리보기만 바꾸고 `착용`에서 서버 상태를 변경한다.
- 착용 해제를 제공한다.
- `치장 뽑기`로 기존 뽑기 화면에 이동하고 돌아오면 치장 탭을 연다.

### 도감

- 11개 세트와 선택 세트의 6부위 구성·보유·성급·수량을 표시한다.
- 치장별 `다음 성급까지 등록`만 제공한다.
- 세트 성급은 6부위 치장 성급의 최솟값이며 서버가 계산한다.
- 도감 단계·도감 보상·도감 전투 효과는 없다.
- 세트 성급 효과만 전투 능력치에 반영한다.

### 마일스톤과 선택 상자

- 전설 배너 성공 결과를 누적하고 200회마다 선택 상자 1개 수령 자격을 만든다.
- 뽑기 화면에 누적 횟수, 다음 상자까지 남은 횟수, 수령 가능 수량을 표시한다.
- `1개 수령`과 `전체 수령`을 제공한다.
- 선택 상자는 전설 세트 6종 중 하나를 선택해 사용한다.
- 상자 결과도 최초 자동 등록·중복 재고·세트 갱신 규칙을 따른다.

## 구현 경계

- 기존 `CosmeticsService`, `CosmeticGachaService`, `CosmeticsCommandService`와 JDBC 저장소를 재사용한다.
- 기존 마일스톤·선택 상자 API를 확장하거나 연결하며 중복 구현하지 않는다.
- 콘텐츠 schema와 loader는 30종·2세트·도감 단계 효과 전용 제약을 제거한다.
- `collectionTiers`, `collectionTier`, `collectionEffect`와 고정 3축 legacy 효과 표현을 제거한다.
- 세트 효과는 안정 `statId`, 정수 `value`, `unit`으로 표현한다.
- 성급 임계값은 전역 배열이 아니라 등급별 배열로 읽는다.
- 능력치 조회와 전투 입력은 같은 순수 계산 결과를 사용한다.
- 상태 변경은 기존 UUID 멱등 키와 payload fingerprint 방식을 유지한다.
- 콘텐츠 버전 불일치는 클라이언트에서 합치지 않고 관련 조회를 다시 수행한다.

## 오류와 불변 조건

- 잠금, 재화 부족, 중복 재고 부족, 최대 성급, 미보유 착용, 부위 불일치, 수령 가능 상자 없음, 잘못된 상자 선택을 구분한다.
- 실패 시 재화·티켓·보유량·등록량·착용·마일스톤·상자를 부분 변경하지 않는다.
- 표시명·이미지 누락은 오류가 아니라 공식 fallback 조건이다.
- ID 중복, 확률 합계 오류, 11세트·6부위 불일치, 등급별 임계값 오류, 세트 효과 단위 오류가 있으면 콘텐츠를 활성화하지 않는다.

## 검증과 완료 판정

필수 검증:

1. 콘텐츠 validator: 66종, 11세트, 등급별 세트 수 `4/3/3/1`, 각 세트 6부위, ID 유일성, nullable 표시 데이터, 확률 합계, 등급별 임계값, 효과 단위.
2. Kotlin 테스트: 등급 추첨과 등급 내 풀, 신규·중복, 등급별 성급, 세트 최솟값, 효과 합산, 마일스톤 수령, 선택 상자, 멱등 재시도, 실패 원자성.
3. React 테스트: fallback 카드, 미리보기와 착용 분리, 등록, 마일스톤, 선택 상자, 로딩·잠금·오류·재시도.
4. TypeSpec 생성, 웹 typecheck·test·build, Gradle 관련 테스트.

이번 작업은 위 검증이 통과하면 `개발 완료 / 부분 검증`으로 기록한다. PostgreSQL 실제 migration, Spring Boot HTTP, 실제 Chromium E2E, 동시 요청과 실제 외형 렌더링을 수행하기 전에는 `검증 완료`로 올리지 않는다.
