# 데모 플레이 데이터·리플레이 수집 설계안

[분야 개요](README.md)

## 상태와 기준

데모의 플레이 통계, 전체 플레이 관찰용 리플레이, 메뉴·커서 기록을 위한 설계다. **로컬 리플레이 기록·코덱·관찰 창의 초기 구현**은 별도 클라이언트 문서의 실제 범위를 따른다. 현재 간소 서버는 [player_id 기반 수집](player-data-collection.md)과 [서버 명세](replay-server-storage.md)를 따른다. 이 문서의 전체 analytics/diagnostics 이벤트 API·동의 범위별 토큰·자동 분석·운영 전체를 구현한 상태는 아니다. 아래 수집률·용량·보관 기간은 측정과 운영 결정을 위한 제안값이다. 게임 규칙·보상·저장 정책을 새로 확정하지 않는다.

문서 역할은 이 문서(기본 통계·동의·분석), [클라이언트 기록](replay-recording.md)(파일/로컬 저장), [서버 저장](replay-server-storage.md)(업로드/검증/보관)으로 나눈다. 상세 규칙이 겹치면 각 담당 문서를 단일 원본으로 읽는다.

플레이 기준은 [런 구조](../../design/run/run-structure.md), [UI·상호작용](../../design/ui/ui-and-interaction.md), [전투 규칙](../../design/combat/rules.md)이다. 연결 기준은 [현재 코드 구조](../architecture/architecture.md), [다중 입력 장치](../presentation/ui/input-devices.md), [전투 명령·결과](../gameplay/combat/combat.md#명령-접수와-실행-결과)를 따른다. 실제 데모에 포함된 콘텐츠만 기록한다.

## 1. 수집 목적과 범위

| 확인할 질문 | 필요한 기록 |
|---|---|
| 시작 후 출발·정비소·보스·클리어까지 얼마나 도달하나? | 세션·런·진행 이벤트와 구역 방문 |
| 어떤 적·패턴에서 죽고 죽기 전 무슨 일이 있었나? | 확정 피격·사망, 장비 상태, 전후 리플레이 |
| 두 무기와 잉크·성장·포탈을 사용하는가? | 시작 장비, 행동 시작, 장비/성장 변경, 포탈 결과 |
| 길 찾기나 UI에서 막히는가? | 이동 궤적, 구역 재방문, 화면·hover·selection·focus·활성화 |
| 어떤 환경에서 느리거나 진행이 중단되나? | 제한된 환경 정보, 성능 요약, 정제한 오류, 기록 공백 |

아래 세 범위는 미구현 확장 설계다. 현재 제품은 첫 실행부터 리플레이 기록을 기본 활성화하고, 서버 주소가 있으면 별도 전송 동의 없이 자동 업로드한다. 기록·대기 전송은 제품 화면에 버튼·설정 창을 두지 않고 백그라운드에서 처리한다. 기존에 명시적으로 중단한 설정은 유지한다. 아래 확장 설계의 동의 범위와 기본값은 현재 제품의 자동 수집 정책과 구분하며, replay에서 주요 사건을 추출하는 현재 경로를 아래 analytics-only 수집과 혼동하지 않는다.

동의 범위는 `analytics`(기본 플레이 통계), `replay`(입력·월드 상태·UI·커서), `diagnostics`(성능·오류)로 나눈다. `replay`는 `analytics`를 켠 경우에만 선택할 수 있다는 UI 제안이며, `diagnostics`는 독립 선택이다. 기본값은 모두 꺼짐을 제안한다. 선택하지 않아도 플레이할 수 있게 한다. 동의 이전 행동은 소급 녹화하지 않는다.

`analytics`는 화면 열기/닫기와 업무 결과만 받으며 hover·selection·focus·좌표·개별 전투 입력은 받지 않는다. 상세 UI와 입력은 `replay`에만 속한다. 표에 적힌 필드도 해당 범위가 꺼져 있으면 저장하지 않는다.

이름·이메일·계정 로그인·광고 ID·하드웨어 고유번호·운영체제 사용자명·파일 경로·자유 입력 내용·클립보드·음성·화면 캡처는 수집 대상에서 제외한다. 창 밖의 마우스와 다른 프로그램의 행동은 기록하지 않는다. 실제 사용자 데이터는 Git과 `resources/`에 넣지 않는다. 개발용 합성 기록과 일회성 검증 출력은 Git 제외 `outputs/`를 사용한다.

## 2. 식별자·시간·버전

| 필드 | 정의 |
|---|---|
| `player_id` | 현재 간소 수집에서 사용하는 무작위 UUID. 자동 전송 시작 시 생성해 로컬 유지하며 저장 영역 변경/삭제 시 새 ID 허용. 아래 확장 설계의 installation_id 역할 |
| `session_id` | 앱 실행마다 UUID. 기록을 시작하는 시점부터 관측하며, 다음 실행의 대기 업로드는 원래 ID 유지 |
| `run_id` | 실제 런 시작 성공 시 UUID. 타이틀·마을·준비 화면은 `null`. 같은 런의 챕터 이동은 유지 |
| `segment_id` | 리플레이 구간 UUID. 자동 기록 시작·씬/맵 변경·전투 세션 리셋·기록 재개 시 새 구간 |
| `entity_id` | 구간 내 단조 ID. 액터·탄·드롭·포탈 등에 부여하고 소멸 후 재사용하지 않음. 런타임 객체 참조를 직렬화하지 않음 |
| `event_id`, `event_seq` | 이벤트 UUID와 세션 내 증가 정수. 재전송에도 그대로 유지 |
| `realtime_ms` | 세션 기준 단조 실제 경과시간. 일시정지·메뉴·창 포커스 상실에도 기준 시계는 진행 |
| `sim_tick`, `sim_time_ms` | 해당 전투 세션의 실제 논리 tick/시간. 월드가 없으면 `null`. 세그먼트·전투 세션 ID와 함께 해석 |
| `session_started_at`, `received_at` | 클라이언트 관측 시작 UTC와 서버 수신 UTC. 기기 시각으로 사건 순서를 정하지 않음 |
| `schema_version`, `capture_profile_id` | 형식 버전과 주기·정밀도·제한을 묶은 불변 수집 설정 ID |
| `build_id`, `content_hash`, `ui_layout_version` | 불변 빌드 ID, 배포 콘텐츠 매니페스트 해시, UI 배치 버전 |
| `environment` | `demo`, `development`, `test` 구분. 공개 지표는 `demo`만 포함 |

전투 리셋으로 tick이 0이 되어도 실제 시간과 세션 순번은 계속 증가한다. 한 tick 안 사건은 원본 결과 순번을 보존한다. 클라이언트의 player/설치 ID는 인증 수단이 아니다. 현재 간소 공개 쓰기 API는 ID 연결만 검사하고, 아래의 서버 자격 발급은 확장 제안이다.

어느 범위든 켜져 있으면 설치·세션·빌드·동의 연결에 필요한 최소 메타데이터만 공통 등록한다. `diagnostics`만 켜져 있으면 런·장비·UI 상태나 기본 플레이 이벤트를 함께 보내지 않는다. 모든 범위가 꺼져 있으면 수집용 설치/세션 등록도 하지 않는다.

## 3. 기본 플레이 통계 (`analytics`)

공통 이벤트 필드는 `event_id`, `event_seq`, `schema_version`, `capture_profile_id`, `session_id`, `run_id?`, `segment_id?`, `realtime_ms`, `sim_tick?`, `type`, `payload`다. 설치·빌드·콘텐츠·동의 버전은 세션 외래키로 연결하며 전송 요청에서 검증한다. 아래 payload는 허용 목록이고 임의 딕셔너리·문자열 로그를 받지 않는다.

| 이벤트 | 기록 시점 | payload |
|---|---|---|
| `session_started` | 동의한 수집 시작 | OS 계열/주 버전, 플랫폼, 언어, 입력 장치 계열, 해상도·UI 배율, 최초/반복 실행 구분 가능 여부 |
| `session_state_changed` | 창 활성·비활성/일시정지 변경 | 상태, 이유 코드. 창 제목·다른 앱 정보 없음 |
| `session_heartbeat` | 활성 수집 중 60초마다 및 상태 변경 | 마지막 이벤트 순번, 누적 관측/포커스/시뮬레이션 진행 시간, 현재 화면·런·구역 |
| `session_ended` | 정상 종료 처리 가능 시 | 종료 이유, 각 누적 시간. 강제 종료에서 발생을 보장하지 않음 |
| `run_started` | 출발이 실제 성공 | 시작 챕터, 시작 무기 2종·슬롯 순서, 활성 슬롯, 팔레트/잉크 구성, 관련 해금 ID와 단계 |
| `chapter_entered` | 챕터 진입 완료 | 챕터 ID, 맵 인스턴스 ID, 생성기 버전·시드, 이전 챕터 ID |
| `region_entered`, `region_left` | 구역 경계를 실제 통과 | 맵/구역 인스턴스 ID, 원형 ID, 일반/정비소/엘리트/보스/기믹 종류, 방문 순번. 시작 시 이미 내부면 entered 한 번 |
| `encounter_started`, `encounter_ended` | 실제 교전 시작/종료 | 적 콘텐츠·개체 ID, encounter ID, 보스 phase, 종료 이유, 누적 피해/처치/경과시간. 시작은 인식 또는 전투 소유자의 사실로 연결 |
| `player_damaged` | 플레이어 피해 적용 확정 | 원인 적·공격 ID, 피해/흡수량, 전후 HP, 구역, 플레이어 위치, 활성 슬롯, 당시 장비 revision |
| `player_died` | 사망 확정 | 마지막 확정 원인 이벤트 ID 또는 `unknown/environment`, 구역·위치, 장비 revision, 만난 보스의 남은/최대 HP |
| `equipment_changed` | 장착·교체·해제 성공 | 원인, 대상 무기/슬롯, 전후 구성, 장비 revision. 메뉴 클릭만으로 발생시키지 않음 |
| `reward_resolved` | 보상 제시/선택/포기/실제 지급 확정 | 보상 묶음 ID, 후보 콘텐츠 ID, 선택 ID, 결과와 실제 지급량. 제시와 지급을 별도 phase로 구별 |
| `economy_changed` | 실제 재화·성장 상태 변경 | 거래 ID, 원인, 재화 ID, 전후 잔액/증감, 대상 강화·해금 ID와 전후 단계 |
| `portal_resolved` | 설치·이동 완료/취소/거절 | 포탈 1/2, 단계, 원인 코드, 출발·도착 구역. 키 누름을 성공으로 세지 않음 |
| `screen_opened`, `screen_closed` | 실제 화면 수명 변경 | 화면 ID, 인스턴스 ID, 부모 화면 ID, 열기/닫기 이유(취소·피격·완료·씬 종료 등) |
| `run_ended` | 결과가 확정 | `death/clear/abandon`와 근거, 도달 챕터/구역, 실제/시뮬레이션 시간, 처치·방문 수, 장비, 재화/조각 정산 결과, 보스 HP |
| `combat_summary` | 구역 이탈·런 종료 | 해당 구간의 무기별 실제 기본/특수 시작 횟수·활성 시간·가한 피해, 적 종류별 처치 수, 대시·점프·패링 횟수, 원본 결과 유실 수 |

`abandon`은 마을 귀환 등 실제 포기를 확정하는 동작만 뜻한다. 앱 종료·heartbeat 중단은 사망이나 포기로 만들지 않는다. 전투 소유자가 교전 경계를 제공하지 않으면 일반 적 교전은 `unsupported`로 표시하고 보스의 명시적 경계부터 연결한다. 보스 처치와 출구 이용·챕터 클리어를 별도 사건으로 유지한다.

장비 구성은 콘텐츠 ID, 런 내 무기 인스턴스 ID, 무기 슬롯, 팔레트 칸별 색·해금/강화 단계·잉크/스탬프 ID, 해석된 주요 스탯을 가진다. 생성되지 않은 미정 콘텐츠는 채우지 않는다. 연속적인 동일 구역 출입은 사실을 유지하되 도달률의 방문 수는 구역별 첫 진입을 사용한다.

예를 들어 보스에게 피격된 기록은 `player_damaged`에 공격 ID·피해·전후 HP를 남긴다. 같은 피해로 사망하면 `player_died`가 그 이벤트 ID를 참조하고, `run_ended`가 실제 결과를 확정한다. UI에서 무기 스킬을 눌렀다는 입력만으로 공격 횟수나 피해를 늘리지 않는다.

## 4. 전체 플레이 관찰용 리플레이 (`replay`)

기록 수명·샘플링·바이너리 파일·snapshot·로컬 큐·복구의 단일 원본은 [리플레이 기록·로컬 저장 설계](replay-recording.md)다. 타이틀·마을·런·결과의 전체 관찰 시간을 기록하고, 기록 시작 전 행동은 소급 수집하지 않는다.

기록된 상태를 표시하는 관찰 재생을 목표로 하며 물리/AI의 결정론적 재실행이나 게임 이어하기를 보장하지 않는다. 용량은 압축 후 5MiB/시간 이하를 최적화 목표, 10MiB/시간을 대표 플레이의 검토 기준으로 둔다. 플레이어/카메라·커서는 변화 시 최대 10Hz, 화면 주변 적은 최대 5Hz가 관측 후보의 상한이며 변화분과 경로 단순화로 저장점을 줄인다. 화면 밖 궤적과 프레임 단위 판정 확인은 지원 범위에서 구별한다. 이 수치는 예상 용량이나 실제 측정 결과가 아니다.

## 5. 메뉴·포인터 기록 (`replay`)

상세 이벤트·좌표·안정적인 UI ID·민감 입력 제외의 단일 원본은 [클라이언트 문서의 메뉴·포인터 계약](replay-recording.md#5-메뉴포인터와-개인정보-경계)이다. hover(커서 아래 대상), selection(선택된 대상), input focus(입력을 받는 컨트롤), 창 활성은 독립 상태로 기록한다. 화면 열기/닫기는 analytics에도 남지만 상세 포커스·좌표·클릭 경로는 replay 범위에만 속한다.

## 6. 성능·오류 (`diagnostics`)

환경은 OS 계열/주 버전, CPU 코어 수 범주, RAM·VRAM 용량 범주, GPU 제조사/제품군, 렌더 API, 그래픽 품질·해상도, Unity 버전으로 제한한다. 원본 시스템 정보 전체를 덤프하지 않는다. 입력 장치는 키보드/마우스/일반 패드/DualSense/Xbox 계열만 기록하고 기기 serial·native ID는 보내지 않는다.

60초 단위로 실제 frame time p50/p95/p99, 최대 프레임 시간, 사전 정의한 긴 프레임 임계값·횟수, 관리 메모리·GC 할당 요약, 수집기 CPU 시간·대기 바이트·전송 성공/실패·누락 개수를 기록한다. 프레임 시간은 클라이언트에서 bounded histogram으로 집계하고 개별 프레임 목록은 전송하지 않는다.

오류는 `error_code`, 빌드, 씬/구역, 정제한 stack의 메서드 식별자·fingerprint, 발생 횟수만 보낸다. 예외 메시지·URL·토큰·절대 파일 경로는 제거하고 허용 목록에 없는 문자열은 폐기한다. native crash dump·메모리 덤프 수집은 이 설계에 포함하지 않는다. 같은 fingerprint는 세션당 최초 상세 1건과 횟수로 제한한다. 강제 종료 뒤 종료 이벤트가 없다는 이유만으로 crash로 분류하지 않는다.

## 7. 서버 저장 모델과 파일 계약

파일 내용·순번·압축·해시는 [클라이언트 파일 계약](replay-recording.md#6-조각-파일-계약-제안-v1), 서버 API·DB·파일 상태는 [서버 저장 설계](replay-server-storage.md)를 단일 원본으로 삼는다. 리플레이 샘플은 압축한 조각 파일로 비공개 객체 저장소에 두고, DB에는 세션/런 연결·검색·무결성·완료 정보만 저장한다.

기본 통계는 설치·동의·빌드·세션·런·events·diagnostics 관계를 가진다. events는 event ID와 `(session_id,event_seq)`를 고유 키로 검사하고, 허용 type/payload와 유한 값·길이/크기 상한을 검증한다. 이 통계 경로와 replay의 record_seq는 다른 순번 공간이며 원본 사실 ID로 연결한다.

## 8. 전송·복구·접근

리플레이의 준비·업로드·검증·확정·재시도·권한 계약은 [서버 문서](replay-server-storage.md)를 따른다. 업로드 성공과 검증 완료는 별개이며, 최종 해시가 일치하는 committed 확인 후에만 로컬 조각을 지운다. 원격 기록 완전성·재생 호환성과 런 결과도 구별한다. 파일 누락·heartbeat 중단을 사망/포기로 만들지 않는다.

기본 통계는 HTTPS로 최대 30초 또는 100건마다 배치 전송하고 event ID/seq와 내용을 유지해 재시도한다. 현재 동의·설치 소유권을 매 요청 검사한다. 종료 시 flush를 시도하되 게임 종료를 기다리게 하지 않으며, 무한 재시도를 하지 않는다. 기록 손실과 늦은 수신을 원본 완전성에 반영한다.

## 9. 보관·철회 제안

| 데이터 | 제안 보관 |
|---|---|
| 리플레이·상세 UI/커서와 관련 메타데이터 | 수집 시점부터 30일 |
| 식별 가능한 세션·런·기본 이벤트·진단 | 수집 시점부터 90일 |
| 설치/세션/런 ID를 없애고 재식별 위험을 검토한 일별 집계 | 최대 180일. 해당 검토 전에는 익명 집계라고 부르지 않음 |
| 로컬 미전송 기록 | 최대 7일 또는 용량 상한 |

범위를 끄면 해당 수집과 대기 업로드를 즉시 멈춘다. 화면에는 이후 수집 중지와 기존 기록 삭제를 구분해 제공한다. 삭제 요청은 계정 없이 로컬에 보관한 서버 발급 삭제 자격으로 인증하고, 실데이터/검색 인덱스/객체/연결 메타데이터를 함께 파기한다. 자격을 잃었을 때의 지원 절차는 운영 결정 항목이다.

이미 발급한 업로드 URL은 만료 전 사용할 수 있으므로 완료 API에서 철회 revision을 다시 검사하고, 철회 이후 들어온 객체는 채택하지 않고 제거한다. 철회된 대기 기록을 다시 켰을 때 소급 업로드하지 않는다. 새 범위 revision으로 이후 기록만 시작한다.

삭제 접수 후 즉시 조회 차단·업로드 거부, 운영 저장소는 7일 내 파기, 백업은 최대 30일 내 만료를 제안한다. 백업 복원 시 삭제 표식을 먼저 적용해 복구를 방지한다. 연결된 집계도 원본 식별자가 남아 있으면 삭제 대상이다. 프로세서 로그·접근 로그·백업 보관도 서비스별로 함께 확인한다. 이는 제품 운영 제안이며 법적 적합성 확인 완료를 뜻하지 않는다. 배포 국가·이용자 연령·실제 서비스/리전·위탁/국외 이전·안내 문구는 공개 배포 전 별도 확정한다.

## 10. 분석·재생 화면의 조회 기준

- 기본 목록: 빌드, 런 시작/결과/미확인, 실제·시뮬레이션 시간, 도달 챕터·구역, 무기 조합, 사망 원인, 보스 HP, 리플레이 완전성. 사망 직전 60초·보스 진입·UI 장기 체류로 이동한다.
- 진행 도달률: 관측된 세션 중 출발한 세션 비율과, 시작한 런 중 각 진행 지점에 처음 도달한 런 비율을 구분한다. 보스 처치율과 출구 이용 클리어율을 구분한다.
- 사망 분석: 만난 적/공격 수 또는 교전 시간도 함께 보여 준다. 단순 사망 건수만으로 가장 강한 적을 정하지 않는다. 원인 미확인은 독립 범주다.
- 무기 분석: 선택률·실제 행동 시작 횟수·사용 시간과 결과를 함께 본다. 유저 숙련도·진행 상태·맵 구성 차이를 분리하지 못한 상관관계를 무기의 효과로 단정하지 않는다.
- UI 분석: 화면 체류시간에서 창 비활성 시간을 제외하고, hover/selection 시간과 실제 활성화·업무 성공을 구분한다. 빈 곳 클릭·비활성 대상·실패 결과을 찾는다.
- 재생: 해당 빌드의 콘텐츠로 카메라·액터·UI·포인터·선택 테두리를 표시하고, 공백/낮은 주기/호환 불가를 타임라인에 표시한다. 누락 구간을 추정 영상으로 감추지 않는다.
- 리플레이·분석 동의자만 관측한다는 표본 편향과 설치 ID의 사람 수 한계를 표시한다. 미전송/불완전 런을 완주율의 실패로 일괄 계산하지 않는다.

## 11. 연결 위치와 구현 순서

현재 `CombatLab/Editor/CombatInputRecorder.cs`의 실험용 입력 녹화와 전투의 `ICombatCommands`·결과 polling·확정 명중 관측 경계 외에, [클라이언트 문서](replay-recording.md)의 로컬 기록기와 UI/전투 어댑터가 있다. 원격 전송과 실제 전체 런의 재생 품질/용량 검증은 별개다. 실험장의 녹화가 Player 전체 런에서도 결정론적으로 동작한다고 간주하지 않는다.

수집기는 읽기 전용 어댑터로 연결한다. `LocalInput`의 단일 소비 큐를 두 번째로 비우지 않고, 이미 해석된 액션과 실제 소비/결과를 관측한다. 전투 polling은 독립 cursor를 가지며 원본 ring 유실을 `capture_gap`으로 전달한다. 세션/런 경계, 장비·경제·월드 변경은 각 소유자의 성공 사실에서 읽고 문자열 로그나 HP 감소로 성공을 추측하지 않는다. 수집 오류는 게임 명령을 재실행하거나 게임 시간을 변경하지 않는다.

1. 동의·세션/런·기본 이벤트와 로컬 큐부터 구현하고, 합성 데이터로 수집 API·중복 방지·삭제를 검증한다.
2. 타이틀·마을·가방·정비소의 UI ID·레이아웃·hover/selection/focus·커서와 시간 축을 연결한다.
3. 해석 레이아웃·월드 상태·확정 사건으로 짧은 관찰용 리플레이를 구현한다. 사망 전후, 포탈, 메뉴 중 피격, 일시정지와 챕터 이동을 재생한다.
4. 30분 이상의 전체 플레이와 대규모 탄/적 상황으로 주기·디스크/CPU/네트워크 비용을 측정하고 전체 런 업로드·검색·재생을 연결한다.

검증 Editor·Player 빌드는 저장소 기준 **Unity 6000.6.5f1**과 원본 패키지를 사용한다. 구현 수락 조건은 동의 전/꺼진 범위 payload 0건, 성공/요청 구별, UI 포커스 3종 구별, 해상도·배율/스크롤 변화 복원, 같은 tick 순서·정지/리셋 시간 처리, 무선 끊김/강제 종료·재전송/중복/부분 파일 처리, 권한 우회·잘못된 파일 차단, 철회/삭제 후 늦은 업로드 거부다. 리플레이와 당시 실제 화면의 위치·장비·HP·UI 상태를 대조하되 프레임 단위 동일성은 별도 목표로 둔다.

## 12. 공개 배포 전 미정 사항

- 공급자·리전·플랜과 운영 접근 담당자. 초기 후보는 Supabase이며 외부 서비스는 아직 만들지 않는다.
- 실제 데모 대상 인원·평균/최대 플레이 시간·예산과, 측정한 시간당 압축 바이트를 근거로 한 설치별/일별 업로드 한도.
- 전체 런 관찰 재생의 표시 품질 승인, 플레이어/커서 10Hz·화면 주변 적 5Hz와 압축 10MiB/시간 목표·큐 한도의 측정 결과에 따른 확정.
- 동의 범위 UI·문구, 제안 보관/삭제 기간, 배포 국가·연령에 따른 실제 운영 절차.
- 정확한 호환 빌드/콘텐츠·재생기의 보관 위치·기간·접근과, 삭제 자격 분실 시 지원 절차.

이 항목을 확정하기 전에는 제안값을 운영 계약이나 이미 승인된 제품 규칙으로 취급하지 않는다.
