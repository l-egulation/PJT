# 협업과 문서 갱신

[분야 개요](README.md)

현재 규칙은 `docs/design/`, 현재 구현 범위와 방법은 `docs/development/`를 수정한다. 문서 링크는 저장소 상대 경로를 사용한다. 동일한 규칙·수치를 여러 문서에 복사하기보다 기준 원본을 연결한다.

결정·변경·작업·검증 이력은 Git 커밋 본문에 남긴다. 기록용 문서, 검증 보고서, 과거 안내 보관함을 추가하지 않는다. 새 결정은 명세 변경과 같은 커밋 흐름에서 이유를 기록한다.

커밋은 최대한 파일별·편집 의도별로 분리한다. 같은 파일의 서로 다른 의도는 부분 스테이징으로 나눈다. 원본·생성물·참조 수정처럼 함께 반영해야 유효한 파일만 묶고 본문에 그 이유를 적는다. 구체적인 규칙은 [AGENTS.md](../../AGENTS.md)를 따른다.

```text
docs(combat): 낙사 복귀의 안전 접지 선택 조건을 명확히 한다

대상: docs/design/combat/rules.md
의도: T-3보다 최근 접지를 선택하는 해석을 막는다.
변경: 정확한 기준 시각과 과거 유효 표본의 선택 조건을 명시한다.
검증: 문서 링크 검사 통과. 실행 동작 변경 없음; Unity 미실행.
```

진행률은 [설계 체크리스트](../design/combat/checklist.md)에서만 관리한다. 설계 완료를 구현·검증 완료로 표시하지 않는다. 이미지와 실행 파일의 전달은 [에셋 복원 안내](../assets/README.md)를 따른다.

## 분야별 책임과 변경 경계

실명 담당은 실제 배정된 내용만 기록한다. 아래는 사람을 새로 배정하는 표가 아니라 작업을 넘길 때 필요한 역할 구분이다.

| 역할 | 유지할 원본·전달 내용 | 함께 확인할 상대 분야 |
|---|---|---|
| 기획 | 목적·확정 규칙·미정·기대 동작, 지정된 수치 원본 | 개발·아트·UI의 적용 가능 범위 |
| 개발 | 현재 구현·목표 구조 구분, 데이터 연결·실행·실패 조건 | 기획·에셋·검증 |
| 아트·모션 | 제작 기준본·승인 범위·규격·배포 패키지 | 판정·타격 시각·씬 적용 |
| UI·연출 | 표시 상태·입력·전환·완료/취소/실패 | 도메인 상태·제어 소유권·스토리 |
| 검증 | 환경·커밋·씬·절차·기대/실제·남은 제한 | 해당 기능의 명세·구현 담당 |

### 조작 영역은 조작 담당 팀원의 내용을 따른다

조작(키 배정, 이동·점프·대시·벽타기, 조작 안내)은 조작 담당 팀원이 작업한다(사용자 지시 2026-10-30). 다른 브랜치에서 이 영역을 고쳤더라도 병합하다 충돌하면 **조작 담당 팀원 쪽 내용을 남긴다**. 두 내용을 섞어 새로 쓰거나, 다른 쪽이 더 최신이라는 이유로 바꾸지 않는다. 병합 방향에 따라 `ours`·`theirs`가 뒤바뀌므로, 옵션 이름이 아니라 실제 작성자로 판단한다.

| 대상 | 경로 |
|---|---|
| 키 배정·입력 | `unity/Assets/Deviant/Combat/Runtime/Unity/CombatKeyboardBindings.cs`, `CombatKeyboardInput.cs` |
| 이동·벽타기 동작과 수치 | `unity/Assets/Deviant/Combat/Runtime/Unity/CombatPlayer.WallMovement.cs`, `data/combat/locomotion/player.json` |
| 조작 안내 화면 | `unity/Assets/Deviant/Game/Runtime/TemporaryGameGui.Inventory.cs`의 왼쪽 아래 키 줄, `unity/Assets/ForestCombatV2/Runtime/Chapter1MovementGuide.cs`(첫 상하 길목 벽타기 안내) |
| 조작 명세 | [UI·상호작용](../design/ui/ui-and-interaction.md)의 조작 안내 항목과 「키보드 기본값」 절, [전투 규칙](../design/combat/rules.md)의 기본 키 문단 |

- 팀원 쪽을 남긴 뒤 이쪽 코드가 사라진 이름을 참조하면 참조만 맞춘다. 예를 들어 `Chapter1MovementGuide`가 없어지면 `TemporaryGameGui`의 `movementGuide`와 `TemporaryGuiVerification`의 벽타기 안내 검사, `Chapter1StartingGuideTests.ClimbHintAppearsOnceAtTheFirstVerticalConnector`를 함께 뺀다. 조작 내용을 이쪽 방식으로 되살리지 않는다.
- 같은 파일 안이라도 조작과 관계없는 부분은 평소대로 양쪽 변경을 합친다. 예를 들어 `TemporaryGameGui.Inventory.cs`의 체력·무기·가방 HUD는 이 규칙의 대상이 아니다.
- 시작방 출구 잠금(`Chapter1StartingBlueprints`의 도면 2개 전 출구 잠금)은 런 시작 규칙이므로 이 규칙의 대상이 아니다. 충돌하면 [런 구조](../design/run/run-structure.md)를 기준으로 판단하고, 판단 근거가 부족하면 사용자에게 묻는다.
- 해소한 뒤 조작 관련 테스트(`Chapter1WallTraversalTests`, `Chapter1StartingGuideTests`)와 GUI 검증을 다시 실행한다. 팀원 쪽 내용 때문에 실패하는 테스트는 팀원 쪽 동작에 맞게 고치거나 빼고, 그 이유를 병합 커밋 본문에 적는다.

## 문서 공통 양식

새 분야 문서는 목적·의도, 기준 원본, 확정 사항, 구상·미정, 현재 구현, 검증 기준·미검증 범위, 관련 자료 순으로 작성한다. 개요와 현황표는 상세 수치를 복사하지 않고 원본으로 연결한다. 생성 문서는 생성기의 소유이므로 수동 내용을 덧붙이지 않는다.

```markdown
# 기능 이름

## 목적과 원본
누구에게 어떤 경험을 주는지, 기준 명세·데이터 링크.

## 확정 사항
승인·위임 근거가 있는 현재 규칙과 예외.

## 구상·미정
아직 선택하지 않은 내용과 연결 기능에 미치는 영향.

## 현재 구현
적용된 코드·씬·패키지와 제품/시험 범위의 구분.

## 검증 기준과 제한
재현 조건·기대 동작, 실제 확인이 필요한 범위.

## 관련 자료
제작 원본·복원·구현·검증 절차 링크.
```

## 변경과 인계 순서

1. [분야별 현황](../overview/project-status.md)과 [미정·충돌](../overview/open-questions.md)을 읽고 작업 범위를 확인한다.
2. 기존 명세·사용자 지시·위임 근거를 확인한다. 충돌을 구현에 맞춰 자동 변경하지 않는다.
3. 승인된 규칙을 원본 명세·데이터에 반영하고 관련 생성물·구현·참조를 함께 갱신한다.
4. 변경한 범위에 맞는 검사·실행을 수행한다. 문서 링크 검사는 `python tools/check_docs.py`다.
5. 현황표·문서 입구에서 찾아갈 수 있게 연결한다. 새 기능을 전체 제품 완료로 표시하지 않는다.
6. 커밋 본문에 변경 이유·검증 환경/명령/범위/결과·미실행 항목을 남긴다. 다른 편집 의도는 분리한다.

인계할 때는 기준 커밋·관련 명세, 적용 씬·원본 데이터, 필요한 에셋 패키지·받는 경로, 재현 순서·기대 결과, 현재 제한·받는 사람이 할 일을 명시한다. 개인 PC의 경로만 적지 말고 저장소 상대 경로와 패키지명을 함께 쓴다. 별도 작업 일지·검증 보고서를 새 문서로 누적하지 않는다.
