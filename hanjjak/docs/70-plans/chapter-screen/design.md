## 목적

사용자가 제공한 챕터 화면 요구사항·목업과 Office Hours에서 확인한 설계 근거를 보존한다. 현재 정책은 [스테이지 SSOT](../../30-domain/world/ssot.md), [클라이언트 UX SSOT](../../30-domain/player/ux/ssot.md), [계정·저장 SSOT](../../30-domain/player/ssot.md), 저장·API 배치는 [데이터 권한과 저장 경계](../../50-architecture/persistence.md)와 [Networking](../../50-architecture/networking.md)이 소유한다.

## 문제 정의

챕터 화면의 핵심 가치는 수집 장식보다 현재 진행 위치를 빠르게 확인하고 해금된 챕터의 스테이지 목록으로 이동하는 것이다. MVP는 기존 범위인 챕터 1~4와 40스테이지를 유지한다.

별도 챕터 화면의 필요성은 아직 한짝 플레이테스트로 관찰하지 않았고 유사 게임의 관례를 근거로 한 가설이다. 현재 대체 내비게이션도 구현 전이므로 K-07 검증에서 실제 플레이어가 도움 없이 현재 위치와 이동 경로를 찾는지 확인해야 한다.

## 목업에서 관찰한 입력

- 양피지형 월드맵 위에 음식점 형태의 챕터 지점 4개가 배치된다.
- 각 카드에는 챕터 번호, 이름, 스테이지 범위와 진행 또는 잠금 상태가 있다.
- 챕터 1 카드는 강조 테두리와 진행률을, 챕터 2~4는 `잠김`을 표시한다.
- 안내 문구는 가게 선택 시 스테이지 목록이 열린다는 흐름을 제시한다.
- `← 전투` 버튼은 전투 화면 복귀를 암시하지만 정확한 목적지는 UX 정본에서 정의한다.

노란 테두리의 정확한 의미, 잠긴 카드의 반응, 스테이지 목록의 모달·별도 화면 여부는 목업만으로 확정하지 않고 Office Hours 결정과 UX SSOT를 따른다.

## Office Hours에서 비교한 접근

### 통합 화면 조회 API — 선택

정적 챕터 정보와 사용자별 해금·진행·현재 위치 표시를 한 조회 모델로 제공한다. 화면 조합 실패가 없고 MVP 챕터 수가 작아 가장 단순하다. 스테이지 목록 요청은 잠금 상태를 다시 검증한다.

### 정적·진행 조회 분리

정적 콘텐츠와 사용자 진행을 각각 조회해 클라이언트가 합친다. 캐시 경계는 명확하지만 두 요청의 부분 실패, 버전 불일치와 조합 로직이 화면에 생긴다.

### 화면 전용 View API

월드맵 전용 BFF 응답을 별도 계약으로 둔다. 여러 화면별 표현이 갈라질 때 유리하지만 현재 범위에서는 통합 챕터 조회와 중복된다.

## 확정한 방향

- MVP 챕터 수는 4개다.
- 전체 스테이지 클리어, 챕터 해금과 접근 검증은 서버가 최종 판정한다.
- 현재 전투 챕터와 최고 미완료 진행 목표 챕터는 서로 다른 상태로 취급한다.
- 챕터 진행률은 최초 클리어한 스테이지 수를 기준으로 계산하고 마지막 스테이지 최초 클리어 시 100%다.
- 완료 챕터는 완료 배지와 100%를 함께 표시한다.
- 잠긴 챕터 선택은 서버가 거부하고 화면은 필요한 이전 챕터 마지막 스테이지를 안내한다.
- 챕터 선택 자체는 진행 상태를 바꾸지 않으며, 해금된 챕터의 스테이지 목록으로 이동한다.
- MVP 4개 지점은 한 화면에 표시하며 페이지·스크롤 탐색은 요구하지 않는다.
- 화면 조회는 통합 챕터 목록 API를 사용하고 스테이지 목록 API가 접근 권한을 다시 검증한다.

## 남은 검증

- 한짝 플레이테스트에서 현재 전투 위치와 진행 목표를 도움 없이 구분하는가.
- 완료 배지, 현재 전투 강조와 진행 목표 강조가 같은 카드에 겹칠 때도 의미가 분명한가.
- 잠긴 카드를 선택했을 때 해금 조건 안내만으로 다음 행동을 이해하는가.
- 16:9·16:10과 최소 창 크기에서 네 챕터 카드와 상태 텍스트가 읽히는가.
- 서버 조회 실패·인증 만료·콘텐츠 버전 불일치 때 오래된 캐시를 권한 상태처럼 보여주지 않는가.
