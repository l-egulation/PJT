# player_id 기반 플레이 데이터 수집

[분야 개요](README.md)

## 구현 목표와 선택

계정/기기 지문 없이, 자동 전송 시작 시 만든 무작위 `player_id`를 로컬에 저장하고 다음 실행에도 재사용한다. 브라우저/프로필/저장 영역이 바뀌면 새 플레이어여도 허용한다. 웹과 바이너리의 자동 동일인 연결이나 로그인은 구현하지 않는다. 이 ID는 분석용 라벨이며 업로드 내용의 진실성이나 소유권을 증명하는 인증 자격이 아니다.

새 session/segment ID에는 생성 UTC ms를 담은 UUIDv7을 사용한다. 같은 프로세스에서는 생성 순서로 문자열 정렬할 수 있고, player ID는 기존 로컬 식별자를 유지한다. 이전 UUIDv4 기록은 바꾸지 않는다. 정확한 시계/순번 해석은 [로컬 기록 명세](replay-recording.md#시간순-구간-id)를 따른다.

한 실행의 session 아래 마을·여러 런·결과/귀환을 포함한 기존 리플레이 조각을 연결한다. 원본 파일에 개인 계정 정보를 추가하지 않고, 별도 session 수집 메타데이터에 player ID를 고정한다. 이후 ID가 달라져도 대기 중인 과거 파일을 새 ID로 바꾸지 않는다.

초기 서버는 Go 표준 HTTP API + SQLite(SQL 메타데이터/일부 사건) + 파일 디렉터리다. 한 API 프로세스와 Docker named volume으로 배포한다. 수평 확장/공유 파일시스템 운영은 범위 밖이며 필요한 시점에 PostgreSQL/객체 저장소로 옮긴다. 구체적인 API·현재 구현 범위·실행은 [서버 명세](replay-server-storage.md)와 [백엔드 안내](../../../backend/collector/README.md)를 따른다.

## 기능 단위 계획

1. Unity 공통 ID 생성/재사용과 세션별 player binding, 기본 활성화한 기록·자동 전송을 연결한다.
2. Go에서 세션 등록·압축 조각 업로드·중복/충돌·형식/해시 검증·서버 확정 응답을 구현한다.
3. SQLite에 player/session/segment/chunk와 주요 UI/플레이어 전투/상태 사건을 저장한다. 이동·커서의 모든 표본은 원본에만 두고 snapshot을 실제 사용자 행동으로 세지 않는다.
4. Unity coroutine에서 이전 세션까지 재시도한다. 성공한 committed 해시를 확인한 뒤 로컬 파일을 지우고, 종료 응답에 의존하지 않고 상태 메타데이터도 동기화한다.
5. 웹에서는 background Task 대신 지원되는 동기 기록 경로와 브라우저 FS 동기화를 사용한다. Player ID/업로드는 플랫폼 공통이며 실제 Web Player 검증은 고정 Editor의 Web 모듈에서 별도로 한다.
6. Go API/파일+DB 복구·중복·인증·한도·CORS·만료/삭제, Unity의 ID/대기 파일/응답 확인을 검증하고 Docker 사용 방법을 제공한다.

## 수집/운영 원칙

- 기록은 기본 켜짐이며 서버 주소가 있으면 자동으로 전송한다. 기록 중단·재개 설정 하나를 사용하고 별도 전송 동의는 두지 않는다. 이전에 명시적으로 중단한 기록 설정은 유지한다. 서버 주소가 없는 빌드는 로컬 기록만 가능하다.
- 기록이 켜지고 서버 주소가 있는 상태에서 확정한 새 조각만 전송하며, 예전에 로컬만 기록한 세션을 소급 업로드하지 않는다.
- 게임에 관리자 토큰을 넣지 않는다. 공개 수집 API는 입력 제한을 적용하고, 목록·다운로드·삭제는 서버 관리자만 할 수 있다.
- 종료 이벤트 누락은 사망·포기로 해석하지 않는다. raw 조각의 기록 완전성과 session의 종료 관측 여부를 분리한다.
- 저장소 원본은 사용자가 보낸 미검증 데이터다. 리워드·안티치트의 권위 있는 근거로 쓰지 않는다.
- 실제 개인정보·입력 문자열·영상·음성·IP 장기 분석 기록은 수집하지 않는다. 실제 파일/로그·테스트 실행 출력은 outputs에만 두고 Git/resources에 넣지 않는다.
- 초기 서버는 세션/원본/사건 모두 수집 시작 기준 30일 보관을 기본으로 한다. 이 운영값은 과거 문서의 미확정 90일 통계 보관 제안보다 우선한다. 서버를 꺼 둔 동안의 자동 파기를 보장하지 않으며 다음 실행/정리 시 적용한다.

## 구현 배치와 남은 수락

- `Replay/Runtime/ReplayCollection.cs`: ID 재사용·세션 binding·전송 endpoint 검증. 기존 코덱 header는 바꾸지 않는다.
- `Replay/Runtime/ReplayStore.cs`: 전송 대상인 새 조각에 binding 저장, 중단/확정 응답 때 binding 정리.
- `Replay/Unity/ReplayUploadClient.cs`: 파일/세션 상태 전송, 중복 재시도, 영구 오류 보존, committed 해시 확인.
- `Game/Runtime/ReplayRecordingHost.cs`: 자동 기록·전송과 중단/재개 UI·PlayerPrefs·플랫폼·세션 시작 UTC 연결. Web은 동기 commit과 `ReplayStorage.jslib`를 사용한다.
- `backend/collector/`: API·제한된 바이너리 검사·SQLite 사건 추출/조회·원본 파일·만료/삭제·Docker 배포 구성.

이 구성은 계정/삭제 자격·자동 숙련도 분석·모든 마을 업무 결과 계측·제품 씬 전체 Player/브라우저 수락을 포함하지 않는다. 실제 수행한 검증 결과는 커밋/실행 출력에서 확인하고 이 목록 자체를 검증 완료의 증거로 쓰지 않는다.
