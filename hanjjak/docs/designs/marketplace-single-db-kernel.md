## Problem Statement

한짝 MVP에 `조회 → 구매 → 판매 등록 → 내 매물 관리 → 거래내역` 흐름을 제공한다. 화려한 데모보다 정상 작동이 우선이다. 사용자가 본 가격과 서버 가격이 달라졌거나, 마지막 재고 구매와 판매 취소가 동시에 들어오거나, 같은 요청이 재전송되더라도 쌀·아이템·매물·정산·기록이 복제되거나 유실되지 않아야 한다.

이 문서는 2026-09-01 당시 제안의 보존 기록이다. 현재 거래 규칙은 [거래소·경제 SSOT](../30-domain/economy/ssot.md)가 소유한다. 특히 스택형 품목의 정확 단가 전량 구매 제안은 2026-09-09 확정된 사용자 지정 개당 상한과 부분 구매 규칙으로 대체되었다. 보석 지정 매물 계약과 아직 현재 SSOT로 전파되지 않은 제안은 별도 결정 전까지 현재 정책이 아니다.

## What Makes This Cool

정확성이 기능이다. 같은 가격의 여러 판매자 매물은 구매자에게 하나의 가격대로 단순하게 보이지만, 서버는 개별 매물을 최저가·등록순으로 체결한다. 마지막 물량을 두 명이 동시에 구매해도 한 명만 성공하고, 구매와 취소가 경쟁해도 아이템이 복제되지 않는다.

## Constraints

- 메이플식으로 판매 등록 건마다 별개의 매물을 유지한다.
- 구매 화면은 같은 아이템·같은 가격의 활성 매물 수량을 합쳐 표시할 수 있다.
- 서버 체결 우선순위는 낮은 가격, 같은 가격에서는 먼저 등록된 매물 순이다.
- 스택형 품목에 대한 구형 제안은 구매자가 현재 사용자 기준 최저가와 같은 `expectedUnitPrice`에 동의하고 가격이 달라지면 전체 실패하는 방식이었다. 현재는 사용자가 `maxUnitPrice`를 정하고 그 이하의 더 싼 매물부터 체결하는 [거래소·경제 SSOT](../30-domain/economy/ssot.md)를 따른다. 보석 지정 매물의 정확 단가 계약은 별도 범위다.
- 판매자는 시세와 무관하게 판매 단가를 자유롭게 정한다. 최소·최대 시세 제한은 두지 않으며 1쌀 이상의 정수를 1쌀 단위로 입력한다.
- 스택형 품목의 구형 전량 구매 제안은 폐기되었다. 현재는 시장 잔량·가격 상한·보유 쌀에 따라 한 개 이상 가능한 수량까지 부분 구매한다.
- 판매 등록 수량은 예약 재고로 이동하며 제작·강화·중복 판매에 사용할 수 없다. 스택형 아이템은 수량을 예약하고, 보석은 개별 `gemInstanceId`를 escrow 상태로 전환한다.
- 구매, 판매 정산 우편 생성, 10% 수수료, 매물 감소, 거래기록은 하나의 DB 트랜잭션으로 처리한다. 판매 대금은 기존 [계정·저장 SSOT](../30-domain/player/ssot.md)의 우편 첨부 정책을 유지해 즉시 쌀 잔액에 더하지 않는다.
- 자기 매물은 구매할 수 없다. 서버와 화면은 전체 시장 최저가와 현재 사용자가 실제 구매할 수 있는 최저가를 구분하며, 구매 동의 가격은 후자를 기준으로 한다.
- 모든 쓰기 요청은 사용자·동작 단위의 중복 요청 키를 받는다. 같은 키와 같은 요청 본문의 재시도는 같은 결과를 반환하고, 같은 키를 다른 본문에 재사용하면 실패한다.
- 최근 시세는 최근 완료된 사용자 체결 5건의 단가 중앙값이다. 상태는 `FRESH`, `INSUFFICIENT_SAMPLES`, `STALE`로 구분하고 화면에는 `최근 5건 중앙값`이라는 이름과 상태를 함께 표시한다.
- 장비는 거래하지 않는다. 최종 거래 가능 품목 목록은 [아이템 SSOT](../30-domain/items/ssot.md)와 [보석 SSOT](../30-domain/gems/ssot.md)의 거래 가능 속성을 참조하고 거래소 문서에 복제하지 않는다.

## Premises

1. 정상 작동의 최소 단위는 구매 API 하나가 아니라 조회·판매 등록·예약·체결·취소·정산·내역의 닫힌 흐름이다.
2. 클라이언트는 예상 금액과 입력 검증을 담당하지만 가격·재고·소유권·수수료의 최종 권한을 갖지 않는다.
3. Kafka나 별도 이벤트 서비스 없이 관계형 DB 트랜잭션과 잠금으로 MVP 정합성을 보장할 수 있다.
4. 같은 가격대의 UI 집계는 조회 표현일 뿐, 개별 매물과 체결 순서를 합치지 않는다.
5. 최신 첨부 요구사항을 기존 거래소 SSOT보다 우선하는 것은 이번 세션의 사용자 결정이며, 실제 정책 전환은 SSOT와 결정 로그 갱신으로 완료한다.

## Cross-Model Perspective

Codex는 “marketplace that works correctly, not a flashy demo”를 핵심 신호로 읽고 단일 DB 시장 커널을 먼저 만들 것을 권했다. PostgreSQL의 행 잠금과 직렬화 실패 재시도 같은 검증된 기능을 활용하고, 개별 매물 스키마·예약 재고·체결 루프·중복 요청 키·수수료 정산·경쟁 테스트를 프로젝트가 소유하는 구성을 제안했다.

Codex는 최근 5건 중앙값을 단순히 `최근 시세`로 표시하는 전제를 문제 삼았다. 저유동성에서는 오래되거나 왜곡된 거래가 공정 가격처럼 보일 수 있다. 사용자는 계산법을 유지하되 `최근 5건 중앙값`이라고 명시하고 데이터 부족·오래됨 상태를 표시하는 방향을 선택했다.

## Approaches Considered

- **선택: 단일 DB 시장 커널.** 가장 작은 구조로 전체 거래 계약과 경쟁 조건을 완성한다.
- **제외: 자산 원장 중심 구조.** 감사·복구에는 유리하지만 해커톤 MVP에서 이벤트·복구 규칙이 거래 완성보다 앞선다.
- **제외: 거래 영수증·경쟁 재현형.** 정확성을 시각화하지만 사용자는 데모 연출보다 정상 작동을 우선했다.

## Recommended Approach

### 데이터 책임

- `market_item_lock`: 아이템 종류별 단일 잠금 행. 판매 등록·구매·취소는 도메인 행보다 먼저 이 행을 잠가 더 싼 매물 삽입과 체결 선택의 경쟁을 직렬화한다.
- `market_listing`: 판매자, 자산 유형(`STACKABLE`·`GEM_INSTANCE`), 아이템 종류, 보석 인스턴스 ID, 등록 단가, 최초 수량, 남은 수량, 상태, 등록 순서. 보석 매물은 수량 1이며 레벨·옵션·콘텐츠 버전 스냅샷을 함께 고정한다.
- `inventory_balance`: 스택형 아이템의 총수량과 예약수량 또는 사용 가능 수량을 원자적으로 검증하는 사용자·아이템 잔액.
- `gem_instance`: 소유자와 `AVAILABLE`·`EQUIPPED`·`ESCROW` 상태를 가진 개별 보석. 등록 시 특정 인스턴스를 `ESCROW`로 바꾸고 체결 시 그 인스턴스의 소유자를 이전하며 취소 시 판매자에게 `AVAILABLE`로 복원한다.
- `market_purchase`: 구매 요청 단위의 불변 그룹. 구매자, 아이템, 동의 단가, 요청 수량, 체결 총액과 완료 시각을 저장한다.
- `market_fill`: 개별 매물별 체결 행. `purchaseId`, `listingId`, 체결 순번, 구매자·판매자, 단가, 수량, 총액과 시각을 저장해 매물 귀속을 보존한다.
- `market_seller_settlement`: 구매·판매자 조합별 집계. 해당 판매자의 fill 총액, 한 번 반올림한 수수료, 실수령액을 저장한다.
- `market_settlement_mail`: `sellerSettlementId`와 일대일이며 실수령액을 첨부한 우편. 체결과 같은 트랜잭션에서 만들며 수령 명령은 기존 우편 중복 지급 방지를 따른다.
- `market_command`: `(userId, action, idempotencyKey)` 고유키, 정규화한 요청 해시, `SUCCEEDED`·`FAILED` 상태와 확정 응답을 저장한다. domain 변경과 같은 트랜잭션에서 삽입하므로 별도의 가시적 진행 상태를 만들지 않는다.
- 쌀 잔액은 서버 권한 자산으로 관리하며 음수 변경을 DB 제약과 조건부 갱신으로 거부한다.

활성 매물 상태는 `ACTIVE`와 종료 상태 `FILLED`, `CANCELLED`로 충분하다. 부분 판매는 상태를 늘리지 않고 `ACTIVE + remainingQuantity < initialQuantity`로 표현한다. 모든 수량과 가격은 정수이며 0보다 커야 한다. 보석 매물의 레벨·옵션은 조회용 스냅샷이며 체결할 때 잠근 `gem_instance`의 값과 일치하지 않으면 거래 전체를 실패시킨다.

### 조회

1. 거래 아이템 목록은 전체 시장 최저가·수량과 현재 사용자 기준 최저 구매 가능 단가·수량을 분리하고, 최근 5건 중앙값 상태를 반환한다.
2. 상세 조회는 현재 사용자 기준 최저 구매 가능 가격대, 내 보유·판매 가능 수량, 보석이면 개별 레벨·옵션을 반환한다.
3. 자기 매물을 제외한 첫 번째 가격대를 현재 사용자 기준 최저 구매 가능 가격대로 선택한다. 자기 매물만 있으면 `SELF_ONLY`, 타인 매물도 없으면 `NO_LISTING`으로 구분한다.
4. 내 매물은 최초수량·남은수량·상태·등록가와 보석 인스턴스 속성을 페이지 조회한다.
5. 거래내역은 `market_purchase`를 먼저 페이지 조회하고 그 페이지의 `market_fill`을 체결 순번으로 붙인다. 판매 필터는 `market_seller_settlement`를 페이지 조회하고 하위 fill을 제공한다.

### 판매 등록

1. `itemId`, 스택형이면 `quantity`, 보석이면 `gemInstanceId`, `unitPrice`, `idempotencyKey`를 받는다.
2. 인증·요청 형식·양의 정수 검증 후 `(userId, LISTING_CREATE, idempotencyKey)` command 삽입을 시도한다. 같은 키가 커밋될 때까지 대기한 중복 요청은 요청 해시가 같으면 확정 응답을 재생하고, 다르면 `IDEMPOTENCY_KEY_REUSED`로 실패한다. 고유키 대기 한도를 넘으면 `MARKET_BUSY_RETRY`를 반환한다.
3. 거래 가능 속성과 `unitPrice >= 1`인 정수 여부를 검증한다. 시세 대비 최소·최대 가격 제한은 적용하지 않는다.
4. `market_item_lock`과 자산 행을 순서대로 잠근다. 스택형은 사용 가능 수량을 확인해 예약으로 이동하고, 보석은 소유자·미장착·`AVAILABLE` 상태를 확인해 특정 인스턴스를 `ESCROW`로 바꾼다.
5. command, 매물, 자산 변화를 같은 트랜잭션에서 커밋한다. 결정적 도메인 실패는 `FAILED` 응답을 command에 저장한다. 연결 오류처럼 결과가 불명확하면 먼저 같은 키를 조회해 확정 응답을 재생하고, 행이 없을 때만 재실행한다.

### 구매

1. 스택형 구매는 `itemId`, `quantity`, `expectedUnitPrice`, `idempotencyKey`를 받는다. 보석 구매는 `listingId`, `gemInstanceId`, 화면이 본 `gemSnapshotVersion`, `expectedUnitPrice`, `idempotencyKey`를 받고 수량은 1로 고정한다.
2. 인증·요청 형식 검증 후 `(userId, PURCHASE, idempotencyKey)` command를 판매 등록과 같은 대기 후 재생 규칙으로 처리한다.
3. 스택형은 `market_item_lock`, 구매자 쌀, 동의 가격의 타인 활성 매물 전체를 순서대로 잠근다. 보석은 `market_item_lock`, 구매자 쌀, 지정 매물, 지정 인스턴스를 잠근다.
4. 스택형에서 사용자 기준 최저 구매 가능 단가가 없으면 타인 매물 없음은 `MARKET_EMPTY`, 자기 매물만 있음은 `SELF_PURCHASE_NOT_ALLOWED`로 실패한다. 보석은 지정 매물이 자기 것이면 `SELF_PURCHASE_NOT_ALLOWED`로 실패한다.
5. 스택형 최저 구매 가능 단가 또는 지정 보석 매물 단가가 `expectedUnitPrice`와 다르면 `MARKET_PRICE_CHANGED`와 최신 정보를 반환한다.
6. 스택형 동의 가격 수량이 부족하면 `MARKET_QUANTITY_CHANGED`를 반환한다. 보석의 매물·인스턴스·스냅샷 버전이 사라지거나 달라졌으면 대체 보석을 고르지 않고 `GEM_LISTING_CHANGED`와 최신 상세를 반환한다.
7. 구매자 쌀이 총 구매금액보다 적으면 `INSUFFICIENT_RICE`로 실패한다.
8. 스택형은 등록 순서대로 매물과 예약수량을 줄이고 구매자 수량을 늘린다. 보석은 지정 매물을 `FILLED`로 종료하고 지정 인스턴스의 소유권을 구매자로 옮긴다.
9. 구매자 쌀 감소, 판매자별 fill 총액, 판매자별 한 번 계산한 10% 수수료와 실수령액, 정산 우편, 구매 그룹, fill, 매물 변화와 command 응답을 기록하고 전체가 성공할 때만 커밋한다.
10. 잠금 대기 초과나 교착·직렬화 실패는 최대 3회 재시도하고, 소진 시 자산 변화 없이 `MARKET_BUSY_RETRY`를 반환한다.

수수료는 `market_seller_settlement`의 판매자별 fill 총액에 한 번 적용한다. 확정 규칙은 해당 총액의 10%를 계산하고 소수점을 내림하는 것이다. 각 fill에는 수수료를 배분하지 않으며, settlement와 우편에 총액·수수료·실수령액을 저장해 `fill 총액 합 = settlement 총액`, `총액 - 수수료 = 우편 첨부액`을 보장한다.

### 판매 취소

1. `listingId`, `idempotencyKey`를 받는다.
2. 인증·요청 형식 검증 후 `(userId, LISTING_CANCEL, idempotencyKey)` command를 같은 대기 후 재생 규칙으로 처리하고 `market_item_lock`, 매물, 예약 자산 순으로 잠근다.
3. 해당 매물의 소유자와 `ACTIVE` 상태를 확인한다.
4. 스택형은 남은 수량을 예약에서 사용 가능 수량으로 반환한다. 보석은 인스턴스를 판매자 소유 `AVAILABLE`로 복원한다. 매물은 `CANCELLED`로 바꾼다.
5. 구매가 먼저 잠금을 얻어 전량 체결했다면 `LISTING_ALREADY_FILLED`, 취소가 먼저 커밋됐다면 구매는 최신 타인 매물 기준으로 실패한다.
6. command, 종료 상태와 반환 수량을 같은 트랜잭션에 저장한다.

### API 계약

| 기능 | API | 주요 요청 | 주요 성공 응답 |
| --- | --- | --- | --- |
| 거래 아이템 목록 | `GET /api/v1/market/items` | 검색·분류·등급·정렬·페이지 | 아이템, 최저가, 구매 가능 수량, 최근 5건 중앙값 상태 |
| 거래 상세 | `GET /api/v1/market/items/{itemId}` | `itemId` | 최저가, 구매 가능 수량, 최근 시세, 내 보유·판매 가능 수량 |
| 스택형 구매 | `POST /api/v1/market/items/{itemId}/purchase` | `quantity`, `expectedUnitPrice`, `idempotencyKey` | 구매 그룹, fill, 남은 쌀, 획득 수량, 다음 최저가·수량 |
| 보석 구매 | `POST /api/v1/market/listings/{listingId}/purchase` | `gemInstanceId`, `gemSnapshotVersion`, `expectedUnitPrice`, `idempotencyKey` | 지정 보석 속성, 정산 결과, 남은 쌀 |
| 판매 등록 | `POST /api/v1/market/listings` | 스택형은 `itemId`, `quantity`; 보석은 `itemId`, `gemInstanceId`; 공통 `unitPrice`, `idempotencyKey` | 매물, 예약 후 판매 가능 자산 |
| 내 매물 | `GET /api/v1/market/listings/me` | 상태·페이지 | 최초수량, 남은수량, 가격, 상태 |
| 판매 취소 | `POST /api/v1/market/listings/{listingId}/cancel` | `idempotencyKey` | 반환 수량, 종료 상태 |
| 내 거래내역 | `GET /api/v1/market/trades/me` | 구매/판매 구분·페이지 | 요청 합계, 체결 상세, 수수료, 거래시각 |

실패 응답은 안정적인 코드와 최신 화면 복구 데이터를 함께 반환한다. 판정 순서는 인증·요청 형식 오류 → command 키 충돌·대기 초과 → 거래 가능 여부 → 사용자 기준 타인 매물 존재 여부 → 정확 단가 변경 → 수량·보석 스냅샷 변경 → 쌀 부족 → 자산 상태 충돌이다. 최소 코드는 `MARKET_EMPTY`, `MARKET_PRICE_CHANGED`, `MARKET_QUANTITY_CHANGED`, `GEM_LISTING_CHANGED`, `INSUFFICIENT_RICE`, `SELF_PURCHASE_NOT_ALLOWED`, `ITEM_NOT_TRADEABLE`, `INSUFFICIENT_SELLABLE_QUANTITY`, `LISTING_NOT_FOUND`, `LISTING_ALREADY_FILLED`, `LISTING_ALREADY_CANCELLED`, `INVALID_PRICE`, `INVALID_QUANTITY`, `IDEMPOTENCY_KEY_REUSED`, `MARKET_BUSY_RETRY`다. 시장 관련 실패는 사용자 기준 최신 구매 가능 정보와 시장 상태를 반환한다.

### 화면 계약

첨부 시안의 구매·판매·거래 내역 탭, 품목·세부분류·등급 필터, 검색, 낮은 가격순·최근 등록순, 선택 아이템 상세, 수량 조절, 보유 쌀, 총 주문 금액을 유지한다.

- 구매 버튼 직전까지 예상 총액을 표시하되 서버 응답을 확정 결과로 사용한다.
- 가격 또는 수량 변경 실패 시 메시지와 함께 서버가 반환한 최신 가격대·수량으로 화면을 갱신한다. 자동으로 더 비싼 가격에 체결하지 않는다.
- 처리 중 같은 버튼을 비활성화하되 네트워크 재전송 안전성은 중복 요청 키가 보장한다.
- 판매 예상 실수령액은 판매자별 체결 총액의 10%를 내림하는 서버 규칙과 동일하게 표시한다.
- 최근 시세 응답은 `status`, `medianUnitPrice`, `sampleCount`, `lastTradedAt`, `freshnessCutoff`을 제공한다. 완료 시각 내림차순, 같은 시각이면 `marketFillId` 내림차순으로 최근 5개 fill 단가를 고른다. `INSUFFICIENT_SAMPLES`는 0~4건이며 0건이면 중앙값은 `null`이다. 홀수 표본은 정렬한 가운데 값, 2건·4건은 가운데 두 값 산술평균의 소수점 이하를 내림한 정수 쌀로 계산한다. `FRESH`는 5건이고 마지막 체결이 신선도 기준 이내, `STALE`은 5건이지만 마지막 체결이 기준 밖인 상태다. 표본이 있으면 중앙값을 참고값으로 표시하되 상태 라벨을 숨기지 않는다.

## Success Criteria

- 판매 등록 시 예약수량만 증가하고 총자산은 변하지 않으며, 예약 아이템은 제작·강화·재판매할 수 없다.
- 한 가격대의 여러 매물이 등록순으로 체결되고 가격대 합계와 개별 잔여량이 일치한다.
- 요청 수량을 동의 가격에서 전부 확보하지 못하면 자산 변화 없이 실패한다.
- 마지막 10개에 대한 동시 전량 구매에서 정확히 한 요청만 성공하고 잔여량은 0이다.
- 구매와 취소 동시 요청에서 커밋 순서에 따라 한쪽만 자산을 가져가며 복제·음수·유실이 없다.
- 같은 중복 요청 키를 동시에 전송해도 한 번만 자산과 기록이 변하고, 응답 유실 후 재시도는 확정 응답을 재생한다.
- 구매 성공 직후 구매자 쌀·아이템, 미수령 정산 우편, 예약수량, 매물, 수수료, fill의 합계가 일치한다. 우편 수령은 첨부액을 판매자 쌀로 정확히 한 번만 이전한다.
- 자기 매물, 쌀 부족, 판매 가능 수량 초과, 가격 변경, 보석 스냅샷 변경, 존재하지 않거나 종료된 매물에서 안정적인 실패 코드와 복구 데이터를 반환한다.
- 최근 5개 fill 중앙값, 0~4건 표본 부족, 오래된 시세 상태가 실제 기록과 일치한다.
