# J-07 거래 동시성·부하 테스트

> 작업 상태와 완료 증거의 SSOT. 도메인 규칙은 [데이터·이벤트 및 배포·운영](../../../../40-systems/event-system/ssot.md)를 따른다.

## 완료 기준

단일 hot instrument에 동시 주문 등록·IOC·수정·취소 100건을 실행해 오류·timeout 0, p95 3초 이하, maker 가격·엄격한 가격/시간 우선순위와 주문·지갑·인벤토리·delivery·정산 불변 조건을 모두 확인한다.

## 선행 작업

I-05, J-02

## 비고

첫 기준선, 동시성 1·5·10·20·50·100 반복 5회 시리즈, 매물/판매자 분산 비교, `FOR UPDATE SKIP LOCKED` 후보 비교, 구매 후보 lock limit 비교, 구매 수량별 후보 lock limit 비교, 구매 수량 기반 동적 후보 lock limit 비교, tiered 후보 limit 비교, simple slack 후보 limit 비교, bucketed 후보 limit 비교, 후보 3개 finalist 재비교, q100 후보 limit tie-break, account state_version 배치 최적화, 정산 메일 배치 insert, market_trade batch insert, 구매자 지갑 차감 배치 최적화, 매물 잔량 batch update, 인벤토리 이동 batch, wallet_ledger batch insert, 거래 완료 outbox batch insert, market_revision lock/query 계측, 동시성 단계 상승 한계 테스트를 단일 로컬 PostgreSQL과 실제 HTTP API에서 측정했다. 전체 완료에는 목표 부하 오류율 기준 합의와 운영급 장시간 계측이 남아 있다.

2026-09-11 후속 Office Hours에서 새 주문장의 최초 인수 부하를 hot instrument 동시 100건·p95 3초 이하로 확정했다. `SKIP LOCKED`를 사용한 기존 측정은 구현 후보 비교와 자산 정합성 증거로만 보존하고 새 품목 row 직렬화 기준을 다시 측정한다.
2026-09-11 새 주문장 benchmark는 legacy listing·purchase 호출과 조회 SQL을 UUID 시장 품목·SELL GTC·BUY IOC·`market_order`/maker·taker 체결 기준으로 이관했다. 그러나 확정 기준인 hot instrument 동시 100건을 새 품목 row 직렬화 구현에서 재실행하지 못했다. 현 머신에 Docker runtime과 PostgreSQL client가 없어 이번 변경의 검증 상태는 계속 부분 검증이다.

- 반복 실행: `./gradlew.bat :apps:market-benchmark:run --args="--db-url jdbc:postgresql://localhost:5432/hanjjak_combat_mvp_qa --db-user hanjjak --db-password local-only --api-base-url http://127.0.0.1:8080 --item-id CORN_M4 --sellers 1 --buyers 100 --listings-per-seller 1 --listing-quantity 400 --unit-price 1 --purchase-quantity 1 --series-concurrency 1,5,10,20,50,100 --repetitions 5 --total-requests 200 --timeout-seconds 180 --output-dir portfolio/evidence/marketplace/market-baseline-series-20260903"`
- 반복 결과 중앙값: 동시성 1 p95 62ms·19.104 req/s, 5 p95 171ms·34.435 req/s, 10 p95 334ms·33.715 req/s, 20 p95 713ms·33.317 req/s, 50 p95 2148ms·33.389 req/s, 100 p95 3368ms·32.103 req/s.
- 병목 후보: 동시성 증가에도 처리량은 5 이후 거의 포화되고 p95/p99가 증가했다. `pg_stat_activity` 샘플에서 `Lock:tuple` 중앙값은 5부터 435, 10부터 1371 이상으로 증가했다.
- 분산 비교: 동시성 20에서 매물/판매자를 1·10·100으로 늘렸지만 p95는 570ms·555ms·579ms, `Lock:tuple`은 1118·1119·1165로 큰 개선이 없었다.
- SKIP LOCKED 비교: `market.purchase.skip-locked=true`로 구매 후보 조회에 `FOR UPDATE SKIP LOCKED`를 적용했을 때 p95는 1매물 570→530ms, 10매물 555→526ms, 100매물 579→537ms로 5~7% 감소했다. 처리량과 `Lock:tuple` 감소폭은 작아 근본 해결로 채택하지 않고 후보로 보존한다.
- 후보 limit 비교: `market.purchase.candidate-limit`을 1000·100·10·1로 바꾸면 p95는 530ms·504ms·594ms·456ms, 처리량은 44.543·47.315·41.314·52.882 req/s였다. 요청당 1개 구매 조건에서는 limit 1이 가장 좋았지만 큰 수량 구매 tradeoff가 있어 동적 limit 후보로 보존한다.
- 구매 수량별 후보 limit 비교: thin(매물당 1개) q5에서 limit 1은 충족률 0.200, limit 5 이상은 1.000이었다. thin q20에서 limit 1은 충족률 0.050, limit 5는 0.250, limit 20 이상은 1.000이었다. thick(매물당 20개) q20은 limit 1도 충족률 1.000이었다. 고정 limit 1은 얇은 매물의 여러 개 구매에서 요청 수량을 채우지 못하므로 구매 수량 기반 동적 limit 후보로 보존한다.
- 동적 후보 limit 비교: `min(1000, purchaseQuantity × factor)` 방식으로 factor 1·2를 비교했다. factor 1은 thin q5와 q20 모두 충족률 1.000을 달성했고, factor 2는 충족률을 더 올리지 못하면서 p95와 `Lock:tuple`을 대체로 증가시켰다. 구현은 `market.purchase.dynamic-candidate-limit=false` 기본값으로 보존해 기본 동작은 기존 static 1000을 유지한다.
- tiered 후보 limit 비교: `10개 미만 +1`, `100개 미만 +10`, `100개 이상 +20`, 최대 1000 전략을 static 1000·구매수량·구매수량×2와 비교했다. 모든 조건 충족률은 1.000이었다. q1은 tiered p95 654ms, x1 659ms, static 909ms였고, q5는 x2 1295ms, tiered 1343ms, x1 1460ms였다. q20은 x2 4170ms, tiered 4297ms, x1 4316ms로 근접했으며, q100은 tiered 7890ms가 static 8398ms, x1 9245ms, x2 9074ms보다 낮았다.
- simple slack 후보 limit 비교: `10개 미만 +1`, 그 외 `+10`, 최대 1000 전략을 측정했다. 모든 조건 충족률은 1.000이고 실패는 0이었다. 다만 q1 p95 785ms, q5 2492ms, q20 7858ms, q100 11942ms로 직전 tiered(+20) 실험보다 지연시간과 `Lock:tuple`이 전반적으로 높아 기본값 후보로 올리기엔 이르다.
- bucketed 후보 limit 비교: `10개 이하 +1`, `100개 이하 +10`, 그 외 `+100`, 최대 1000 전략을 `market.purchase.bucketed-candidate-limit=true`로 측정했다. 모든 조건 충족률은 1.000이고 실패는 0이었다. 5회 반복 중앙값 기준 q1 p95 469ms, q5 1283ms, q20 4277ms, q100 8726ms였다. q100 이하에서는 simple slack과 계산 limit이 같으므로 이전 simple slack 대비 개선은 공식 차이가 아니라 반복 수와 실행 편차 보정으로 본다. q200은 `+100` 구간 확인용으로 limit 300, p95 7343ms, 충족률 1.000이었다.
- finalist 재비교: 같은 빌드·같은 서버(`8090`, `skip-locked` 기본값 false, cap 1000)에서 `linear-x1`(구매수량), `tiered-plus`(`10 미만 +1`·`100 미만 +10`·`100 이상 +20`), `bucketed`(`10 이하 +1`·`100 이하 +10`·그 외 `+100`)를 thin q1/q5/q20/q100과 thick q20에서 각 5회 반복해 총 75회 실행했다. 세 정책 15개 조건 모두 충족률 1.000, 실패 0, 정합성 통과였다. 5회 중앙값 q100 p95는 bucketed 7364ms, linear-x1 8355ms, tiered-plus 8533ms였고 q100 `Lock:tuple`은 969·1115·1098이었다. thin q20은 linear-x1 3983ms, tiered-plus 4122ms, bucketed 5074ms로 순위가 뒤집혔다. `tiered-plus`와 `bucketed`는 q100을 뺀 모든 조건에서 계산 limit이 같은데도 p95가 최대 23.1%, `Lock:tuple`이 최대 28.8% 차이 났다. 실행 편차가 정책 간 격차(q100 11.9~13.5%)보다 커서 성능 1순위를 확정하지 않고, 기본값은 static 1000을 유지한다. `market.purchase.tiered-plus-candidate-limit` 플래그를 이번 비교용으로 추가했고 기본값은 false다.
- q100 후보 limit tie-break: finalist 재비교에서 q100 순위를 확정하지 못해 `linear-x1`(limit 100)과 `bucketed`(limit 110) 둘만 thin q100에서 각 20회 교차 실행했다. 두 정책 서버를 8090·8091에 동시에 띄우고 홀수 라운드는 linear-x1 먼저, 짝수 라운드는 bucketed 먼저 실행해 순서 효과를 상쇄했다. 두 정책 모두 충족률 1.000(최소값도 1.000), 실패 0, 정합성 통과였다. p95 중앙값은 linear-x1 7134ms, bucketed 7269ms로 차이 1.9%였고 `Lock:tuple` 중앙값은 1012과 1036이었다. 라운드별 승패는 10대 10 동률이고, 라운드별 p95 차이의 평균은 +42ms로 그 표준편차 226ms보다 작았다. 한 정책 안의 p95 변동폭이 최대 36.1%라 이 격차는 실행 편차와 구분되지 않는다. 직전 finalist 실험의 q100 12% 격차는 재현되지 않았고 순서 효과였을 가능성이 높다. 성능으로는 확정하지 않으며, 동률 조건에서 계산식이 단순하고 후보를 10개 적게 잠그는 `linear-x1`을 후보로 둔다. 기본 동작은 static 1000을 유지한다.
- 기본값 전환: 구매 후보 lock limit 기본 동작을 고정 1000에서 `linear-x1`로 바꿨다. 기본 계산은 `min(market.purchase.candidate-limit, purchaseQuantity)`이고 상한 기본값은 기존과 같은 1000이다. 근거는 이 문서의 후보 limit 비교, 구매 수량별 비교, finalist 재비교, q100 tie-break다. 실험 플래그는 제거하지 않고 모두 기본값 false로 유지했으며, 예전 고정 limit 동작은 `market.purchase.static-candidate-limit=true`로 재현할 수 있게 플래그를 추가했다. 단위 테스트로 q1→1, q10→10, q100→100, q2000→상한 1000과 static 플래그 회귀를 고정했다.
- 기본값 전환 스모크: 플래그를 하나도 지정하지 않은 서버에서 thin 매물(판매자 10명, 매물당 1개) 구매 q3과 q7을 실행해 `market_trade` 생성, 구매자 인벤 증가, 구매자 쌀 감소, 매물 잔량 감소, 판매자 예약 수량 감소, 음수 인벤/지갑 부재를 확인했다. 두 실행 모두 충족률 1.000, 실패 0, 불변 조건 전부 통과였다. PostgreSQL 문장 로그로 후보 조회 쿼리의 바인드 파라미터를 직접 확인해 q3은 `limit 3`, q7은 `limit 7`로 나가는 것을 검증했다. 로깅 설정은 확인 후 원복했다. 증거는 `portfolio/evidence/marketplace/market-linear-default-smoke-20260905/`에 보존했다.
- market_revision lock 실험: 구매 트랜잭션은 `expireActiveForItem`과 `purchase`에서 item당 행이 하나인 `market_revision`을 각각 `for update`로 선점한다. 동시성 20 부하 중 `pg_locks`를 샘플링한 결과 326개 샘플에서 못 얻은 relation 락이 전부 `market_revision`이었고 `market_listing`은 0건이라, 이 행이 병목임을 확인했다. `market.purchase.skip-revision-lock=true`로 두 선점을 모두 생략해 비교했더니 같은 item 동시성 5에서 p95가 3059ms에서 10164ms로 3.3배 악화됐고, 동시성 20에서는 3라운드 모두 benchmark의 30초 HTTP 타임아웃을 넘겨 완주하지 못했다. 서로 다른 item 4개를 병렬로 돌린 조건에서는 p95 6694ms 대 6772ms로 차이가 없었다. 완주한 실행의 충족률은 1.000, 실패 0, 정합성 불변 조건과 revision 증가는 모두 통과했다. 선점이 입구에서 요청을 줄 세우는 역할을 하고 있어 단순 제거는 기각하고 기본값은 기존 동작을 유지한다. 다음 방향은 락 보유 시간 축소다.
