## Problem Statement
사용자가 게임을 종료한 동안 현재 스테이지를 자동전투한 결과의 절반을 쌀·주력 재료·경험치로 돌려받는 복귀 경험을 만든다. 서버 UTC 경과시간을 1분 단위로 계산하며 최대 480분까지 적용한다.

## What Makes This Cool
다시 접속하면 실제로 자리를 비운 시간과 보상이 적용된 시간을 함께 보여주고 바로 보상을 받는다.

- 서버가 시간과 보상의 최종 권한을 가진다.
- 1분 미만은 보상하지 않고 1분 단위로 내림하며 최대 8시간만 인정한다.
- 보상은 복귀 시점 현재 스테이지의 1분 평균 보상률 중 50%를 사용한다.
- 같은 탭의 새로고침과 1분 미만 재접속은 기존 게임 세션을 재개하고 오프라인 작업을 고정하지 않는다.
- 주력 재료·쌀·경험치만 대상이며 스테이지 해금·랭킹·거래 자산은 제외한다.

## Premises
- `offlineSeconds = max(accrualEndedAt - lastHeartbeatAt, 0)`이고 `eligibleSeconds = min(floor(offlineSeconds / 60) × 60, 28,800)`이다. 두 시각은 서버 UTC를 사용한다.
- `eligibleSeconds`가 0이면 작업은 `CANCELLED`로 종료되고 보상 팝업을 만들지 않는다.
- `lastHeartbeatAt`은 정상 heartbeat 또는 명시적 로그아웃 서버 시각이다. `accrualEndedAt`은 첫 재로그인·만료된 세션 대체 시각으로 transaction 안에서 고정한다.
- 보상 결과를 고정할 때 현재 스테이지와 현재 콘텐츠·전투 능력치·주력 재료로 1분 기대 보상률을 계산하고 50%를 적용한다.
- 같은 탭의 새로고침은 저장한 게임 세션을 heartbeat로 재개한다. 저장값을 잃었더라도 서버는 1분 미만의 기존 활성 세션을 반환한다.
- 계정당 `ACTIVE` 또는 `CLAIMABLE` 오프라인 작업은 하나만 허용한다. 기존 작업은 claim 전까지 새 작업을 시작할 수 없다.

## State and Settlement

```text
ACTIVE --heartbeat timeout / reconnect freeze--> CLAIMABLE
ACTIVE --explicit cancel-----------------------> CANCELLED
CLAIMABLE --claim------------------------------> CLAIMED
CLAIMABLE --explicit cancel--------------------> CANCELLED
```

`CLAIMABLE`은 보상 계산이 끝나고 결과가 고정된 상태다. MVP에서는 claim 만료를 두지 않으며, 8시간은 accrual cap이지 claim TTL이 아니다. `EXPIRED`는 후속 정책으로 남긴다.

모든 mutation은 공통 UUIDv4 idempotency key와 fingerprint/result command 기록을 사용한다. claim transaction은 command record, offline job, account stateVersion, wallet ledger, progression, inventory, 필요한 Outbox 이벤트를 함께 확정한다. 아이템 capacity 부족은 transaction 실패가 아니라 성공 상태이며, 지급 요청량·지급량·skippedQuantity를 result에 기록하고 XP·쌀 지급은 계속한다.

## Reward Rate Contract

MVP 평균 보상률은 versioned content의 stage별 정수/rational vector다.

```text
rewardRate(stageId, contentVersion) = {
  xpPerMinute,
  ricePerMinute,
  itemDrops: [{ itemId, quantityPerMinute }]
}
```

서버는 현재 스테이지의 1분 보상률을 계산하고 `floor(rate × 0.5 × eligibleSeconds / 60)`로 자원별 최종 정수 지급량을 만든다. 주력 재료는 현재 선택된 전문의 허용 드롭 규칙과 기존 세대 가중치를 따른다. 오프라인 정산은 kill·stage clear·unlock 이벤트를 만들지 않는다.

## Recommended Approach
서버 작업 상태 + 평균 보상률.

1. 온라인 게임 세션은 기존 `game_session`과 heartbeat 규칙을 유지한다.
2. 웹은 탭 단위 게임 세션 식별자를 저장하고 새로고침 시 heartbeat로 재개한다.
3. 서버는 오프라인 작업을 별도 `offline_job` 논리 모델로 관리한다.
4. 첫 재로그인에서 실제 경과시간, 적용시간, 현재 스테이지와 50% 보상 결과를 고정한다.
5. 1분 미만 작업은 취소하고, 그 이상은 쌀·재료·경험치 보상과 작업 상태 변경을 하나의 transaction으로 확정한다.
6. 웹은 서버 결과의 실제 경과시간과 보상 적용시간을 함께 표시한다.
7. 웹은 점진 배포 중 `offlineSeconds`가 없는 구형 응답을 받을 수 있으며, 이때 `eligibleSeconds`를 실제 경과시간 표시값으로 사용한다.

### Logical model

```text
offline_job
- job_id
- account_id
- game_session_id
- stage_id
- content_version
- reward_rate_snapshot_json
- combat_snapshot_json
- started_at
- last_heartbeat_at
- accrual_ended_at
- status: ACTIVE | CLAIMABLE | CLAIMED | CANCELLED
- result_json
- claimed_at
- created_at
- updated_at
- version
```

### API

```text
GET  /api/v1/offline-rewards/pending
POST /api/v1/offline-rewards/claim
```

`claim`은 UUIDv4 idempotency key를 받고, PostgreSQL partial unique index로 계정당 `ACTIVE`·`CLAIMABLE` 작업 하나를 보장한다. 동시 start, reconnect vs heartbeat, 서로 다른 claim key 경쟁은 account row → offline_job row 순서로 잠근다.

## Resolved Decisions
- 브라우저 종료·장기 네트워크 단절·로그아웃은 heartbeat를 중단하고 첫 재로그인 시 서버 타임스탬프로 결과를 고정한다.
- 같은 탭의 새로고침과 1분 미만 재접속은 기존 게임 세션을 재개하며 오프라인 보상을 만들지 않는다.
- 1분 단위 내림·480분 상한을 적용한다.
- 보상률은 복귀 시점 현재 스테이지의 1분 자동전투 기대 쌀·경험치·주력 재료의 50%다.
- `ACTIVE → CLAIMABLE → CLAIMED`와 1분 미만 `ACTIVE → CANCELLED`를 제공한다.

## Success Criteria
- 정상 heartbeat와 같은 탭 새로고침에서는 오프라인 보상이 생성되지 않는다.
- 실제 오프라인 59초는 보상 없음, 60초는 1분, 119초는 1분, 480분 이상은 480분을 적용한다.
- UI는 실제 오프라인 경과시간과 보상 적용시간을 함께 표시한다.
- 현재 스테이지의 1분 기대 보상률 50%를 인정 분 수만큼 적용한다.
- 쌀·재료·경험치 지급과 작업 상태 변경이 원자적으로 처리된다.
- 동일 claim 요청을 반복해도 보상이 중복 지급되지 않는다.
- 브라우저 시계 변경으로 보상량을 늘릴 수 없다.
- 계정 세션 대체와 네트워크 재연결에서도 작업이 중복 생성되지 않는다.

## 현재 전체 계정 적용 모드

`OFFLINE_REWARD_TEST_ALL_ACCOUNTS=true`, 배율 0.5, 유예 0초, 버킷 60초, 상한 28,800초를 사용한다. 보상 지급 실패 시 작업과 자산은 이전 상태로 롤백된다.


## What I noticed about how you think
- “현재 스테이지를 한시간 돌렸을때 보상”이라고 말해 보상 경험을 추상적인 자동화가 아니라 실제 플레이 시간으로 정의했다.
- “8시간이 최대”라고 바로 상한을 정해 무한 누적 악용을 막는 운영 경계를 먼저 잡았다.
- “종료 신호 없이도 보상”을 선택해 강제 종료 사용자도 놓치지 않는 편의성을 우선했다.
