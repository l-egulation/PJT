## 1. 목적

이 문서는 최초 로그인 사용자가 감자·고구마·옥수수 중 주력 재료 하나를 선택하고, 서버가 해당 선택을 자동 사냥의 재료 드롭 판정에 적용하기 위한 구현 요구사항을 정의한다. 재료 이름·최초 선택·드롭 비율의 정본은 [주력 재료 SSOT](../../30-domain/character/ssot.md), 아이템 지급과 보상 원자성의 정본은 [아이템 SSOT](../../30-domain/items/ssot.md)가 소유한다. 이 문서는 규칙의 두 번째 정본을 만들지 않고 구현 범위, 데이터 책임, API, 실패 처리와 검증 기준을 정의한다.

## 2. 기준 문서와 우선순위

| 구분 | 기준 문서 | 사용 방식 |
| --- | --- | --- |
| 주력 재료 규칙 | [주력 재료 SSOT](../../30-domain/character/ssot.md) | 재료 목록, 최초 선택 시점, 변경 불가, 드롭 비율과 판정 단위의 구현 기준 |
| 아이템·드롭 | [아이템 SSOT](../../30-domain/items/ssot.md) | 자동 사냥 재료 보상, 수량 지급, 원자성과 멱등성 기준 |
| 재료 드롭 수치 | [MVP 주력 재료 드롭표 v1](../../60-content/items/material-drops-mvp-v1.md) | 일반 적·보스 추첨 횟수, 성공률, 지급 수량과 챕터별 세대 가중치의 working 구현 기준 |
| 계정 상태 | [계정·저장 SSOT](../../30-domain/player/ssot.md) | 선택값의 서버 권한 저장과 재접속 복원 기준 |
| 클라이언트 UX | [클라이언트 UX SSOT](../../30-domain/player/ux/ssot.md) | 최초 로그인 차단 흐름, 선택 화면과 오류 표시 기준 |
| 거래 | [거래소 SSOT](../../30-domain/economy/ssot.md) | 감자·고구마·옥수수 거래의 구현 경계 |
| 결정 상태 | [결정 로그](../../80-decisions/README.md) | confirmed, working, unresolved 상태 확인 |
| 실행 상태 | [C 작업 색인](../../wiki/06-delivery/tasks/C-professions/_index.md), [F 작업 색인](../../wiki/06-delivery/tasks/F-items-inventory/_index.md), [K 작업 색인](../../wiki/06-delivery/tasks/K-client-ux/_index.md) | 개발·검증 상태와 완료 증거 확인 |

충돌 시 confirmed 결정이 반영된 SSOT를 우선한다. 작업 문서와 보관 원문의 구형 `A/B/C`, 선택 전문 단독 생산, 전문 변경 규칙은 현재 구현 기준으로 사용하지 않는다.

## 3. 범위

### 3.1 포함 범위

- 최초 로그인 후 주력 재료 선택 필요 여부 조회
- 감자·고구마·옥수수 선택지와 적용 드롭 비율 조회
- 주력 재료 최초 선택과 서버 권한 영구 저장
- 선택 완료 전 메인 화면과 게임 진행 차단
- 같은 재료 재요청의 멱등 성공과 다른 재료 재선택 거절
- 재접속·다른 클라이언트 접속 후 선택값 복원
- 자동 사냥에서 챕터별 누적 세대 풀을 적용하고 재료 보상 한 개마다 세대와 주력 재료 종류를 순서대로 추첨
- 전투 보상 지급의 원자성과 중복 방지
- 조회·선택 API 2개와 책임 경계

### 3.2 제외 범위

- 선택 완료 후 재료 변경권·초기화·관리자 변경
- 재료별 별도 선택 API
- 사용자가 드롭 비율이나 보상 수량을 제출하는 API
- 스테이지별 재료 드롭률의 최종 밸런스와 챕터별 세대 가중치의 `applied` 승격
- 장기 누적 결과를 정확히 80:10:10으로 맞추는 보정 또는 천장
- 거래소 등록·구매 API의 상세 계약
- 선택 화면의 최종 레이아웃·일러스트·문구·접근성 규격

스테이지별 재료 드롭률·지급 수량과 챕터별 세대 가중치의 working 값은 [MVP 주력 재료 드롭표 v1](../../60-content/items/material-drops-mvp-v1.md)이 소유한다. 본 명세는 해당 버전 데이터를 서버 권한 입력으로 사용하는 구현 계약을 정의하며, 최종 밸런스 승격은 드롭표의 검증 조건을 따른다.

## 4. 용어와 식별자

| 용어 | 의미 |
| --- | --- |
| 주력 재료 | 사용자가 최초 로그인 후 한 번 선택하는 감자·고구마·옥수수 중 하나 |
| 선택 미완료 | 인증은 완료했으나 주력 재료가 저장되지 않은 계정 상태 |
| 재료 보상 판정 | 스테이지 드롭 표가 재료 보상 1개를 생성하기로 한 뒤 세대와 재료 종류를 순서대로 정하는 판정 |
| 동일 선택 재요청 | 저장된 주력 재료와 요청 `materialType`이 같은 요청 |
| 변경 요청 | 저장된 주력 재료와 요청 `materialType`이 다른 요청 |
| 재료 세대 | M1부터 M4까지의 단계. 챕터가 오르면 상위 세대가 누적 해금되고 이전 세대도 드롭 풀에 남는다. |

외부 API와 영속 상태는 다음 안정 식별자를 사용한다.

| 표시명 | `materialType` |
| --- | --- |
| 감자 | `POTATO` |
| 고구마 | `SWEET_POTATO` |
| 옥수수 | `CORN` |

표시명이나 번역 문구는 바뀔 수 있지만 저장값과 API 식별자는 위 enum을 유지한다.

세대별 아이템 ID는 계열 식별자에 `_M1`~`_M4`를 결합한다.

| 세대 | 감자 | 고구마 | 옥수수 |
| --- | --- | --- | --- |
| M1 | `POTATO_M1` | `SWEET_POTATO_M1` | `CORN_M1` |
| M2 | `POTATO_M2` | `SWEET_POTATO_M2` | `CORN_M2` |
| M3 | `POTATO_M3` | `SWEET_POTATO_M3` | `CORN_M3` |
| M4 | `POTATO_M4` | `SWEET_POTATO_M4` | `CORN_M4` |

챕터별 누적 세대 풀은 다음과 같다.

| 현재 챕터 | 드롭 가능한 세대 |
| --- | --- |
| 1 | M1 |
| 2 | M1, M2 |
| 3 | M1, M2, M3 |
| 4 | M1, M2, M3, M4 |

## 5. 사용자 흐름

### 5.1 최초 진입

1. 사용자가 로그인한다.
2. 클라이언트가 주력 재료 선택 상태를 조회한다.
3. 선택 미완료이면 감자·고구마·옥수수와 각 선택 시 적용될 비율을 표시한다.
4. 선택 미완료 동안 메인 화면, 자동 전투와 게임 진행으로 진입할 수 없다.
5. 사용자가 한 재료를 선택하면 클라이언트는 해당 `materialType`만 서버에 보낸다.
6. 서버는 인증, enum 허용 여부와 현재 선택 상태를 검증한다.
7. 서버가 최초 선택을 저장하고 확정된 선택값과 현재 규칙에서 계산한 비율을 반환한다.
8. 클라이언트는 성공 응답을 반영한 뒤 메인 화면으로 이동한다.

### 5.2 자동 사냥 재료 보상

1. 서버의 스테이지 드롭 로직이 콘텐츠 버전의 적 유형별 추첨 횟수를 읽는다.
2. 각 추첨에서 콘텐츠 버전의 재료 드롭 성공률을 독립 판정한다.
3. 성공한 추첨마다 현재 챕터의 정수 세대 가중치로 세대 하나를 선택한다.
4. 서버가 사용자의 주력 재료를 조회한다.
5. 선택된 세대 안에서 주력 재료 80%, 두 비주력 재료 각각 10%로 종류를 독립 추첨한다.
6. 서버가 `계열 + 세대` 아이템 ID와 콘텐츠 버전의 지급 수량을 전투의 다른 보상과 함께 확정한다.
7. 서버가 보상 결과와 인벤토리 수량 변경을 한 멱등 처리 단위로 기록한다.
8. 클라이언트는 서버가 확정한 결과만 표시한다.

## 6. 기능 요구사항

### 6.1 선택 상태 조회

| ID | 요구사항 | 검증 |
| --- | --- | --- |
| MAT-QUERY-001 | 인증된 사용자는 자신의 주력 재료 선택 상태를 조회할 수 있어야 한다. | 미선택 계정은 `selected=false`, 선택 계정은 `selected=true`와 저장된 `materialType`을 받는다. |
| MAT-QUERY-002 | 조회 응답은 허용된 세 재료의 안정 식별자, 표시명과 각 재료를 선택했을 때 적용될 드롭 비율을 제공해야 한다. | 세 선택지 모두 주력 80, 나머지 각각 10인 합계 100의 비율을 반환한다. |
| MAT-QUERY-003 | 드롭 비율은 서버의 현재 게임 규칙에서 계산하며 사용자 저장값이나 클라이언트 입력을 사용하지 않아야 한다. | 규칙 버전 변경 시 사용자 행 수정 없이 조회 응답이 새 비율을 반영할 수 있다. |
| MAT-QUERY-004 | 선택 완료 계정의 조회 응답은 현재 주력 재료와 그 선택에 적용되는 재료별 비율을 반환해야 한다. | 재접속과 다른 클라이언트 조회에서도 같은 선택값과 서버 계산 비율이 반환된다. |
| MAT-QUERY-005 | 비인증 요청은 선택 여부나 계정 정보를 노출하지 않고 실패해야 한다. | 인증 없는 요청은 상태를 바꾸지 않고 인증 오류를 반환한다. |

### 6.2 최초 선택

| ID | 요구사항 | 검증 |
| --- | --- | --- |
| MAT-SELECT-001 | 인증된 선택 미완료 계정은 `POTATO`, `SWEET_POTATO`, `CORN` 중 하나를 주력 재료로 선택할 수 있어야 한다. | 각 enum의 최초 선택 요청이 성공하고 선택값이 저장된다. |
| MAT-SELECT-002 | 선택 요청은 `materialType`만 입력받고 확률, 보상 수량, 사용자 ID를 입력받지 않아야 한다. | 추가 확률 필드가 선택 결과나 게임 규칙에 영향을 주지 않는다. |
| MAT-SELECT-003 | 서버는 허용 enum을 검증하고 알 수 없는 값, 빈 값과 형식이 다른 값을 거절해야 한다. | 비정상 입력에서 상태가 바뀌지 않고 `INVALID_MATERIAL_TYPE`을 반환한다. |
| MAT-SELECT-004 | 최초 선택 저장은 계정당 최대 한 행 또는 동등한 유일성 제약으로 보호해야 한다. | 같은 계정의 동시 최초 선택 요청에서 서로 다른 두 값이 저장되지 않는다. |
| MAT-SELECT-005 | 최초 선택 성공 응답은 선택 완료 여부, 확정 `materialType`과 서버가 계산한 적용 비율을 반환해야 한다. | 클라이언트가 별도 확률 계산 없이 확정 상태를 표시할 수 있다. |
| MAT-SELECT-006 | 이미 선택한 계정이 같은 `materialType`을 다시 요청하면 새 상태 변경 없이 현재 확정 상태를 성공으로 반환해야 한다. | 응답 유실 뒤 동일 요청을 반복해도 같은 성공 결과로 수렴한다. |
| MAT-SELECT-007 | 이미 선택한 계정이 다른 `materialType`을 요청하면 변경 없이 거절해야 한다. | `POTATO` 저장 후 `CORN` 요청은 `MATERIAL_ALREADY_SELECTED`와 현재 `POTATO`를 반환한다. |
| MAT-SELECT-008 | 서버 오류 또는 트랜잭션 실패 시 선택값을 부분 저장하거나 불명확한 상태로 남기지 않아야 한다. | 실패 뒤 조회 결과가 성공 전 상태 또는 완전히 확정된 성공 상태 중 하나다. |
| MAT-SELECT-009 | 로그아웃·재로그인, 앱 종료·재실행과 다른 기기 접속 이후에도 확정 선택값을 유지해야 한다. | 모든 경로에서 서버에 저장된 같은 `materialType`을 조회한다. |

### 6.3 최초 로그인 차단 흐름

| ID | 요구사항 | 검증 |
| --- | --- | --- |
| MAT-GATE-001 | 로그인 성공 후 주력 재료가 없는 계정은 선택 화면으로 이동해야 한다. | 신규 계정은 메인 화면보다 선택 화면을 먼저 본다. |
| MAT-GATE-002 | 선택 미완료 계정은 메인 화면 진입, 1-1 전투 시작과 게임 진행 명령을 실행할 수 없어야 한다. | 경로 직접 접근과 API 직접 호출도 `MATERIAL_SELECTION_REQUIRED`로 실패한다. |
| MAT-GATE-003 | 선택 화면은 세 재료, 각 선택에 적용되는 비율과 최초 선택 후 변경할 수 없음을 선택 전에 표시해야 한다. | 사용자가 선택 효과와 영구성을 확인할 수 있다. |
| MAT-GATE-004 | 클라이언트는 선택 요청 처리 중 추가 클릭을 막되, 서버의 중복·동시 요청 검증을 대체하지 않아야 한다. | 빠른 연속 클릭에서도 하나의 확정 선택만 생성된다. |
| MAT-GATE-005 | 선택 성공 응답을 받은 뒤에만 메인 화면으로 이동해야 한다. | 검증 실패·충돌·서버 오류에서는 선택 화면을 유지하고 원인을 표시한다. |
| MAT-GATE-006 | 이미 선택한 계정은 최초 선택 화면을 건너뛰고 현재 선택값을 계정 상태에 반영해야 한다. | 재로그인 시 선택 화면이 반복되지 않는다. |

### 6.4 드롭 적용

| ID | 요구사항 | 검증 |

## 7. 데이터 책임과 불변 조건

### 7.1 서버 권한 상태

사용자별로 저장할 도메인 값은 하나다.

| 필드 | 제약 |
| --- | --- |
| `primaryMaterialType` | `POTATO`, `SWEET_POTATO`, `CORN` 중 하나, 선택 전만 `null`, 선택 후 변경 불가 |

구현은 사용자 테이블의 nullable enum 또는 계정당 유일한 별도 선택 행을 사용할 수 있다. 다음 불변 조건을 보장해야 한다.

- 한 계정에는 주력 재료가 없거나 정확히 하나만 존재한다.
- 선택 완료 후 다른 값으로 갱신할 수 없다.
- 사용자별 `potatoRate`, `sweetPotatoRate`, `cornRate`를 저장하지 않는다.
- 드롭 규칙 버전과 가중치는 콘텐츠 또는 서버 규칙으로 관리한다.
- 클라이언트 캐시는 표시용이며 서버 선택값을 덮어쓰지 않는다.

### 7.2 동시성

서로 다른 재료의 최초 선택 요청이 동시에 도착하면 서버는 정확히 하나만 최초 성공으로 확정한다. 패배한 요청이 확정값과 같으면 현재 성공 상태로 수렴하고, 다르면 `MATERIAL_ALREADY_SELECTED`로 실패한다. 최종 상태가 요청 도착 순서에 따라 둘 이상 생성되어서는 안 된다.

## 8. API 요구사항

MVP에 필요한 전용 API는 두 개다.

| 기능 | Method | Path | 요청 | 성공 응답 핵심 |
| --- | --- | --- | --- | --- |
| 선택 정보 조회 | `GET` | `/api/v1/material-preference` | 없음 | 선택 여부, 현재 주력 재료, 선택지, 적용 비율 |
| 최초 주력 재료 선택 | `POST` | `/api/v1/material-preference` | `materialType` | 선택 완료 여부, 확정 주력 재료, 적용 비율 |

### 8.1 조회 계약

선택 미완료 응답 예시:

```json
{
  "selected": false,
  "primaryMaterialType": null,
  "options": [
    {
      "materialType": "POTATO",
      "displayName": "감자",
      "dropRates": {
        "POTATO": 80,
        "SWEET_POTATO": 10,
        "CORN": 10
      }
    },
    {
      "materialType": "SWEET_POTATO",
      "displayName": "고구마",
      "dropRates": {
        "POTATO": 10,
        "SWEET_POTATO": 80,
        "CORN": 10
      }
    },
    {
      "materialType": "CORN",
      "displayName": "옥수수",
      "dropRates": {
        "POTATO": 10,
        "SWEET_POTATO": 10,
        "CORN": 80
      }
    }
  ]
}
```

선택 완료 응답은 `selected=true`, 확정 `primaryMaterialType`과 동일한 `options` 계약을 반환한다. 클라이언트가 현재 선택의 적용 비율을 별도로 계산할 필요가 없어야 한다.

### 8.2 선택 계약

요청 예시:

```json
{
  "materialType": "POTATO"
}
```

성공 응답 예시:

```json
{
  "selected": true,
  "primaryMaterialType": "POTATO",
  "dropRates": {
    "POTATO": 80,
    "SWEET_POTATO": 10,
    "CORN": 10
  }
}
```

같은 재료 재요청은 위와 같은 현재 확정 상태를 성공으로 반환한다. 다른 재료 재요청은 실패 응답에 현재 확정 `primaryMaterialType`을 포함해 클라이언트가 서버 상태로 복구할 수 있어야 한다.

### 8.3 오류 코드

| 코드 | 의미 | 상태 변경 | 클라이언트 처리 |
| --- | --- | --- | --- |
| `AUTHENTICATION_REQUIRED` | 인증 없음 또는 만료 | 없음 | 로그인 흐름으로 이동 |
| `INVALID_MATERIAL_TYPE` | 허용되지 않은 enum·빈 값·형식 오류 | 없음 | 선택 화면 유지, 입력 오류 표시 |
| `MATERIAL_SELECTION_REQUIRED` | 선택 미완료 상태에서 게임 진행 또는 재료 보상 요청 | 없음 | 선택 화면으로 이동 |
| `MATERIAL_ALREADY_SELECTED` | 저장값과 다른 재료로 변경 요청 | 없음 | 현재 확정값을 반영하고 변경 불가 안내 |
| `MATERIAL_PREFERENCE_UNAVAILABLE` | 일시적 서버 오류로 상태를 확정할 수 없음 | 없음 또는 이미 확정된 상태 | 재조회·재시도 가능 안내 |

HTTP 상태, 오류 envelope, 인증 헤더와 공통 추적 ID는 프로젝트 공통 API 계약에서 확정한다. 본 명세는 도메인 의미와 상태 변경 여부를 정의한다.

## 10. 검증 기준

### 10.1 선택과 저장

- 감자·고구마·옥수수 각각의 최초 선택이 성공한다.
- 잘못된 enum, 빈 값과 인증 없는 요청은 상태를 바꾸지 않는다.
- 같은 재료 재요청은 동일한 확정 상태로 성공한다.
- 다른 재료 재요청은 현재 선택을 유지하고 실패한다.
- 서로 다른 재료의 동시 요청은 하나의 선택값만 남긴다.
- 재로그인, 앱 재실행과 다른 클라이언트 접속에서도 선택값이 유지된다.
- 사용자 저장 데이터에 비율 필드가 존재하지 않는다.

### 10.2 진입 차단과 UI

- 신규 계정은 로그인 후 선택 화면을 먼저 본다.
- 선택 전 메인 화면·1-1 전투·직접 게임 진행 API 호출이 모두 차단된다.
- 선택 화면은 세 재료, 각 비율과 변경 불가를 선택 전에 보여 준다.
- 처리 중 연속 클릭이 중복 화면 전환이나 서로 다른 선택 상태를 만들지 않는다.
- 성공 응답 뒤 메인 화면으로 이동하고 실패 응답에서는 선택 화면을 유지한다.
- 기존 선택 계정은 선택 화면을 건너뛴다.

### 10.3 드롭과 보상

- working 콘텐츠 버전에서 일반 적 1회·15%, 보스 5회·각 15%, 성공당 10개를 읽는지 확인한다.
- 일반 적 20마리와 보스 1마리의 한 사이클이 25회의 독립 재료 추첨 기회를 만드는지 확인한다.
- 챕터 1~4의 누적 세대 풀이 각각 `M1`, `M1~M2`, `M1~M3`, `M1~M4`인지 확인한다.
- 챕터별 정수 세대 가중치가 `1`, `5:1`, `25:5:1`, `125:25:5:1`이고 아직 해금되지 않은 세대의 가중치가 0인지 확인한다.
- M1~M4 각 세대에서 세 주력 선택의 계열 가중치가 각각 `80:10:10`이고 합계가 100인지 확인한다.
- 같은 seed·입력·콘텐츠 버전으로 같은 `계열 + 세대` 아이템 ID와 수량이 재현된다.
- 여러 재료 보상의 성공·세대·계열이 개별 독립 판정된다.
- 드롭 수치나 주력 재료 규칙 버전을 바꿔도 사용자 데이터 마이그레이션이 필요하지 않다.
- 클라이언트가 보낸 세대·확률·종류·수량이 결과에 영향을 주지 않는다.
- 미선택 계정에는 재료 보상을 만들지 않는다.
- 동일 전투 보상 재시도에서 재료가 중복 지급되지 않는다.
- 서버 응답의 아이템 ID·수량과 인벤토리 증가량이 일치한다.

확률 검증은 짧은 난수 표본의 실측 비율 일치만으로 판정하지 않는다. 가중치 매핑, 경계값 선택, 결정론적 seed 결과를 검증하고 충분한 표본의 통계 검사는 보조 회귀 검증으로 사용한다.

## 12. 완료 정의

- 기능 요구사항 32개가 구현 또는 검증 작업과 연결된다.
- 전용 API 두 개가 인증·입력·응답·오류 계약을 충족한다.

- 감자·고구마·옥수수 명칭과 구형 A/B/C·단독 생산·전문 변경 문서의 충돌이 정본과 결정 로그에서 해소된다.
