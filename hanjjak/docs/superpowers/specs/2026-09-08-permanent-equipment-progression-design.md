# 영구 장비 해금·강화·승급 설계

## 목적

장비 성장을 반복 제작·교체 구조에서 `부위별 최초 제작 1회 → 지속 강화 → 챕터 클리어 후 승급` 구조로 전환한다. 계정은 무기·장갑·갑옷·투구·망토·신발을 각각 최대 하나만 영구 소유하며, 장비 인스턴스 다중 보유·장착 교체·재제작은 제공하지 않는다.

게임 규칙과 수치는 [장비 SSOT](../../30-domain/items/equipment/ssot.md)가 소유하고, 전투 능력치 계산은 [전투 SSOT](../../30-domain/combat/ssot.md)가 소유한다. 실행 상태와 검증 증거는 [G·K 작업 문서](../../wiki/06-delivery/tasks/_index.md)가 소유한다. 이 문서는 2026-09-08 사용자 승인 설계의 기록이며 현재 기준은 전파된 SSOT와 결정 로그를 따른다.

2026-09-09 이후 장비 강화 카드의 부족 재료 거래소 구매 흐름은 [장비 강화 부족 재료 거래소 구매 계획](../../70-plans/equipment-shortage-market-purchase/requirements.md)이 구체화하며, 이 문서의 비용·강화 상태 규칙은 변경하지 않는다.

## 범위

포함한다.

- 6부위 최초 제작과 영구 해금
- 등급별 1~30강 강화
- 챕터 클리어와 30강을 함께 요구하는 승급
- 노말·희귀·영웅·전설을 잇는 연속 성장
- 누적 세대 혼합 강화 비용
- 다음 세대 재료 승급 비용
- 부위별 하나의 장비 성장 상태
- 장비 화면의 미해금·강화·승급·최종 완료 상태
- 부위 기반 조회·명령 API와 멱등 처리

제외한다.

- 완성 장비 드롭·거래
- 장비 인스턴스 다중 보유
- 장착·교체
- 장비 잠금·분해·판매
- 강화 실패·파괴·하락
- 주문서와 품질 수치
- 전설 이후 등급

## 장비 생명주기

계정은 다음 6부위를 각각 최대 하나만 영구 소유한다.

- `WEAPON`: 무기
- `GLOVES`: 장갑
- `ARMOR`: 갑옷
- `HELMET`: 투구
- `CAPE`: 망토
- `SHOES`: 신발

부위별 상태 전이는 다음과 같다.

```text
미해금
→ 최초 제작
→ 노말 1강
→ 노말 30강
→ 1-10 최초 클리어 후 희귀 승급
→ 희귀 1강
→ 희귀 30강
→ 2-10 최초 클리어 후 영웅 승급
→ 영웅 1강
→ 영웅 30강
→ 3-10 최초 클리어 후 전설 승급
→ 전설 1~30강
→ 최종 성장 완료
```

- 주력 재료를 선택한 뒤 6부위 최초 제작식이 모두 열린다.
- 최초 제작은 부위별 계정당 한 번만 가능하다.
- 제작 성공 시 해당 부위가 노말 1강으로 영구 해금된다.
- 같은 부위를 다시 제작하지 않는다.
- 미해금 부위는 전투 계산에서 기존 기본 Q=0 기여를 사용한다.
- 해금된 모든 부위는 별도 장착 없이 항상 전투에 적용된다.
- 제작·강화·승급 성공률은 100%다.

## 최초 제작 비용

모든 부위는 같은 비용을 사용한다.

| 항목 | 수량 |
| --- | ---: |
| 쌀 | 100 |
| 감자 M1 | 10 |
| 고구마 M1 | 10 |
| 옥수수 M1 | 10 |

최초 제작 비용 차감과 노말 1강 상태 생성은 하나의 원자적 결과다.

## 강화 단계와 쌀 비용

각 등급은 화면에서 1~30강을 사용한다. 다음 강화 비용은 전체 성장 구간에서 연속 증가한다.

```text
gradeIndex = NORMAL 0, RARE 1, EPIC 2, LEGENDARY 3
costStep = gradeIndex × 30 + currentEnhancementLevel
riceCost = 30 × costStep
```

`currentEnhancementLevel`이 30이면 다음 강화 비용과 강화 동작을 제공하지 않는다. 전설 이외 등급은 승급 조건을 확인하고, 전설 30강은 최종 성장 완료 상태다.

| 강화 | costStep | 쌀 비용 |
| --- | ---: | ---: |
| 노말 1→2강 | 1 | 30 |
| 노말 29→30강 | 29 | 870 |
| 희귀 1→2강 | 31 | 930 |
| 희귀 29→30강 | 59 | 1,770 |
| 영웅 1→2강 | 61 | 1,830 |
| 영웅 29→30강 | 89 | 2,670 |
| 전설 1→2강 | 91 | 2,730 |
| 전설 29→30강 | 119 | 3,570 |

승급 후 강화 단계는 1로 돌아가지만 첫 강화 비용은 직전 등급의 마지막 강화 비용보다 높다.

## 강화 재료

강화는 현재 등급까지의 모든 세대 재료를 누적 사용한다.

| 등급 | 사용하는 세대 |
| --- | --- |
| 노말 | M1 |
| 희귀 | M1, M2 |
| 영웅 | M1, M2, M3 |
| 전설 | M1, M2, M3, M4 |

강화 묶음 수는 다음과 같다.

```text
bundleCount = ceil(costStep / 10)
```

묶음 하나는 세대 가치 `1:5:25:125`에 맞춘 동일 환산 가치다. 각 세대에서 감자·고구마·옥수수를 같은 수량으로 소비한다.

| 세대 | 묶음 1개당 각 재료 수량 |
| --- | ---: |
| M1 | 125 |
| M2 | 25 |
| M3 | 5 |
| M4 | 1 |

예를 들어 희귀 1→2강은 `costStep=31`, `bundleCount=4`이므로 감자·고구마·옥수수 각각 M1 500개와 M2 100개를 소비한다.

## 승급 조건과 비용

승급은 부위별로 실행한다. 계정 진행과 현재 부위 상태를 모두 만족해야 한다.

| 승급 | 강화 조건 | 진행 조건 | 쌀 | 다음 세대 각 재료 |
| --- | --- | --- | ---: | ---: |
| 노말→희귀 | 노말 30강 | 1-10 최초 클리어 | 1,000 | 감자·고구마·옥수수 M2 각 10 |
| 희귀→영웅 | 희귀 30강 | 2-10 최초 클리어 | 5,000 | 감자·고구마·옥수수 M3 각 10 |
| 영웅→전설 | 영웅 30강 | 3-10 최초 클리어 | 25,000 | 감자·고구마·옥수수 M4 각 10 |

승급 성공 시 등급을 하나 올리고 강화 단계는 1이 된다. 진행 조건을 만족해도 해당 부위가 30강이 아니면 승급할 수 없다. 30강이어도 챕터를 클리어하지 않았으면 승급할 수 없다.

## 능력치 연속성과 승급 점프

유효 Q는 다음 공식으로 계산한다.

```text
gradeOffset = NORMAL 0, RARE 39, EPIC 78, LEGENDARY 117
Q = gradeOffset + enhancementLevel
```

| 상태 | Q |
| --- | ---: |
| 노말 1강 | 1 |
| 노말 30강 | 30 |
| 희귀 1강 | 40 |
| 희귀 30강 | 69 |
| 영웅 1강 | 79 |
| 영웅 30강 | 108 |
| 전설 1강 | 118 |
| 전설 30강 | 147 |

각 승급은 직전 등급 30강보다 Q가 10 높은 지점에서 시작한다. 공격력·최대 HP 장비는 기존 $M(Q)=1.05^{Q/2}$ 공식을 사용하고, 방어 관통 장비도 같은 Q를 입력으로 사용한다. 클라이언트는 Q나 능력치 증가량을 재계산하지 않는다.

## 저장 모델

계정×부위를 유일 키로 저장한다.

```text
account_id
slot
grade
enhancement_level
unlocked_at
updated_at
```

불변 조건:

- `(account_id, slot)`은 유일하다.
- 해금된 상태의 강화 단계는 1~30이다.
- 등급은 `NORMAL`, `RARE`, `EPIC`, `LEGENDARY` 중 하나다.
- 미해금은 행 없음으로 표현한다.
- 장비 UUID, 장착 상태와 다중 보유 목록을 저장하지 않는다.

현재 개발 DB의 기존 장비·장착 데이터만 clean cutover 시 초기화한다. 계정·지갑·재료 인벤토리·치장 및 그 밖의 데이터는 초기화하지 않는다. 운영 사용자 데이터 마이그레이션으로 해석하지 않는다.

## API

```http
GET  /api/v1/equipment
POST /api/v1/equipment/{slot}/unlock
POST /api/v1/equipment/{slot}/enhance
POST /api/v1/equipment/{slot}/promote
```
조회 응답은 6부위 각각에 대해 다음을 서버 계산값으로 제공한다.

- 해금 여부
- 현재 등급·강화 단계·Q·능력치
- 최초 제작 비용·실행 가능 여부, 쌀 잔액과 필요한 각 재료의 보유량
- 다음 강화 비용·재료·능력치 상승량(`statIncrease`)·전체 결과와 실행 가능 여부
- 승급 대상 등급·진행 조건·비용·승급 후 Q·능력치와 실행 가능 여부
- 비활성 사유

쌀 차감은 `wallet_balance`와 `wallet_ledger`를 같은 트랜잭션에서 갱신한다. 장비 command의 멱등 키를 ledger source ID로 사용하고, wallet service의 내부 상태 버전 증가는 억제한 뒤 장비 command가 계정 상태 버전을 한 번 증가시킨다.

영구 장비 해금·강화·승급은 권한 상태 변경과 같은 트랜잭션에서 Outbox 이벤트를 기록한다. 이벤트는 장비 인스턴스 UUID 대신 `equipmentSlot`과 계정·부위 기반 안정 aggregate ID를 사용하며, 승급은 `EQUIPMENT_PROMOTED`로 분리한다. 상세 계약은 [데이터·이벤트 SSOT](../../40-systems/event-system/ssot.md)와 `packages/contracts/events.tsp`를 따른다.

모든 명령은 UUID 멱등 키와 payload fingerprint를 사용한다. 같은 요청 재시도는 저장된 결과를 반환하고 같은 키의 다른 요청은 거절한다.

기존 API는 clean cutover에서 제거한다.

- `POST /api/v1/equipment/craft`
- `POST /api/v1/equipment/{equipmentId}/equip`
- 장비 UUID 기반 강화 API

## 화면

기존 제작식·보유 장비·장착 슬롯 화면을 6개 영구 부위 성장 카드로 교체한다.

### 미해금 카드

- 부위명
- 기본 Q=0 능력치 기여
- 공통 최초 제작 비용
- 보유량/필요량
- 제작 가능 여부와 부족 사유
- `최초 제작` 버튼

### 강화 카드

- 현재 등급·강화 단계
- 현재 Q와 능력치
- 다음 강화 후 Q와 능력치 상승량
- 다음 강화 쌀·세대별 재료 비용
- 보유량/필요량
- `강화` 버튼

### 승급 카드

- 현재 등급 30강 충족 여부
- 요구 챕터 클리어 여부
- 다음 등급과 승급 후 1강
- 승급 전·후 Q와 능력치
- 승급 쌀·다음 세대 재료 비용
- `승급` 버튼

전설 30강은 버튼 대신 `최종 성장 완료`를 표시한다.

## 오류와 원자성

다음 오류를 구분한다.

- 이미 해금된 부위
- 미해금 부위 강화·승급
- 재료 부족
- 쌀 부족
- 현재 등급 30강 미달
- 승급 요구 챕터 미클리어
- 전설 이후 승급
- 전설 30강 이후 강화
- 같은 멱등 키에 다른 요청 재사용

비용 차감과 장비 상태 변경은 한 트랜잭션으로 확정한다. 실패하면 재료·쌀·등급·강화 단계·계정 상태 버전을 변경하지 않는다.

## 검증 기준

- 계정×부위 상태가 최대 한 개다.
- 6부위 최초 제작 비용이 모두 100쌀·M1 세 재료 각 10개다.
- 최초 제작 재시도는 중복 상태나 중복 차감을 만들지 않는다.
- 각 등급의 강화 단계는 1~30이다.
- 다음 강화 쌀 비용 경계가 `30, 870, 930, 1,770, 1,830, 2,670, 2,730, 3,570`이다.
- 실행 가능한 강화의 costStep 1·10·11·29·31·119에서 `bundleCount`는 각각 1·1·2·3·4·12다. 각 등급 30강에는 강화 비용을 노출하거나 차감하지 않는다.
- 등급별 누적 세대와 묶음당 `M1 125, M2 25, M3 5, M4 1` 수량을 정확히 적용한다.
- 각 세대의 감자·고구마·옥수수 수량이 같다.
- 30강과 챕터 클리어를 모두 만족해야 승급한다.
- 승급 후 다음 등급 1강이 되고 Q 경계가 `30→40`, `69→79`, `108→118`이다.
- 전설 30강에서 강화·승급을 모두 차단한다.
- 조회 응답의 비용·Q·능력치와 명령 결과가 일치한다.
- 같은 멱등 키 재시도와 실패 원자성을 검증한다.
- 화면이 미해금·강화·승급 대기·승급 가능·최종 완료 상태를 구분한다.

단위·컴포넌트 테스트만 수행한 단계는 `개발 완료 / 부분 검증`으로 기록한다. PostgreSQL migration, 실제 Spring Boot HTTP와 실제 브라우저 E2E를 수행하기 전에는 `검증 완료`로 올리지 않는다.
