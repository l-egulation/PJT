# 간편 거래·호가 거래 경험 분리 개선안

## 확정된 기준과 제안의 경계

사용자가 확정한 경험 기준은 [클라이언트 UX SSOT](../../30-domain/player/ux/ssot.md#거래소), 결정·전파 상태는 [결정 로그](../../80-decisions/README.md)가 소유한다. 아래 가격대 표시 형식·입력 연동·배치·구현 순서는 그 기준을 구현하기 위한 candidate다. 계획 작성은 구현 승인이 아니다.

체결·자산 규칙은 [거래소 SSOT](../../30-domain/economy/ssot.md), 현재 API는 [Networking](../../50-architecture/networking.md#거래소주문장-계약), 최초 선택 근거는 [Office Hours 설계](./design.md)를 참조한다.

## 사용자 근거와 앞선 해석의 정정

2026-09-11 사용자는 약 50명에게 기존 거래 UI를 테스트했으며, `어떤 상품을, 얼마에, 몇 개 구매하고 최대 단가를 얼마까지 허용할지` 정하는 데 큰 진입 장벽이 없었다고 보고했다. 기존 매물 리스트도 개별 판매자나 주문을 고르는 것이 아니라 각 가격대에 물량이 얼마나 있는지 보여 주는 역할이었다고 명확히 했다. 이 사용자 보고를 계획의 근거로 사용하며 재현 테스트를 요구하지 않는다. 이를 새 화면의 사용성 검증 완료나 판매 흐름까지 검증됐다는 근거로 확대하지 않는다.

앞선 계획의 다음 제안은 철회한다.

- 가격 입력을 없애고 수량만 입력하게 하는 간편 거래.
- 현재 최저 가격의 물량만 구매하도록 제한하고 다른 가격대 구매를 별도 승인 대상으로 돌리는 방식.
- 간편 거래는 가격을 정하지 않고 호가창에서만 가격을 정한다는 역할 구분.
- 가격 생략·자동 단가 선택 API를 이번 개선의 선행 조건으로 추가하는 것.
- 간편 판매의 첫 행동을 무조건 즉시 판매로 바꾸는 것.

유지할 것은 특정 매물 리스트 모양이 아니라 사용자가 이미 이해하는 가격·수량 판단 방식이다. 호가창이 기능상 상위 호환이어도 두 경험이 겹치는 것은 문제가 아니다. 간편 거래를 불편하게 만들어 기능 차이를 강제하지 않는다.

## 현재 문제

[MarketScreen](../../../apps/web/src/features/market/MarketScreen.tsx)은 `view`에 따라 `SimpleOverview`와 `OrderBookPanel`만 바꾸고 `OrderTicket`을 공유한다. 간편 화면의 최우선 가격 요약만으로는 그다음 가격대에 얼마의 물량이 있는지 알 수 없고, 호가 차트는 사용자에게 가격별 수량을 쉽게 읽게 하지 못하는 상태라는 보고가 있다.

따라서 문제는 최대 단가 입력 자체가 아니다. **입력한 수량과 최대 단가가 현재 시장 물량과 어떻게 연결되는지 읽을 수 있는 정보가 부족하다.** 공통 입력 필드가 있다는 것도 그 자체로 잘못이 아니다. 목적에 맞는 시장 정보와 조작 동선 없이 동일한 고급 주문 패널을 양쪽에 노출하는 점을 바꾼다.

## 경험 분리 권장안

| 항목 | 간편 거래 | 호가 거래 |
| --- | --- | --- |
| 중심 질문 | 이 상품을 이 가격까지 허용하면 몇 개 살 수 있나? | 양쪽 시장이 어떤 상태이고 어떤 조건으로 주문할까? |
| 시장 정보 | 현재 행동에 필요한 가격대별 물량과 누적 물량 | 양방향 시장 깊이·내 주문·최근 체결 |
| 입력 | 구매 수량·최대 단가, 판매 목적에 맞는 가격·수량 | 방향·수량·가격·즉시/대기 주문 조건 |
| 화면의 주어 | 상품과 구매·판매 결과 | 시장과 주문 |
| 사용자 동작 | 가격대 물량 확인 → 수량·허용 가격 설정 → 견적 확인 | 시장 깊이 확인 → 주문 조건 설정 → 견적 확인 |

간편의 가격 입력·복수 가격대 거래·부분 거래를 없애지 않는다. 고급은 간편에서 할 수 있는 거래를 포함하면서 시장 전체 확인과 확장 주문을 제공한다. 엔진·거래 데이터·수령·정산은 동일하며 별도 시장을 만들지 않는다.

## 간편 구매: 가격대별 물량 안내

### 권장 표현

차트 대신 숫자를 바로 읽는 가격대 행을 기본 후보로 둔다. 동일 가격의 여러 주문은 한 가격대로 합쳐 보인다. 개별 매물·판매자 선택이나 구형 listing API를 복원하지 않는다. 행 안에 짧은 물량 막대를 보조로 둘 수 있지만 숫자와 단위 없이 막대 길이만 해석하게 만들지 않는다.

아래는 **표시 검토용 가상 시장**이다. 본인 주문·자산·공간 제약이 없는 예시이며 실제 로컬 시장 상태나 정책 수치가 아니다.

| 개당 가격 | 해당 가격의 판매 물량 | 이 가격 이하 누적 물량 |
| --- | ---: | ---: |
| 110쌀 | 40개 | 40개 |
| 125쌀 | 60개 | 100개 |
| 140쌀 | 100개 | 200개 |

읽게 하려는 관계는 `125쌀까지 허용하면 현재 판매 물량은 100개`다. 누적 100개를 전부 125쌀에 산다는 의미가 아니며, 특정 판매자의 60개 주문을 고른다는 의미도 아니다.

- 실제 화면의 물량은 본인 물량을 별도로 구분하고, 구매 대상이 될 수 있는 타인 물량의 누적을 사용한다. 누적 물량은 사용자의 지갑·인벤토리까지 반영한 확정 구매 가능량이 아니므로 `시장 물량`과 `내 조건의 예상 구매량`을 분리한다. 매수는 본인 매도 물량을 구매 후보에서 제외하며, 매도 방향의 본인 교차만 별도 안내한다.

### 입력과 연동

위 가상 시장에서 수량 80개·최대 단가 125쌀을 입력하면 다음처럼 연결한다.

- 허용 가격 안의 물량 영역을 강조한다. 예시의 110쌀 물량 40개와 125쌀 물량 중 40개가 예상 구매 대상임을 보여 준다.
- 예상 구매: 80개, 예상 결제액: 9,400쌀, 예상 평균 단가: 117.5쌀.
- 최대 지출 한도: 10,000쌀. 예상 결제액과 최대 지출을 같은 값으로 표시하지 않는다.
- 125쌀 행 선택은 최대 단가만 125쌀로 채우는 편의 동작으로 제안한다. 수량을 누적 물량으로 바꾸거나 주문을 실행하지 않는다.
- 최대 단가는 계속 직접 입력할 수 있다. 시장에 정확히 같은 가격 행이 없는 값도 허용 범위 안이면 입력하고 해당 경계까지 포함되는 물량을 표시한다.
- 요청 수량을 채울 수 없으면 요청량·현재 조건의 예상량·부족량을 함께 보여 준다. 입력 수량이나 가격을 자동으로 바꾸지 않는다.

가격대별 물량을 읽는 것만으로 복잡한 주문 개념을 배울 필요는 없다. 기본 구매 폼은 품목·수량·최대 단가·예상 결과에 집중하고, 고급 주문의 방향/유형 조합을 그대로 붙여 놓지 않는다.

## 간편 판매와 호가 거래

간편 판매는 기존 판매 등록과 즉시 판매를 목적별로 찾을 수 있게 유지한다. 이번 사용자 근거는 구매 흐름이므로 판매 진입 기본값을 임의로 변경하지 않는다.

- 판매 등록: 품목·판매할 수량·판매 가격을 입력하고, 같은 품목의 가격대별 판매 물량을 참고해 가격을 판단한다. 이것은 경쟁 판매 물량이며 지금 그 가격에 팔 수 있는 수요로 표현하지 않는다.
- 즉시 판매: 현재 구매 대기 물량을 높은 가격부터 표시하고 `개당 최소 허용 가격`과 판매 수량을 입력한다. 누적은 구매와 반대로 해당 가격 이상 물량이다.
- 판매금액·수수료·순정산액·수령 위치를 기존 정책에 맞게 확인한다. 판매 등록의 즉시 판매분과 대기분도 구분한다.
- 호가창은 기존 양방향 깊이·최근 체결·주문 패널과 매수/매도·지정가/즉시 조건 설정을 유지한다. 이번 작업에서 차트 자체를 다시 디자인하거나 그 기능을 축소하지 않는다.

## 화면과 모드 전환

간편은 `품목 탐색 | 가격대별 물량 + 구매/판매 입력`, 호가 거래는 `품목 탐색 | 양방향 시장 깊이 + 고급 주문 입력`을 권장한다. 같은 필드를 공유해도 간편에서는 구매/판매 목적이 먼저 정해지고 그에 필요한 정보만 보여 준다. 모바일은 가격대 숫자와 입력 결과를 함께 찾아볼 수 있는 세로 흐름으로 구성한다.

- 구매/판매 방향 선택의 중복을 줄인다. 기존 품목 탐색과 수령·정산·내 주문은 공유한다.
- 같은 품목·방향·즉시 거래 목적에서 모드를 바꾸면 수량과 가격 한도를 보존하고 다시 견적을 확인한다. 최대 단가를 설정할 줄 아는 사용자의 입력을 이유 없이 버리지 않는다.
- 대기 주문에서 간편으로 이동할 때는 즉시 거래로 몰래 변환하지 않는다. 대응하는 판매 등록 흐름 또는 별도 고급 초안으로 보존하고, 현재 실행 목적을 명시적으로 선택한 뒤 재확인하게 한다.
- 품목/방향 변경 시 관련 견적·확인을 무효화하며 다른 품목의 단가를 재사용하지 않는다. 모드 전환만으로 주문을 제출하거나 기존 주문을 취소하지 않는다.
- 시세 갱신은 사용자가 입력한 최대/최소 단가를 덮어쓰지 않는다. 확인 대상 입력과 견적을 구분하고 실제 실행 결과는 서버 응답으로 표시한다.

## 구현 경계와 선행 관계

### 기존 계약 우선 사용

[MarketDepthLevel](../../../modules/market/src/main/kotlin/com/hanjjak/market/domain/OrderBook.kt)은 가격·총량·누적·본인 물량을 제공한다. [OrderBookService](../../../modules/market/src/main/kotlin/com/hanjjak/market/application/OrderBookService.kt)는 명시적 가격과 수량의 견적 및 생성 명령을 이미 처리한다. 가격대별 안내와 기존 최대 단가 거래를 연결하기 위해 새 주문 유형이나 자동 가격 선택 API가 필요한 것은 아니다.

공통 수치 표시·입력 검증·API·명령 결과 처리를 재사용한다. 간편과 고급이 동일 컴포넌트를 전혀 공유하면 안 된다는 제약도 두지 않는다. 사용자 동선을 분리하는 데 필요한 컴포넌트만 나누고 `simple` 플래그로 고급 폼 일부만 가리는 구현으로 끝내지 않는다.

### 물량 조회와 견적의 정확성

- depth는 제한된 가격대만 반환한다. 현재 서버는 `levels` 1~20을 받는다. 표시 끝의 누적량을 시장 전체 물량으로 단정하거나 그 범위 밖의 허용 가격을 거래 불가로 처리하지 않는다.
- 첫 구간 외 가격대를 확인할 필요가 있으면 가격대 더 보기/조회 범위 확장을 제공하는 계약안을 함께 검토한다. 조회 구간과 다음 구간 존재 여부를 명시하고 숫자 상한을 임의로 늘리는 것으로 전체 시장 지원을 대체하지 않는다. 부분 구간에서 누적을 계산할 경우 더 유리한 미표시 구간을 누락하지 않는다.
- 입력한 수량·가격에 대한 예상 거래는 화면에 표시된 depth 합계가 아니라 서버 `order-quote`를 사용한다. 시각 표시와 견적 revision이 다르면 서로 다른 시점의 숫자를 일치하는 것처럼 합치지 않는다.
- 기존 `quote`는 매수 시 본인 매도 주문을 제외한 상대 잔량으로 예상량을 계산하고, 매도 시 본인 반대 주문 교차를 거절하며 자산을 별도 반환한다. 단순 시장 물량을 `지금 확정 구매 가능`으로 바꾸지 않는다. 사용자 조건을 반영한 가능량을 약속하려면 자산·공간 검증과 실행의 차이를 I 작업에서 해소해야 한다.
- 보석은 시장 품목의 실제 옵션 값과 판매 인스턴스를 구분한다. 표시명이 같다는 이유로 물량을 합치지 않는다.
- 단가 한도 안의 복수 가격대 체결은 기존 엔진을 사용한다. 총액·수수료는 서버 개별 체결 결과를 사용하고 견적은 가격/수량 예약으로 취급하지 않는다.
- 계약 보완이 필요할 때만 TypeSpec·생성 OpenAPI/SDK·서버·웹 호출자를 함께 바꾼다. 기존 장비 부족 재료 구매의 명시적 가격 계약은 유지한다. DB migration·별도 시장·새 매칭 엔진은 이 개선에 필요하지 않다.

## 남은 설계 선택

가격대 행·짧은 막대·누적 요약을 어떻게 조합할지, 추가 가격대를 어떻게 펼칠지, 고급 대기 초안에서 간편으로 돌아올 때의 구체 배치는 candidate다. 최대 단가 입력 유지·가격대 물량의 가독성·개별 매물 목록 비강제라는 사용자 기준을 다시 미정으로 돌리지 않는다. 새 화면의 사용성 검증은 기존 테스트를 재확인하는 것이 아니라 그 경험이 유지되고 가격대 물량 판단이 개선됐는지 비교하는 것이다.
