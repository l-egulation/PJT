# 진행·성장 리밸런싱 v1 구현 설계

## 목적

`progression-rebalance-v1`의 승인 정책과 수치를 한 콘텐츠 버전으로 구현하고, 기존 전투 결과·replay·멱등 결과를 보존한 채 신규·기존 계정에 안전하게 적용한다. 이 문서는 구현 구조·데이터 흐름·오류 처리·검증만 소유하며 규칙과 수치는 복제하지 않는다.

## 범위

### 포함

- 1~4장·1~79레벨 콘텐츠 산출과 런타임 적용
- 1~4장 최초 클리어 보상과 1장 확정 재료 드롭
- 노말·희귀·영웅 장비 비용 적용
- 최초 스킬 직접 해금
- 기존 계정 최초 클리어 기록의 버전형 소급 지급
- 인벤토리 공간 부족 최초 보상의 전용 수령 대기함
- 1~4장 적 수치 재산출과 진행·경제 인수 시뮬레이션

### 제외

- 5~10장·80레벨 이후 절대 수치
- 전설·신화 장비 비용과 M4·M5 신규 공급
- 4-10 신규 보상과 레이드 보상
- 치장 티켓·천장·확률을 포함한 치장 밸런스
- 기존 보석 규칙과 거래소 체결 규칙 변경

## 콘텐츠 구조

`progression-rebalance-v1` manifest는 다음 데이터 파일과 의존 버전을 함께 고정한다.

- 1~79레벨 몬스터 경험치
- 1~4장 최초 클리어 보상
- 1장 확정 재료 드롭
- 희귀·영웅 단계별 장비 재료 비용
- 1~4장 적 수치와 기준 빌드 ID
- 유지하는 2~4장 반복 드롭 콘텐츠 버전

loader는 보상 합계, 장비 단계 합계, 레벨 행 완전성, 스테이지·아이템·스킬 참조와 의존 버전을 전체 검증한다. 하나라도 잘못되면 새 버전을 활성화하지 않는다. Kotlin·React 상수로 정책 수치를 복제하지 않는다.

## 전투 버전 경계

- 새 전투 세션은 시작 시 `progression-rebalance-v1`을 snapshot한다.
- 세션 중 배포가 바뀌어도 적·경험치·드롭·최초 보상을 섞지 않는다.
- 기존 진행 중 세션, 저장 결과와 replay는 시작 당시 콘텐츠 버전을 계속 사용한다.
- 새 버전은 새 전투 세션과 새 최초 클리어 결과부터 적용한다.

## 최초 클리어 보상 모델

### 저장 상태

최초 보상 레코드는 `(account_id, stage_id, reward_version)` 유일 키를 사용한다. 최소 상태는 다음과 같다.

- 최초 클리어 결과 식별자와 적용 콘텐츠 버전
- 쌀 지급 완료 여부와 지급량
- 직접 스킬 해금 결과
- 아이템 보상 묶음 snapshot
- 아이템 상태 `CLAIMED` 또는 `PENDING`
- 생성·지급·수령 시각

계정은 적용한 리밸런싱 버전과 소급 완료 시각을 가진다. 물리 테이블명은 기존 저장 규칙에 맞춰 구현 계획에서 확정한다.

### 신규 최초 클리어

1. 전투 세션 snapshot의 보상표를 읽는다.
2. 최초 클리어·다음 스테이지 해금과 보상 유일 키를 확인한다.
3. 쌀과 직접 스킬 해금을 같은 서버 명령에서 확정한다.
4. 아이템 묶음의 전체 수용량을 검사한다.
5. 수용 가능하면 인벤토리에 전량 지급하고 `CLAIMED`로 기록한다.
6. 공간이 부족하면 아이템 묶음을 `PENDING`으로 보존한다. 클리어·해금·쌀·스킬 결과는 되돌리지 않는다.
7. 동일 명령 재시도는 저장 결과를 반환한다.

### 수령 대기함

- 우편·거래 정산과 분리한 최초 보상 전용 조회·수령 API를 둔다.
- 조회는 보상 버전, 스테이지, 아이템 묶음, 필요한 슬롯, 부족 슬롯과 수령 가능 여부를 서버 계산값으로 반환한다.
- 수령은 pending 한 건을 전량 원자 지급하며 부분 수령하지 않는다.
- 수령 중 공간 부족·동시 수령·낙관적 잠금 충돌은 상태 변경 없이 실패한다.
- 동일 멱등 키 재시도는 최초 수령 결과에 수렴한다.

## 기존 계정 소급

소급은 신규 최초 클리어와 같은 보상 생성 경로를 사용한다.

1. dry-run이 대상 계정·스테이지 수, 총 쌀, 품목별 총량과 예상 pending 건수를 산출한다.
2. 승인된 배포 명령이 저장된 최초 클리어 기록을 계정 단위로 처리한다.
3. 이미 같은 reward version 레코드가 있으면 건너뛴다.
4. 쌀·스킬·아이템 처리는 신규 최초 클리어와 동일하다.
5. 계정의 모든 대상이 성공하거나 이미 처리된 경우에만 소급 완료 시각을 기록한다.
6. 중간 실패 계정은 완료로 기록하지 않으며 같은 작업을 재실행할 수 있다.

소급 재료는 신규 보상과 동일하게 거래할 수 있다. dry-run과 배포 후 지표에서 한 번에 늘어나는 쌀·재료·매물량을 추적한다.

## 클라이언트 흐름

- 전투 결과는 즉시 지급 쌀, 즉시 지급 아이템, 수령 대기 아이템과 직접 스킬 해금을 구분한다.
- 체류 획득 요약에는 실제 지급 아이템만 포함하고 pending은 별도 수령 대기 항목으로 표시한다.
- 최초 보상 수령함은 pending 목록과 수령 가능 여부를 제공한다.
- 수령 성공 후 인벤토리·장비·스킬·pending 상태를 다시 조회한다.
- 클라이언트는 보상 수량·슬롯 요구량·승급 가능 여부를 재계산하지 않는다.
- 거래소는 지급 완료된 재료를 기존 거래 가능 재료와 동일하게 취급한다.

## 오류 처리

- 인벤토리 부족은 스테이지 클리어 실패가 아니다.
- pending 수령 공간 부족은 상태 변경 없이 실패하고 최신 슬롯 요구량을 반환한다.
- 같은 최초 클리어·소급 재실행·수령 재시도는 중복 쌀·아이템·스킬 해금을 만들지 않는다.
- 콘텐츠 버전이나 보상 snapshot을 찾을 수 없으면 임의 기본값으로 보정하지 않는다.
- 기존 버전과 새 버전의 수치를 한 세션이나 한 보상 결과에서 섞지 않는다.

## 검증

### 산술·콘텐츠

- 책임 SSOT의 합계와 생성 콘텐츠의 스테이지·단계별 합계가 정확히 일치한다.
- 레벨·적·보상·장비·스킬·아이템 참조와 의존 버전이 완전하다.
- 잘못된 합계·누락 행·알 수 없는 ID·혼합 버전을 activation 전에 거절한다.

### 도메인·PostgreSQL

- 신규 최초 클리어와 기존 계정 소급이 같은 유일 키로 중복 지급을 막는다.
- 쌀 즉시 지급, 아이템 즉시 지급, pending 전환과 공간 확보 후 전량 수령을 검증한다.
- 동시 수령, 응답 유실 재시도, 소급 재실행과 중간 실패 복구를 검증한다.

### 전투·경제

- [성장 SSOT](../../30-domain/progression/ssot.md)의 P50·P90 목표를 seed 기반으로 측정한다.
- [스테이지 SSOT](../../30-domain/world/ssot.md)의 기준 빌드 성공률·부족 성장축 실패·승급 시점을 검증한다.
- 거래소 사용·미사용, 시장 유동성 부족과 주력 재료 편중 표본을 분리한다.
- 소급 dry-run과 배포 후 지표로 쌀·재료 공급과 거래 가격 영향을 확인한다.

### 클라이언트·회귀

- 최초 보상 결과, 직접 스킬 해금과 수령함을 실제 브라우저에서 검증한다.
- 기존 전투 replay·멱등 결과, 치장·보석 해금, 거래소 재료 거래와 10스테이지 무드롭을 회귀 검증한다.

## 작업 상태

설계 승인과 정본 전파로 A-05 기획 상태만 완료로 올린다. 콘텐츠·서버·클라이언트 구현 전에는 개발 미착수, 시뮬레이션·PostgreSQL·브라우저 증거 전에는 검증 부분 검증을 유지한다.
