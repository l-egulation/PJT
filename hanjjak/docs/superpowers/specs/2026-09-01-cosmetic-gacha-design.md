> 이 설계의 시스템 흐름은 보존한다. 도감 단계·도감 전투 효과·콘텐츠 수치는 [2026-09-02 MVP 핵심 수집·성장 콘텐츠 바이블 설계](./2026-09-02-mvp-content-bible-design.md), [치장 SSOT](../../30-domain/cosmetics/ssot.md), [MVP 치장 콘텐츠 v1](../../60-content/cosmetics/mvp-v1.md)의 최신 결정으로 대체됐다.

## 1. 목적

이 문서는 치장 뽑기 시스템의 요구사항 명세를 작성하기 전에 사용자와 합의한 제품 규칙, 책임 경계, 처리 흐름, API 범위와 검증 원칙을 보존한다.

핵심 흐름은 다음과 같다.

```text
재화 확인
→ 뽑기 요청
→ 서버 추첨
→ 치장 지급
→ 신규·중복 처리
→ 도감·세트 갱신
→ 전투 효과 반영
→ 결과 반환
```

클라이언트는 사용자의 뽑기 의도만 전달한다. 확률, 결과, 결제 재화 배분, 치장 지급, 도감 등록, 세트 계산과 전투 효과는 서버가 확정한다.

## 2. 기준과 충돌

현재 기준 문서는 다음과 같다.

- 제품 출시 범위: [MVP 범위](../../70-plans/mvp-release/requirements.md)
- 미래 후보 범위: [미래 범위](../../70-plans/future-content/brief.md)
- 계정·서버 권한: [계정·저장 SSOT](../../30-domain/player/ssot.md)
- 쌀 획득·소비: [성장 SSOT](../../30-domain/progression/ssot.md)
- 아이템 수량·인벤토리: [아이템 SSOT](../../30-domain/items/ssot.md)
- 전투 스탯: [전투 SSOT](../../30-domain/combat/ssot.md)
- 클라이언트 화면 원칙: [클라이언트 UX SSOT](../../30-domain/player/ux/ssot.md)
- 결정 상태: [결정 로그](../../80-decisions/README.md)

현재 [MVP 범위](../../70-plans/mvp-release/requirements.md)는 치장 뽑기를 포함하지 않고, [미래 범위](../../70-plans/future-content/brief.md)는 치장·스킨·컬렉션을 미래 후보로 분류한다. 이번 설계에서는 치장 뽑기·도감·세트 성급 성장을 MVP에 포함하기로 결정했다. 정식 요구사항 승인 시 두 범위 문서와 결정 로그를 함께 갱신해야 한다.

보관 회의 원문의 치장 외형 전용 설명은 이번 설계의 세트 전투 효과와 충돌한다. 정식 명세를 전파할 때 원문은 보존하고, 결정 로그와 새 치장 SSOT에 현재 기준을 명시한다.

## 3. 선택한 문서 구조

### 3.1 채택안: 도메인·콘텐츠·구현 3계층

| 계층 | 계획 경로 | 책임 |
| --- | --- | --- |
| 도메인 규칙 | `docs/30-domain/cosmetics/ssot.md` | 해금, 배너, 결제 우선순위, 치장 보유·성급, 도감, 세트, 선택 상자의 게임 규칙 |
| 콘텐츠 수치 | `docs/60-content/cosmetics/mvp-v1.md` | 배너 비용, 4등급 확률, 활성 치장 풀, 세트 구성, 도감 임계값, 세트별 성급 효과 수치 |
| 구현 요구사항 | `docs/70-plans/cosmetic-gacha/requirements.md` | 기능 요구사항, API 목록, 데이터 책임, 트랜잭션, 멱등성, 동시성, 오류와 검증 |
| 기능 경로 | `docs/30-domain/cosmetics/features/` | 뽑기·도감·승급을 찾는 routing-only 문서 |

이 구조를 선택한 이유는 다음과 같다.

- 규칙과 밸런스 수치를 분리해 콘텐츠 조정이 API·트랜잭션 계약을 바꾸지 않게 한다.
- 요구사항 문서가 규칙의 두 번째 정본이 되는 것을 막는다.
- 뽑기와 치장 성장은 한 원자 흐름으로 연결되므로 별도 도메인으로 과도하게 분리하지 않는다.

### 3.2 검토 후 제외한 안

- 단일 요구사항 문서: 읽기는 쉽지만 저장소의 SSOT 정책을 위반하고 규칙·수치·구현 책임이 섞인다.
- 뽑기와 치장 도메인 완전 분리: 경계는 엄밀하지만 하나의 지급 트랜잭션과 검증 흐름을 두 명세에서 추적해야 해 현재 MVP 규모에는 과하다.

## 4. 범위

### 4.1 포함

- 1-5 최초 클리어 기반 치장 시스템 해금
- 초기 공용 치장 뽑기권 10장 지급
- 전설 세트별 상시 픽업 배너
- 보유 쌀·공용 뽑기권·비용·확률 조회
- 1회·10회 독립 뽑기
- 뽑기권 우선 혼합 결제
- 신규·중복 치장 지급과 도감 자동 등록
- 치장별 보유 수량과 1~5성 수동 성장
- 도감 고유 등록 수·단계·다음 단계 진척
- 세트 완성·세트 성급·단계별 누적 전투 효과
- 픽업별 200회 반복 마일스톤과 세트 선택 상자
- 세트 선택 상자 수령·사용
- 원자성·멱등성·동시성·감사 재현성
- 서버 확정 결과의 클라이언트 표시

### 4.2 제외

- 치장 실제 착용·교체·해제와 외형 렌더링
- 공용 치장 뽑기권의 반복 공급처와 공급량
- 뽑기·도감 화면의 최종 레이아웃, 애니메이션 세부 연출, 접근성 규격
- 뽑기 감사 기록의 보존 기간과 아카이빙 정책
- 5성 이후 중복 치장의 추가 소비처
- 세트 선택 상자 외 일반 보상 상자 시스템
- 상세 HTTP 상태, 공통 오류 envelope, 인증 헤더와 추적 헤더
- 확률 통계 검증의 최종 표본 수와 유의수준

제외 항목은 임의 기본값이나 임시 구현으로 대체하지 않는다. 필요한 기능은 별도 콘텐츠·UX·운영·API 계약에서 확정한다.

## 5. 해금

- 치장 시스템은 계정이 스테이지 1-5를 처음 클리어할 때 해금한다.
- 해금 상태와 공용 치장 뽑기권 10장 지급은 계정당 한 번, 같은 원자적·멱등 처리 단위로 확정한다.
- 같은 최초 클리어 결과가 재전송되거나 재접속해도 해금과 10장 지급을 반복하지 않는다.
- 해금 전에는 치장 전용 조회·명령 API를 모두 거절한다.
- 해금 전 메뉴 잠금 여부와 `1-5 최초 클리어` 조건은 치장 API가 아닌 공통 계정 진행 상태가 제공한다.

## 6. 배너와 확률

### 6.1 배너 구성

- 일반 배너는 제공하지 않는다.
- 모든 전설 치장은 정확히 하나의 전설 세트에 속한다.
- MVP의 각 전설 세트는 상시 픽업 배너 하나와 중첩 가능한 전용 선택 상자 하나에 연결한다.
- 관계는 `전설 세트 1 : 픽업 배너 1 : 선택 상자 1`이다.
- 모든 픽업 배너는 항상 열려 있으며 기간 종료나 회차 초기화가 없다.
- 모든 배너의 1회 쌀 비용은 같다.

### 6.2 등급과 풀

안정 등급 식별자는 다음 네 개다.

- `NORMAL`
- `RARE`
- `EPIC`
- `LEGENDARY`

모든 배너는 같은 노말·희귀·영웅 전체 활성 풀을 사용한다. 배너 간 하위 등급 구성과 개별 확률은 같다.

전설이 당첨되면 해당 픽업 배너가 가리키는 전설 세트 구성품만 나온다. 다른 전설 세트 치장은 나오지 않는다.

### 6.3 추첨

- 서버가 먼저 4등급 중 하나를 추첨한다.
- 선택된 등급 안에서는 모든 활성 치장이 동일한 정수 가중치 `1`을 가진다.
- 1회와 10회의 각 결과는 같은 공개 확률표로 독립 추첨한다.
- 한 요청에서 같은 치장이 여러 번 나올 수 있다.
- 최소 등급 보장, 미보유 보정, 중복 방지, 셔플백과 자연 획득 초기화형 천장은 적용하지 않는다.
- 전설 총확률은 모든 픽업 배너에서 같다.
- 10회 비용은 1회 비용의 정확히 10배이며 할인·추가 결과·보장 보상이 없다.

### 6.4 확률 표현과 공개

- 등급 확률은 백만분율 정수로 관리한다. `1,000,000`이 100%다.
- 각 등급 확률은 0 이상이며 합계는 정확히 `1,000,000`이어야 한다.
- 0보다 큰 확률을 가진 등급은 활성 치장을 최소 1개 가져야 한다.
- 개별 치장 확률은 `등급 확률 ÷ 해당 등급의 활성 치장 수`다.
- API는 등급 확률, 활성 풀, 개별 확률의 정확한 분자·분모와 표시용 퍼센트 문자열을 반환한다.
- 표시 문자열 반올림 때문에 개별 표시값의 합이 등급 표시값과 미세하게 다를 수 있으므로 서버는 분자·분모를 권한 원천으로 제공한다.
- 클라이언트는 확률을 표시할 뿐 추첨에 사용하지 않는다.

## 7. 결제

### 7.1 재화

- 쌀은 기존 공통 계정 지갑의 서버 권한 잔액을 참조한다.
- 공용 치장 뽑기권은 슬롯을 점유하지 않는 서버 권한 계정 재화다.
- 쌀과 뽑기권은 0 이상의 정수만 허용한다.
- 뽑기권 1장은 어느 픽업 배너에서든 정확히 1회 비용 전체를 대체한다.

### 7.2 우선순위와 혼합 결제

- 서버는 요청 시점의 뽑기권을 가능한 만큼 먼저 사용한다.
- 남은 회차는 `남은 유료 회차 × 공통 1회 쌀 비용`으로 계산한다.
- 사용자는 뽑기권을 아끼거나 결제 재화를 선택할 수 없다.
- 예: 10회 요청에서 뽑기권 3장이 있으면 3장과 7회분 쌀을 사용한다.
- 티켓과 쌀을 합친 총 결제 능력이 요청 횟수에 부족하면 전체 요청을 실패시키고 어느 재화도 소비하지 않는다.
- 일부 횟수 실행은 허용하지 않는다.

### 7.3 비용 표시

배너 목록 조회는 현재 잔액을 기준으로 1회·10회 각각 다음 값을 제공한다.

- 예상 사용 뽑기권 수
- 예상 사용 쌀
- 실행 가능 여부
- 부족 원인

실행 시 서버는 최신 잔액으로 비용을 다시 계산한다. 조회 결과는 예약이나 가격 고정이 아니다.

## 8. 치장 보유와 성급

### 8.1 보유 모델

치장은 일반 200슬롯 인벤토리를 점유하지 않는 계정 단위 도감형 상태로 저장한다.

치장별 최소 상태는 다음과 같다.

- `cosmeticId`
- `registeredQuantity`
- `cosmeticStar`

규칙은 다음과 같다.

- 최초 획득: `registeredQuantity=1`, `cosmeticStar=1`
- 같은 치장 중복 획득: `registeredQuantity`를 결과 수만큼 증가
- 5성 이후 중복: 변환·환급하지 않고 같은 치장 수량으로 계속 보관
- 도감 등록 상태: `registeredQuantity >= 1`
- 승급 후에도 기본 소유 1개를 반드시 남김

### 8.2 신규·중복 판정

10회 요청 안에서 같은 미보유 치장이 여러 번 나오면 서버가 결과 순서대로 반영한다.

- 첫 번째 결과: 신규
- 뒤의 같은 치장 결과: 중복

응답은 추첨 순서를 보존한다. 클라이언트가 요청 전 보유 상태만으로 신규·중복을 재계산하지 않는다.

### 8.3 목표 성급 일괄 승급

치장의 최대 성급은 5다. 각 다음 성급에 필요한 같은 치장 소비량은 다음과 같다.

| 목표 단계 | 추가 소비 수량 |
| ---: | ---: |
| 2성 | 1 |
| 3성 | 2 |
| 4성 | 3 |
| 5성 | 4 |

사용자는 현재 성급보다 높고 5 이하인 `targetStar`를 요청한다. 서버는 현재 성급 다음 단계부터 목표 성급까지의 소비량을 합산한다.

예: 1성에서 4성은 `1 + 2 + 3 = 6개`를 소비한다.

승급은 다음 상태를 하나의 트랜잭션으로 확정한다.

- 소유권·현재 성급·목표 성급 검증
- 소비 후 `registeredQuantity >= 1` 검증
- 필요한 같은 치장 수량 전체 소비
- `cosmeticStar`를 목표 성급으로 변경
- 영향받는 세트 성급과 효과 재계산
- 실행 중 전투 스탯 갱신
- 멱등 결과 저장

중간 성급을 별도 커밋하지 않는다. 전체 조건이 맞지 않으면 수량과 성급을 모두 유지한다.

컬렉션 조회는 각 치장에 현재 성급에서 가능한 목표 성급별 누적 필요 수량과 실행 가능 여부를 제공한다. 별도 승급 미리보기 API는 두지 않는다.

## 9. 도감

- `uniqueRegisteredCount`는 세트 소속 여부와 무관하게 `registeredQuantity >= 1`인 서로 다른 모든 치장 수다.
- 같은 치장의 중복 수량과 성급은 고유 등록 수를 늘리지 않는다.
- 도감 단계는 활성 콘텐츠 버전의 고유 치장 수 임계값으로 계산한다.
- 임계값은 엄격히 증가해야 한다.
- 응답은 현재 고유 등록 수, 현재 단계, 현재 단계 임계값, 다음 단계 임계값과 다음 단계까지 필요한 고유 치장 수를 제공한다.
- 도감 단계는 전투 스탯이나 다른 능력치를 제공하지 않는다.
- 도감 임계값이 바뀌면 모든 계정은 최신 활성 콘텐츠 설정과 현재 고유 등록 수로 단계를 재계산한다.

## 10. 세트

### 10.1 구성

- 세트는 동일 등급의 서로 다른 치장 2개 이상으로 구성한다.
- 치장 하나는 동시에 최대 한 세트에만 속한다.
- 세트는 부위 개념을 사용하지 않고 구성 `cosmeticId` 목록만 가진다.
- 노말·희귀·영웅 치장은 세트 소속일 수도, 미소속일 수도 있다.
- 모든 전설 치장은 정확히 하나의 전설 세트에 속한다.
- 출시된 세트의 구성 목록은 영구 불변이다.
- 기존 미소속 치장은 후속 업데이트에서 새 세트를 만들 때 그 새 세트의 구성품으로 편입할 수 있다.
- 기존 출시 세트에는 구성품을 추가·삭제·교체하지 않는다.

### 10.2 세트 성급

세트 성급은 모든 구성 치장의 현재 성급 중 최솟값이다.

```text
setStar = min(cosmeticStar of every set member)
```

미등록 구성품은 0성으로 본다. 구성품 하나라도 미등록이면 세트는 0성이고 효과가 없다. 모든 구성품을 최초 획득하면 각 치장이 1성이므로 세트 1성이 즉시 활성화된다.

### 10.3 세트 효과

- 모든 세트는 1~5성 각각에 단계별 증가량 행을 가진다.
- 현재 세트 성급 이하의 모든 행을 합산한다.
- 예: 5성 세트는 1·2·3·4·5성 증가량을 모두 합산한다.
- 완성된 모든 세트의 활성 효과를 스탯 ID별로 다시 합산한다.
- 치장 시스템은 원시 증가량 합계만 제공한다. 다른 성장축과의 계산 순서·상한은 전투 SSOT가 소유한다.
- 스탯 ID는 서버 허용 목록에 등록된 값만 사용할 수 있다.
- MVP 콘텐츠 버전은 `attack`, `maxHp`, `defensePenetration`을 사용한다.
- MVP의 세 스탯 증가량은 0 이상의 정수이며, 성급 상승이 이미 활성화된 효과를 감소시키지 않는다.
- 새 스탯 종류는 전투 규칙과 계약을 먼저 확장한 뒤 콘텐츠에서 사용할 수 있다.
- 세트 효과 수치가 새 콘텐츠 버전으로 바뀌면 기존 계정도 최신 활성 효과표로 재계산한다.
- 기존 미소속 치장을 구성품으로 하는 새 세트가 활성화되면, 현재 보유·성급 상태로 새 세트 성급과 효과를 즉시 계산해 기존 계정에도 반영한다.

## 11. 전투 실시간 반영

치장 획득, 치장 승급 또는 최신 활성 세트 효과 버전 전환으로 전체 세트 효과가 바뀌면 실행 중인 전투에 즉시 반영한다.

- 공격력과 방어 관통: 새 합계를 즉시 사용
- 최대 HP 증가: 현재 HP도 같은 증가량만큼 증가
- 최대 HP 감소: 현재 HP도 같은 감소량만큼 감소
- 살아 있는 캐릭터의 감소 후 현재 HP 하한: 1
- 이미 HP가 0이거나 패배가 확정된 상태: 효과 증가로 부활하지 않고 0 유지

효과 변경 전후 상태와 전투 반영은 같은 서버 권한 변경 흐름에서 일관되게 관찰되어야 한다.

## 12. 픽업 200회 마일스톤

### 12.1 누적

- 픽업 배너별 성공 결과 수를 계정에 영구 누적한다.
- 1회 성공은 `+1`, 10회 성공은 `+10`이다.
- 쌀, 뽑기권, 혼합 결제 여부는 누적에 영향을 주지 않는다.
- 실패·롤백·같은 멱등 키 재요청·선택 상자 사용은 누적을 늘리지 않는다.
- 자연 추첨으로 픽업 세트 치장을 얻어도 누적은 초기화되지 않는다.

### 12.2 수령 자격

200회마다 해당 세트 선택 상자 수령 자격 1개가 생긴다.

```text
claimableBoxCount = floor(totalSuccessfulDraws / 200) - claimedBoxCount
```

- 200·400·600회처럼 제한 없이 반복한다.
- `totalSuccessfulDraws`와 `claimedBoxCount`를 분리해 영구 보존한다.
- 미수령 자격은 배너 상태와 무관하게 만료되지 않는다.
- 사용자는 1개, 미수령 범위의 지정 수량 또는 전체를 한 번에 수령할 수 있다.

### 12.3 인벤토리 수령

- 세트 선택 상자는 동일 `boxItemId`끼리 수량 중첩한다.
- 기존 스택이 있으면 빈 슬롯 없이 수량을 늘린다.
- 기존 스택이 없으면 공용 200슬롯 인벤토리의 빈 슬롯 1개가 필요하다.
- 요청 수량과 무관하게 같은 상자 수령에는 최대 1슬롯만 필요하다.
- 공간이 부족하면 `claimedBoxCount`와 인벤토리를 모두 유지하고 전체 요청을 실패시킨다.
- 일부 수령으로 자동 축소하지 않는다.

### 12.4 선택 상자 사용

- 선택 상자는 한 번에 1개만 사용한다.
- 사용자는 상자가 가리키는 불변 세트 구성품 전체 중 `cosmeticId` 하나를 고른다.
- 서버는 상자·세트 매핑, 선택 치장의 구성원 여부와 콘텐츠 유효성을 검증한다.
- 성공하면 상자 1개 소비와 치장 1개 지급을 한 트랜잭션으로 처리한다.
- 잘못된 선택이면 상자를 소비하지 않는다.
- 지급 치장은 뽑기 결과와 같은 신규·중복·도감·세트·전투 반영 규칙을 따른다.
- 선택 상자 사용은 픽업 성공 횟수에 포함하지 않는다.

## 13. 서버 처리 흐름

### 13.1 뽑기

```text
인증·해금 확인
→ bannerId와 활성 콘텐츠 버전 검증
→ 계정 재화 처리 직렬화
→ count 검증
→ 티켓 우선 비용 재계산
→ 티켓·쌀 충분 여부 검증
→ 재화 조건부 차감
→ count개 독립 추첨
→ 결과 순서대로 치장 신규·중복 처리
→ 도감·세트·전체 효과 재계산
→ 픽업 성공 횟수 증가
→ 마일스톤 수령 가능 수 재계산
→ 전투 실시간 반영
→ 감사 기록과 멱등 성공 결과 저장
→ 응답
```

위 상태는 모두 함께 성공하거나 모두 롤백한다.

### 13.2 동시성

- 클라이언트는 처리 중 버튼을 잠그지만 이것은 정합성 보장이 아니다.
- 서로 다른 멱등 키의 동시 뽑기 요청은 계정의 공통 쌀·뽑기권 기준으로 직렬 처리하거나 동등한 원자 조건부 차감을 사용한다.
- 먼저 확정된 요청 이후의 최신 잔액으로 다음 요청의 가능 여부를 다시 판단한다.
- 쌀·뽑기권은 음수가 될 수 없다.

### 13.3 멱등성

- 상태 변경 명령은 공통 요청 헤더의 멱등 키를 요구한다.
- 같은 계정·명령 종류·멱등 키의 재요청은 입력 일치 여부를 검증한다.
- 입력이 같고 최초 요청이 성공했다면 최초 성공 결과를 그대로 반환한다.
- 재추첨, 추가 차감, 추가 지급, 추가 마일스톤 누적을 하지 않는다.
- 같은 키로 다른 입력을 보내면 상태 변경 없이 충돌로 거절한다.

## 14. 감사와 재현성

성공한 뽑기 요청은 최소한 다음 정보를 추적 가능하게 기록한다.

- 계정과 요청 식별자
- 멱등 키
- `bannerId`
- 요청 `count`
- 확률표·치장 풀·비용 콘텐츠 버전
- 요청 처리 시점의 비용 계산과 실제 티켓·쌀 차감
- 추첨 결과 순서
- 결과별 `cosmeticId`, 등급, 신규·중복 판정
- 지급 후 수량·성급
- 픽업 누적 전후와 새 수령 가능 수
- 서버 내부 감사 재현 토큰
- 최종 성공 상태

감사 재현 토큰은 운영 검증에 사용하고 클라이언트에 노출하지 않는다. 보존 기간은 운영 명세가 소유한다.

## 15. 콘텐츠 버전 유효성

활성 치장 콘텐츠 버전은 배너 조회·실행 전에 다음을 만족해야 한다.

- 등급 enum이 허용 목록과 일치
- 등급 확률 합계가 정확히 `1,000,000`
- 전설 총확률과 1회 쌀 비용이 모든 배너에서 동일
- 확률이 0보다 큰 등급의 풀이 비어 있지 않음
- 모든 배너가 동일한 노말·희귀·영웅 전체 활성 풀을 사용
- 전설 세트·배너·선택 상자가 1:1:1로 연결
- 픽업 전설 풀과 선택 상자 선택 목록이 해당 불변 세트 구성 목록과 일치
- 세트가 동일 등급의 고유 치장 2개 이상으로 구성
- 치장이 최대 한 세트에만 속함
- 모든 전설 치장이 정확히 한 전설 세트와 획득 배너를 가짐
- 모든 세트가 1~5성 단계별 효과 행을 가짐
- 효과 스탯 ID가 서버 허용 목록 안에 있음
- 도감 임계값이 엄격히 증가

하나라도 위반하면 서버는 해당 콘텐츠 버전의 배너 조회·뽑기 실행을 정상 제공하지 않는다. 누락 풀 제외, 확률 재분배, 기본 배너 대체나 임의 치장 지급으로 보정하지 않는다.

## 16. API 설계

상세 DTO, HTTP 상태, 공통 인증·오류 envelope는 후속 API 계약이 소유한다. 요구사항 명세는 다음 리소스 경계와 핵심 입력·출력을 정의한다.

| 기능 | Method·Path | 핵심 입력 | 핵심 출력 |
| --- | --- | --- | --- |
| 배너 목록 | `GET /api/v1/cosmetic-gacha/banners` | 없음 | 상시 픽업, 비용, 쌀·티켓 잔액, 1회·10회 예상 결제, 누적·미수령 상자 수 |
| 배너 상세·확률 | `GET /api/v1/cosmetic-gacha/banners/{bannerId}` | 경로 `bannerId` | 등급 확률, 등장 치장, 개별 확률 분자·분모·표시값, 콘텐츠 버전 |
| 뽑기 실행 | `POST /api/v1/cosmetic-gacha/banners/{bannerId}/draws` | body `count`만, 공통 멱등 키 | 결과 목록, 소비·잔액, 도감·세트 변화, 누적·미수령 수 |
| 마일스톤 수령 | `POST /api/v1/cosmetic-gacha/banners/{bannerId}/milestone-claims` | 수령 모드와 필요 시 수량, 공통 멱등 키 | 지급 상자 수, 남은 미수령 수, 인벤토리 스택 상태 |
| 선택 상자 사용 | `POST /api/v1/cosmetic-selector-boxes/{boxItemId}/open` | `cosmeticId`, 공통 멱등 키 | 신규·중복, 치장·도감·세트·전투 효과 변화 |
| 컬렉션 조회 | `GET /api/v1/cosmetics/collection` | 없음 | 보유 치장, 수량·성급, 도감 진척, 세트 성급·효과, 전체 효과, 목표 성급 비용표 |
| 치장 승급 | `POST /api/v1/cosmetics/{cosmeticId}/upgrades` | `targetStar`, 공통 멱등 키 | 소비·남은 수량, 성급·세트·전체 효과 변경 전후 |

뽑기 요청 body에는 `paymentType`, 사용자 ID, 확률, 결과나 지급 목록을 받지 않는다. `bannerId`는 경로에서만 받는다.

Front가 별도로 결과 등록, 도감 추가, 세트 효과 갱신 API를 호출하지 않는다. 전용 뽑기 기록 조회 API도 MVP에 포함하지 않는다. 응답 유실은 같은 멱등 키 재요청으로 복구한다.

## 17. 응답 의미

### 17.1 뽑기 성공

최소 다음 정보를 반환한다.

- 결과 순서
- 결과별 `cosmeticId`, 표시 정보, 등급
- 결과별 신규·중복 여부
- 결과별 지급 후 `registeredQuantity`, `cosmeticStar`
- 실제 소비 뽑기권 수와 쌀
- 실행 후 뽑기권·쌀 잔액
- 도감 고유 수·단계·다음 단계 진척 변경 전후
- 영향받은 세트의 성급과 활성 효과 변경 전후
- 전체 활성 세트 효과 합계 변경 전후
- 픽업 누적 횟수 전후
- 새 미수령 선택 상자 수

### 17.2 승급 성공

- 소비한 같은 치장 수량
- 남은 `registeredQuantity`
- 이전·새 `cosmeticStar`
- 영향받은 세트 성급과 활성 효과 변경 전후
- 전체 활성 세트 효과 합계 변경 전후

### 17.3 선택 상자 사용 성공

치장 획득 부분은 뽑기와 같은 신규·중복·도감·세트 의미를 사용한다. 사용 후 해당 상자 스택 수량도 반환한다.

### 17.4 실패

실패는 클라이언트가 재시도 가능 여부와 사용자 조치를 구분할 수 있는 도메인 원인 코드를 포함한다. 도메인 검증 실패는 상태를 바꾸지 않는다.

| Database | 비음수 재화, 계정별 치장 수량·성급, 배너별 누적·수령 수, 상자 스택, 멱등 결과와 감사 기록의 영속 제약 | 단독으로 확률·세트 효과 규칙 결정 |
| Content | 비용·확률·활성 풀·세트 구성·도감 임계값·세트 효과와 버전 | 계정 상태·추첨 결과·재화 차감 결정 |
| Combat | 허용 스탯 ID, 다른 성장축과의 합산 순서·상한, 전투 상태 갱신 | 치장 보유·세트 성급 계산 |
| QA | 기능·원자성·멱등성·동시성·재현성·분포·전투 반영 검증 | 짧은 표본의 관측 비율만으로 확률 구현 합격 판정 |

## 19. 오류 범주

정식 요구사항은 최소 다음 오류 의미를 구분해야 한다.

- 인증 필요
- 치장 시스템 미해금
- 존재하지 않는 배너
- 유효하지 않은 콘텐츠 버전 또는 일시적 배너 비활성
- 허용되지 않은 `count`
- 티켓·쌀 합산 결제 능력 부족
- 같은 멱등 키의 입력 충돌
- 존재하지 않거나 미보유 치장
- 허용되지 않은 목표 성급
- 승급용 같은 치장 수량 부족
- 수령 가능한 마일스톤 상자 없음
- 잘못된 수령 수량
- 인벤토리 공간 부족
- 존재하지 않거나 미보유 선택 상자
- 선택 상자와 맞지 않는 `cosmeticId`
- 동시 상태 변경 충돌
- 일시적 서버 처리 실패

오류 코드는 정식 요구사항에서 안정 식별자로 정의하되 HTTP 상태와 envelope는 공통 API 계약으로 넘긴다.

## 20. 검증 설계

### 20.1 정상 기능

- 1-5 최초 클리어 시 해금과 티켓 10장 한 번 지급
- 1회·10회 티켓 전액 결제
- 1회·10회 쌀 전액 결제
- 10회 티켓+쌀 혼합 결제
- 신규 치장 획득
- 같은 요청 안의 동일 치장 신규 후 중복 판정
- 기존 치장 중복 수량 증가
- 도감 고유 수·단계·다음 진척 갱신
- 세트 최초 완성과 1성 효과 활성
- 세트 일부 치장 승급 후 최솟값 유지
- 마지막 최저 성급 치장 승급 후 세트 성급 상승
- 1성에서 목표 2·3·4·5성 일괄 승급 비용
- 200·400·600회 반복 마일스톤
- 1개·지정 수량·전체 상자 수령
- 상자 1개 사용과 선택 치장 지급

### 20.2 실패와 롤백

- 해금 전 모든 치장 API 거절
- 존재하지 않는 배너
- 1·10 이외 `count`
- 티켓과 쌀 합산 부족 시 전체 실패
- 콘텐츠 풀·확률·세트·상자 매핑 오류 시 뽑기 차단
- 잘못된 목표 성급 또는 승급 수량 부족
- 수령 가능한 수보다 큰 요청
- 새 상자 스택을 만들 인벤토리 공간 부족
- 다른 세트 구성품으로 선택 상자 사용
- 각 트랜잭션 중간 실패에서 모든 상태 롤백

### 20.3 멱등성과 동시성

- 같은 멱등 키 재요청이 최초 결과를 그대로 반환
- 같은 키·다른 입력이 상태 변경 없이 충돌
- 서로 다른 키의 동시 뽑기가 최신 계정 잔액으로 직렬 확정
- 뽑기와 다른 쌀 소비처가 동시에 실행되어도 음수·이중 사용 없음
- 마일스톤 수령 재시도에서 상자 중복 지급 없음
- 상자 사용 재시도에서 상자 중복 소비·치장 중복 지급 없음
- 승급 재시도에서 수량 중복 소비·성급 초과 상승 없음

### 20.4 확률과 감사

- 고정 콘텐츠 버전과 감사 재현 토큰으로 개별 결과 재현
- 등급 경계값과 풀 선택 경계 검증
- 10회 각 슬롯의 독립성 검증
- 대량 표본에서 등급과 개별 치장 분포를 통계적 허용구간으로 검증
- 짧은 표본이 공개 확률과 정확히 일치해야 한다고 요구하지 않음
- 최종 표본 수·유의수준·판정식은 별도 QA 계획에서 확정

### 20.5 전투

- 신규 획득으로 세트가 완성될 때 즉시 효과 반영
- 승급으로 세트 최솟값이 오를 때 단계별 누적 효과 반영
- 영향 없는 구성품 승급은 세트 효과를 바꾸지 않음
- 여러 세트의 같은 스탯 원시값 합산
- 최대 HP 증가량만큼 현재 HP 증가
- 최대 HP 감소량만큼 현재 HP 감소, 살아 있으면 최소 1 유지
- HP 0 또는 패배 확정 상태는 효과 증가로 부활하지 않음
- 콘텐츠 효과 버전 전환에도 같은 실시간 규칙 적용

## 21. 구현 전 필수 콘텐츠 입력

정식 구현을 시작하려면 `docs/60-content/cosmetics/mvp-v1.md`에서 최소 다음 값을 승인해야 한다.

- 모든 배너의 공통 1회 쌀 비용
- 노말·희귀·영웅·전설 등급 확률
- 활성 노말·희귀·영웅 치장 목록
- 모든 전설 세트와 구성 치장 목록
- 전설 세트별 배너 ID와 선택 상자 ID
- 치장별 표시 메타데이터와 등급
- 노말·희귀·영웅의 세트 구성 또는 미소속 상태
- 도감 단계 임계값
- 모든 세트의 1~5성 단계별 스탯 증가량

이 값들은 구조적으로 별도 콘텐츠 정본의 책임이다. 요구사항 명세나 구현 코드에 임의 상수로 넣지 않는다.
