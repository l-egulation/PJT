## Implemented contract

- `packages/contracts/raid.tsp` defines the nine required routes:
  - `GET /api/v1/raid`
  - `GET /api/v1/raid/ranking?cursor=&limit=`
  - `GET /api/v1/raid/claims`
  - `GET /api/v1/raid/attempts/current`
  - `POST /api/v1/raid/attempts`
  - `POST /api/v1/raid/attempts/{attemptId}/retry`
  - `POST /api/v1/raid/attempts/{attemptId}/confirm`
  - `POST /api/v1/raid/attempts/{attemptId}/discard`
  - `POST /api/v1/raid/claims/{claimId}`
- Every POST requires the standard UUID `Idempotency-Key`; UUID path types are explicit for `attemptId` and `claimId`.
- Start input is a closed object with only the closed `REWARD | PRACTICE` mode enum. No client damage, grade, contribution, reward, seed, account, or rank fields are accepted.
- Start, retry, and current-attempt responses reference the same server-authored `RaidAttemptView` shape, including persisted input snapshot, authoritative current/terminal result, completion timing, and rendering timeline.
- Timeline events use closed event/actor domains and include sequence, logical tick, nullable actor/target, nullable damage/critical/HP values, and applicable escalation values.
- `RaidErrorEnvelope` uses the closed `RaidErrorCode` enum, while the pre-existing shared `ErrorEnvelope.code` remains `string` for backward compatibility.
- Required raid errors are closed and exact: locked content, no slot, running/result held, attempt limit, invalid transition, zero-damage confirmation, reward capacity, stale/settled session, main-battle transition failure, claim not found/already claimed, state-version conflict, and reused idempotency key.
- Required non-negative counters are int64 with minimum constraints; `currentRank` is nullable with minimum 1, and `topEntries` has no max-items constraint so competitive rank-100 ties can all be returned.
