# AGENTS.md

## 목적과 적용 범위

이 저장소는 현재 `한짝` 프로젝트의 구현 전 기획·설계 단계다. 이 파일의 규칙은 저장소 전체에 적용하며, 특히 `docs/`의 게임 중심 문서 계층과 `docs/wiki`의 보존·운영 경로를 통제한다.

코드, 패키지 매니페스트, DB 마이그레이션, 배포 파일은 사용자가 명시적으로 구현을 요청하기 전까지 만들지 않는다. 설계 변경은 문서로만 반영한다.

## Jira 프로젝트

- Atlassian MCP에서 확인된 Jira 프로젝트는 `S15P21B107`이다.
- 프로젝트 키와 이름은 모두 `S15P21B107`, 프로젝트 ID는 `22550`, 사이트는 `https://ssafy.atlassian.net`이다.
- Jira 작업을 조회하거나 변경할 때는 이 프로젝트를 사용하고, Confluence 스페이스로 해석하지 않는다.
- Jira 이슈를 조회·생성·수정·전환하기 전에 [JIRA-RULES.md](./JIRA-RULES.md)를 읽고, 프로젝트·에픽·필드·상태 전환·AI 에이전트 규칙을 따른다.
- Jira는 실행 기록을 소유하며 게임 정책을 확정하지 않는다. 정책 충돌 시 `docs/wiki/00-meta/ssot-policy.md`와 `docs/wiki/00-meta/source-map.md`를 우선한다.

## 작업 시작 전에 반드시 읽을 문서

질문이나 변경 요청을 받으면 다음 순서로 확인한다.

1. `docs/README.md` — 문서 체계 진입점
2. `docs/wiki/00-meta/ssot-policy.md` — SSOT 운영 규칙
3. `docs/wiki/00-meta/wiki-structure.md` — 경로와 문서 유형
4. `docs/wiki/00-meta/source-map.md` — 주제별 정본과 책임 문서
5. 요청 주제의 `ssot.md`와 해당 `features/` 색인 (`docs/30-domain`, `docs/40-systems`, `docs/50-architecture`)
6. 충돌이 있으면 `docs/80-decisions/README.md`와 `docs/wiki/05-meetings/records`의 관련 회의 원문
7. 실행 상태나 완료 기준이 필요하면 `docs/wiki/06-delivery/tasks`

구형 `docs/product`·`docs/architecture`와 이전 `docs/wiki` 일반 경로는 호환 안내문일 뿐 정본이 아니다. Notion 원문은 `docs/wiki/99-archive/notion`에서만 참고한다.

## 문서 권한 모델

| 문서 유형 | 책임 | 작성 규칙 |
| --- | --- | --- |
| `ssot` | 해당 주제의 규칙·수치·상태 전이·허용 목록 | 하나의 주제에 정본 하나만 둔다. |
| `feature-index`, `feature-route` | 도메인과 기능을 찾는 경로 | 정책·수치·상태·완료 여부를 작성하지 않고 SSOT와 작업 문서만 링크한다. |
| `task` | 실행 상태·완료 기준·선행 작업·증거 | 도메인 규칙을 복사하지 않는다. |
| `decision` | 결정의 상태·전파 여부·충돌 | 회의 내용을 현재 정책으로 자동 승격하지 않는다. |
| `reference` | 설계 해석에 필요한 참고 자료·실험 결과 | 현재 정책의 단독 근거가 아니다. |
| `archive` | Notion 원문·DB 스키마·행 속성·첨부 메타데이터 | 원문을 삭제·정리·현재 정책으로 재해석하지 않는다. |
| `_index.md` | 탐색과 링크 | 요약이 필요해도 규칙의 두 번째 정본을 만들지 않는다. |

하나의 사실은 하나의 책임 문서에서만 정의한다. 다른 문서는 링크, 영향, 질문, 검증 결과만 기록한다.

## SSOT 편집 규칙

- 변경하려는 주제의 정본을 `source-map.md`에서 먼저 찾는다.
- 규칙·수치·필드·허용 목록은 해당 SSOT 한 곳만 수정한다.
- 다른 도메인의 필드나 규칙을 복사하지 말고 상대 SSOT를 링크한다.
- 기능 경로 문서는 제목과 책임 연결만 제공한다. 작업 상태는 task 문서에만 둔다.
- 회의록·원문·레거시 문서의 내용을 현재 기준으로 임의 확정하지 않는다.
- 서로 다른 기준이 발견되면 양쪽 출처를 보존하고 `decisions.md`에 `unresolved` 또는 적절한 상태로 등록한다.
- 결정이 `confirmed`로 전파될 때만 관련 SSOT와 영향을 받는 작업 문서를 함께 갱신한다.
- 미확정 값을 숨기거나 최신처럼 보이게 정규화하지 않는다. `working`, `candidate`, `legacy`, `conflict-aware`, `unresolved` 상태를 유지한다.
- 원문 보관 파일은 원문 전사를 수정하지 않는다. 회수 오류는 별도 보정 메모와 출처를 추가한다.
- Notion으로 내용을 되돌려 쓰거나 Notion 페이지를 수정하는 작업은 사용자가 별도로 요청한 경우에만 한다.

## 구현 변경과 문서 현황 동기화

- 소스 코드, 패키지 매니페스트, API·콘텐츠 계약, DB 마이그레이션, 배포·운영 설정을 새로 만들거나 수정한 작업은 코드 변경만으로 완료하지 않는다. 같은 작업 안에서 구현 현황을 문서 시스템에 갱신한다.
- 먼저 변경과 연결된 `docs/wiki/06-delivery/tasks/<그룹>/<code>.md`를 찾아 실제 구현·검증 상태와 증거 링크를 갱신하고, `docs/wiki/06-delivery/tasks/_index.md`의 해당 행도 같은 상태로 맞춘다. 일부만 구현했으면 완료로 올리지 않고 부분 범위와 남은 범위를 명시한다.
- 구현 증거에는 변경된 코드·계약·마이그레이션 경로와 실제 수행한 빌드·테스트·스모크 시나리오의 결과를 기록한다. 컴파일 성공만으로 기능 완료나 인수 완료를 주장하지 않는다.
- 해당 기능에 별도 구현 증거 문서가 있으면 함께 갱신한다. 기능 라우트와 기능 색인에는 상태나 완료 여부를 복제하지 않고 task·증거 문서 링크만 유지한다.
- 변경과 연결된 task가 없으면 `새 작업` 규칙에 따라 실행 상태를 소유할 task를 먼저 추가하고, A–K 색인과 담당 기능 경로에서 찾을 수 있게 연결한다.
- 구현으로 저장소의 단계나 제공 범위를 설명하는 기존 안내 문장이 거짓이 되면 해당 안내도 같은 작업에서 바로잡되, 상세 실행 상태의 정본은 task 문서에만 둔다.
- 정책·규칙·수치가 함께 변경된 경우에는 구현 현황 갱신과 별도로 `source-map.md`에서 찾은 해당 SSOT와 필요한 결정 로그를 갱신한다. 구현이 존재한다는 이유만으로 정책을 확정하거나 미해결 값을 해소하지 않는다.

## 위키 확장 규칙

### 새 도메인

새 도메인은 다음 구조를 갖춘다.

```text
docs/30-domain/<domain>/
├─ README.md
├─ ssot.md
└─ features/
   └─ _index.md
```

`ssot.md`에는 `doc_kind: ssot`, `owner_domain`, `authority_level`을 front matter에 넣고, `docs/wiki/00-meta/source-map.md`에 정본 경로를 등록한다. 상위 도메인 README에도 규칙 정본과 기능 색인을 추가한다. 세부 책임이 있는 도메인은 목표 계층 안에서 하위 디렉터리로 분리할 수 있다.

### 새 기능

기능은 담당 도메인의 `features/<slug>.md`로 추가한다. 새 기능 제안의 계획 문서는 먼저 `docs/70-plans/<feature>/`에 둔다.

- `doc_kind: feature-route`와 `authority_level: routing-only`를 사용한다.
- 기능 문서에는 기능 이름, 담당 SSOT 링크, 관련 작업 링크, 결정 로그 링크만 둔다.
- 기능 문서에 성공 조건·상태값·숫자·도메인 규칙을 새로 정의하지 않는다.
- 기능 색인과 도메인 색인에 링크를 추가하고, 상대 링크가 유효한지 검사한다.

### 새 작업

Notion 작업을 추가하거나 작업 구조를 확장할 때는 `docs/wiki/06-delivery/tasks/<그룹>/<code>.md`에 보존한다.

- 원문 `notion_id`, `source_url`, `snapshot_date`를 유지한다.
- 상태·완료 기준·선행 작업·증거는 작업 문서가 소유한다.
- 도메인 정책은 관련 SSOT 링크로 연결하고 작업 문서에 복사하지 않는다.
- A–K 색인과 해당 기능 경로에서 새 작업을 찾을 수 있게 한다.

### 새 결정

`docs/80-decisions/README.md`에 주제, 최신 출처, 상태, 현재 사용 기준, 영향을 받는 SSOT와 작업을 기록한다. 확인되지 않은 회의 제안은 `confirmed`로 표현하지 않는다.

## Notion 원문 이동 규칙

- Notion MCP에서 회수한 페이지 본문과 속성은 `99-archive/notion` 또는 해당 날짜·작업 경로에 보존한다.
- 페이지 원문에는 `notion_id`, `source_url`, `snapshot_date`를 둔다.
- 데이터베이스는 스키마, 행 export, 현재 실행 문서를 분리한다.
- 작업 페이지는 원문 속성과 전사 내용을 모두 보존하되, 현재 규칙은 SSOT에서만 관리한다.
- 첨부 바이너리를 회수할 수 없으면 파일명·첨부 ID·원문 위치·접근 실패 상태를 `attachments.md`에 남긴다. 내용을 추정하거나 재작성하지 않는다.
- 새 스냅샷을 추가할 때 기존 스냅샷과 원문을 덮어쓰지 말고 기준일을 구분한다.

## 충돌 해결 주의사항

- 브랜치 병합·rebase·cherry-pick에서 충돌 표시를 제거한 것만으로 완료하지 않는다. 양쪽 브랜치가 추가한 파일·계약·설정·마이그레이션을 함께 보존해야 하는지 확인하고, 병합 결과 전체를 다시 검수한다.
- Flyway 마이그레이션을 추가하거나 마이그레이션 파일이 포함된 충돌을 해결할 때는 `apps/game-api/src/main/resources/db/migration` 전체에서 버전이 유일한지 확인한다. 서로 다른 파일이 같은 `V<version>__` 접두사를 가져서는 안 된다.
- Flyway 버전이 충돌하면 이미 `main` 또는 운영 DB에 적용된 migration은 이름·버전·내용을 변경하지 않는다. 아직 적용되지 않은 신규 migration을 다음 미사용 버전으로 재번호화하고, 해당 경로를 참조하는 테스트·문서·배포 명령을 함께 갱신한다.
- 충돌 해결 후 `FlywayMigrationVersionTest`와 영향받은 migration·Spring context 테스트를 실행한다. 처리된 runtime resources에도 동일 버전 파일이 중복되지 않는지 확인한다.

## 검수 규칙

문서 변경 후 다음을 확인한다.

- `rg --files docs`로 새 문서가 올바른 계층에 있는지 확인한다.
- 모든 상대 Markdown 링크가 실제 파일을 가리키는지 검사한다.
- 새 SSOT의 `owner_domain`과 `docs/wiki/00-meta/source-map.md`의 경로가 일치하는지 확인한다.
- Notion 원문 파일의 식별자·출처 URL·스냅샷 날짜 누락을 확인한다.
- A–K 작업 수와 기능 경로 연결이 끊기지 않았는지 확인한다.
- `git diff --check`와 `git status --short`로 공백 오류와 의도하지 않은 파일을 확인한다.
- 구현 요청이 없었다면 소스 코드나 실행 파일이 생성되지 않았는지 확인한다.

## 금지 사항

- `_index.md`, feature-route, task, 회의록에 SSOT 규칙을 복제하지 않는다.
- 오래된 문서의 숫자나 규칙을 최신 기준으로 조용히 덮어쓰지 않는다.
- unresolved 충돌을 추측으로 해결하지 않는다.
- 원문 보관소의 전사와 첨부 식별자를 삭제하지 않는다.
- 저장소 전체를 대상으로 하는 파괴적 삭제·초기화 명령을 사용하지 않는다.
- 사용자가 요청하지 않은 구현·외부 서비스 변경·Notion 수정은 수행하지 않는다.

## 응답 시 지켜야 할 것

- 답변에는 판단 근거가 된 SSOT 경로를 명시한다.
- 현재 기준과 미해결 사항을 구분해서 표현한다.
- 작업 상태를 말할 때는 해당 task 문서의 상태를 사용한다.
- 문서 구조를 바꿨다면 새 진입점과 영향받는 SSOT를 함께 안내한다.
